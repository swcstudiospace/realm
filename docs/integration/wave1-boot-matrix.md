# Wave 1 boot matrix

This page is the production-stack boot status of the five wave 1 hosts (`claude`, `codex`, `opencode`, `kimi`, `kimi-code`): whether a real host, started through its own CLI, booted Realm against the production stack and listed its tools, with the procedure, the evidence and the limits. The Disposition column is a view of the T3 status in the evidence registry (`test/support/host-registry.ts`), and a test (`test/docs/wave1-boot-matrix.test.ts`) ties each row to it, so a row cannot claim a result the registry does not hold. The per-host summary is the [Host support matrix](host-support-matrix.md), the unverified items and their lift conditions are on [Host plugin gaps](host-plugin-gaps.md), and the contract the recipes follow is [Host plugin contract and installer](host-plugin-contract.md).

A skipped test is `not-run`, never a pass. A cell that names no date and no version has no result behind it.

Rehearsals cover one machine and one version per host, with the digest-pinned image already present (GAP-31-03, GAP-22-02). The three production tiers attach cold, with no warm-up: a cold first attach no longer exceeds a host's connect timeout, shown on 2026-11-18 (GAP-31-04, GAP-23-02, closed, below). `kimi` and `kimi-code` were not run: `kimi` is archived, and installing Kimi Code here needs an owner decision (GAP-24-02).

Recorded from the live window of 2026-11-18 (evidence kept outside the repository, summarised in `.planning/phases/31-production-stack-boot-rehearsals-for-wave-1-hosts/31-VERIFICATION.md`): the window ran on the production stack (a rootless Podman 5.7.1 account) with 8 of 8 tests passing, the claude validator tier (3) and production tier (1), and the opencode validator tier (3) and production tier (1). The opencode binary was a scratch install outside the repository. A later window the same day ran codex-cli 0.154.0 on the same stack: 5 of 5 passed (validator 2, validator session 2, production 1). Those two windows ran with a warm-up; the cold window is described below and under The window.

- opencode 1.19.5: the production tier passed (`opencode mcp list` reported realm connected), against a warm session in the first window and cold on 2026-11-18 (below).
- claude 2.1.322: connects with the modern MCP revision, with no initialize handshake: it sends `server/discover` and then `tools/list`, and `realm mcp --host claude` answered with all six tools. The production assertion accepts either `initialize` (legacy era) or `server/discover` (modern era) and still requires `tools/list` and the six tool names.

The cold-attach gap (GAP-31-04, GAP-23-02, closed): until Phase 33, `realm mcp --host ID` ensured the daemon and ran `up` before it answered initialize, so a first attach that had to create the sandbox took about 35 to 60 s to its first answer and outlasted the host's MCP connect timeout (OpenCode 30 s; Claude's `mcp list` probe also gave up, leaving `realm status` unbound with no workspace). The warm windows worked around it with an idempotent `realm up --workspace` before the host. Phase 33 made `realm mcp` serve early (`src/cli/stdio-host.ts`): the handshake and `tools/list` are answered at once, every tool call is refused `REALM_NOT_ACTIVE` with `retryable` true until the realm is active, and the same connection forwards calls afterwards. The warm-up is removed from the production tier, and a static test keeps it removed.

Cold result, 2026-11-18, production stack. The direct cold attach probe (`test/integration/cold-attach-live.test.ts`, which starts `realm mcp --host claude` itself, with no recipe and no host binary) passed: `server/discover`, `initialize` and `tools/list` were all answered at 500 ms (bound 10000 ms; an earlier run of the same probe measured 285 ms) while `realm status` was not active; 5 calls were refused `REALM_NOT_ACTIVE` with `retryable` true, the last at 6918 ms; the first call served at 8982 ms after 4 status polls, on the same process; a `list` of the workspace root was done at 8995 ms; the daemon counted 1 attached boot report; the child ended cleanly after its input closed; and `realm down` left no container. The earlier run measured the first success at 8955 ms. Before the change the first answer took 35 to 60 s. The three host health-check tiers then passed cold: claude 2.1.322 (`claude mcp list` returned after 2438 ms; `server/discover` then `tools/list`, six tools), opencode 1.19.5 (`opencode mcp list` after 2155 ms; `initialize`, `notifications/initialized`, `tools/list`, six tools) and codex-cli 0.154.0 (the `codex exec` host command after 896 ms; the same wire as opencode). The hosts leave before the realm is ready; that is correct for a health check, and the proof that the same connection serves calls once the realm is active is the probe, not a host.

The session drive now judges a host that exits on its own from the wire. With that fix the production tier passed against a warm session (5 of 5 tests in that window) and then cold (below), and the registry holds codex as `rehearsed`.

## How a host is booted

- **claude.** The production test installs the real recipe into an isolated Claude configuration directory, puts a wire recorder first on the path as the registered `realm`, and runs `claude mcp list` from a directory under the pinned workspace root, with no warm-up: the host attaches cold, and its own `realm mcp` creates the daemon and the sandbox for the new project directory. `realm mcp` answers the handshake before the bring-up completes, so the health check connects within the bound. The health check performs a real MCP handshake against `realm mcp --host claude` (`initialize` in the legacy era, `server/discover` in the modern era; Claude Code 2.1.322 used the latter); the test requires `connected` for the realm line and no `failed`.
- **codex.** The same install and recorder, then a `codex exec` session in an isolated Codex home against a loopback provider that answers every request with a 503 and records only whether an Authorization header ever arrived. The provider table has no key, auth or bearer field, so no credential exists. The entry is told to forward three extra environment names to the server (`XDG_RUNTIME_DIR`, `XDG_CONFIG_HOME`, `REALM_DRIVER_SOCKET`) on top of Codex's default `HOME`, `LANG` and `PATH`. While Codex runs, the test polls for the boot (the daemon answers active, an attached boot report for the host, the recorder shows the tool listing) and then ends the process group, which applies only to a host that is still alive when the realm is ready. Codex finishes its turn against the refusing provider and exits within seconds, before the realm is ready; its `realm mcp` child goes with it. When the host exits first, the test requires the handshake, `tools/list` and the six tools on the wire, and does not poll `realm status`.
- **opencode.** The production test runs `opencode mcp list` as the health check, like claude, cold. It is gated on an `opencode` executable and passed cold on 2026-11-18 (see above); the wire it showed is `initialize`, `notifications/initialized`, `tools/list` and the six tools.
- **kimi and kimi-code.** No drive exists. `kimi` is archived and cannot run a session. `kimi-code` has no documented command that lists or launches a registered server (`docs/hosts/snippets/kimi.md`).

The wire recorder forwards the host's stdio to the real CLI byte for byte, and logs one line per message: the direction, the kind, the JSON-RPC method name, the request id and, for the response to `tools/list`, the tool names. It never records parameters, results, headers, paths or environment values. For every host the test requires a handshake from the host (`initialize` or `server/discover`, and the failure message names the methods seen), `tools/list` and the six tools (`exec`, `list`, `read`, `retry`, `status`, `write`). The default drive also requires the host command to return below 25000 ms (below OpenCode's 30 s connect timeout) with exit 0, a realm line reporting `connected` and no `failed`.

After the host command, every drive checks the same things: the daemon shows no live session and an empty presence directory, `realm down` succeeds (a refusal that says the daemon is absent or the session never became active is accepted, because the health check may have left before the realm was ready), no sandbox or container remains, `realm host uninstall` removes the entry, and the operator's real host configuration file is byte-identical. The session drive also requires that the provider saw no Authorization header and only loopback peers. The tiers do not assert that the realm became active or that an attached boot report exists after the host has left: that proof is the cold attach probe.

## The window

A production run happens in a human-owned window on the production stack's account, under the shared live lock, one host test at a time. The person who runs it keeps the evidence outside the repository (versions, counts, hashes and results, never paths or environment values), takes a before and an after snapshot of containers, sandboxes, state-directory entries and processes, and compares the real host configuration hashes. A failed step is reported with its catalogue code and the plan that owns the behaviour; it is not retried silently and nothing is patched in the window. No agent runs the production tests. The results are recorded here, in the registry and on the gaps page from that evidence only.

The passing cold window of 2026-11-18 (window 3 of the cold series, on `main` after PRs 166 to 169, account `realmlive`, rootless Podman 5.7.1) ran the cold attach probe and the three production tiers with no warm-up: nothing started the daemon or the sandbox before the host or the probe did, each run used a new project directory, and the stack was clean before and after (0 containers, 0 sandboxes, an empty workspace). 14 of 14 tests passed. The diagnostics recorded per run are the host command elapsed milliseconds (claude 2438, opencode 2155, codex 896, against the 25000 ms bound), the wire summary (handshake method, `tools/list`, the six tool names), the zero residue and the byte-identical real host file; for the probe, the millisecond marks listed above. The earlier cold windows of the same day failed and are recorded as such, not retried silently; between them they showed that the probe's `list` call needed its required `depth` argument (a probe defect, fixed in PR 167), that the host health-check tiers had been given the wrong criterion (they required `realm status` active after the host left, but a health check leaves before the realm is ready, and the child `realm mcp` is then stopped mid bring-up; PR 169 changed the tiers to assert the bounded connect and the six tools). An interrupted run also left the host receipt behind in the shared state directory, which the next run's gate refuses until it is removed; the cleanup is finally-based, so it removes the receipt on any failed assertion but cannot run in a killed process.

## Not shown

- No model turn and no tool call by a real host ran: a session against a refusing provider lists tools and nothing more (GAP-31-02). The cold attach probe calls the tools itself, over its own connection, and that is not a host. A scripted provider that makes Codex call a Realm tool is a deferred idea.
- A cold image pull: every cold run had the digest-pinned image already present, so only the daemon and the sandbox were created cold (GAP-22-02).
- A second version of any host (GAP-31-03, GAP-22-03).
- The wave 2 hosts: they have no production tier by owner decision (GAP-25-07).
- Windows and macOS: Linux only (GAP-23-05).
- The Codex default-environment consequence: Codex forwards only `HOME`, `LANG` and `PATH` to a stdio server unless the entry lists more, and the codex recipe writes no such list, so whether a real Codex user reaches a non-default production stack is inferred (GAP-31-01).
