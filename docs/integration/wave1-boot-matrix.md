# Wave 1 boot matrix

This page is the production-stack boot status of the five wave 1 hosts (`claude`, `codex`, `opencode`, `kimi`, `kimi-code`) and, since Phase 48, of the three hosts whose production tiers were defined by owner decision D-v7-5 (`muse-code`, `prime-agent`, `grok-build`): whether a real host, started through its own CLI, booted Realm against the production stack and listed its tools, with the procedure, the evidence and the limits. The Disposition column is a view of the T3 status in the evidence registry (`test/support/host-registry.ts`), and a test (`test/docs/wave1-boot-matrix.test.ts`) ties each row to it, so a row cannot claim a result the registry does not hold. The per-host summary is the [Host support matrix](host-support-matrix.md), the unverified items and their lift conditions are on [Host plugin gaps](host-plugin-gaps.md), and the contract the recipes follow is [Host plugin contract and installer](host-plugin-contract.md).

A skipped test is `not-run`, never a pass. A cell that names no date and no version has no result behind it.

## How a host is booted

- **claude.** The production test installs the real recipe into an isolated Claude configuration directory, puts a wire recorder first on the path as the registered `realm`, and runs `claude mcp list` from a directory under the pinned workspace root, with no warm-up: the host attaches cold, and its own `realm mcp` creates the daemon and the sandbox for the new project directory. `realm mcp` answers the handshake before the bring-up completes, so the health check connects within the bound. The health check performs a real MCP handshake against `realm mcp --host claude` (`initialize` in the legacy era, `server/discover` in the modern era; Claude Code 2.1.322 used the latter); the test requires `connected` for the realm line and no `failed`.
- **codex.** The same install and recorder, then a `codex exec` session in an isolated Codex home against a loopback provider that answers every request with a 503 and records only whether an Authorization header ever arrived. The provider table has no key, auth or bearer field, so no credential exists. The entry is told to forward three extra environment names to the server (`XDG_RUNTIME_DIR`, `XDG_CONFIG_HOME`, `REALM_DRIVER_SOCKET`) on top of Codex's default `HOME`, `LANG` and `PATH`. While Codex runs, the test polls for the boot (the daemon answers active, an attached boot report for the host, the recorder shows the tool listing) and then ends the process group, which applies only to a host that is still alive when the realm is ready. Codex finishes its turn against the refusing provider and exits within seconds, before the realm is ready; its `realm mcp` child goes with it. When the host exits first, the test requires the handshake, `tools/list` and the six tools on the wire, and does not poll `realm status`.
- **opencode.** The production test runs `opencode mcp list` as the health check, like claude, cold. It is gated on an `opencode` executable and passed cold on 2026-11-18 (see above); the wire it showed is `initialize`, `notifications/initialized`, `tools/list` and the six tools.
- **kimi.** The legacy Python CLI is driven as a command: the production test runs `kimi mcp test realm` from a directory under the pinned workspace root, with no warm-up, and asserts exit 0, a return below the 25000 ms bound and the wire (handshake, `tools/list`, the six tools); it asserts no success wording, because the wording is not known in advance. The legacy CLI forwards only `HOME` and `PATH` to a stdio server and does not expand references in an env value (probe of 2026-11-19), so the wire recorder gives `XDG_RUNTIME_DIR`, `XDG_CONFIG_HOME` and `REALM_DRIVER_SOCKET` back to `realm mcp` for the target only and logs their names, never values (GAP-43-01); the run therefore proves the host side and not the reachability of a non-default stack for a real user. The recorder restores nothing else and the recipe carries no `env` block. Diagnostic switches restore a chosen subset of the three names for an ablation; a run with a subset is a diagnostic variant, never the tier. The validator tier runs `kimi mcp list`, `kimi mcp test` and `kimi mcp remove` against the stub realm, and a session step runs `kimi mcp test realm` against a fake MCP server.
- **kimi-code.** A `kimi -p` session in an isolated Kimi Code home against the same refusing loopback provider as Codex, with one fixed non-secret placeholder key in `KIMI_MODEL_API_KEY` (a throwaway constant, never an operator credential; the provider records only whether a header equals it) and the documented update and telemetry switches. Kimi Code starts its MCP servers before the model request, so the session lists the tools and then retries the refused model request until the drive ends it once the boot is observed. The validator tier of Kimi Code is a session proof, because no validator command exists (`kimi mcp` is an unknown command in 2.6.3): the recorder fronts a fake MCP server and a dead proxy contains the host's network use.
- **muse-code.** The production test runs `muse exec --provider echo --trust-workspace` as a command drive from a new project directory, cold, with a wire recorder that restores `REALM_DRIVER_SOCKET`, `XDG_CONFIG_HOME` and `XDG_RUNTIME_DIR` because Muse does not forward them to a stdio server, and asserts exit 0, the return below the 300000 ms failure bound and the full wire (`initialize`, `notifications/initialized`, `tools/list` and the six tools). The host left before the realm was ready, by design; the run is judged from the wire (Phase 48 open question OQ-48-2). Muse Code 1.4.24 passed cold on 2026-11-19 (5891 ms); the recorded version is 1.4.23 and the different version ran and is recorded (B-48-01).
- **prime-agent.** No boot paragraph: Prime Agent has no credential-free command that starts the registered server (blocker B-48-02, observed 2026-11-19 with Prime Agent 0.10.2). `prime-agent mcp list`, `get`, `add`, `remove`, `status` and `doctor` read or write the file and start nothing, and a start needs a model tool call, so the production test skips with the fixed B-48-02 sentence and the tier stays `config-only` (GAP-48-04).
- **grok-build.** The production test runs `grok mcp doctor` as a health-check drive: the doctor starts `realm mcp --host grok-build` and hands the six tools back over the wire, which is a doctor health-check attach and not a model session and not a tool call through the model loop (GAP-31-02). The scenario sets HOME to its own directory with a per-run leader socket, because Grok documents no relocation variable (48-CONTEXT E-48-10), and the recorder gives the account's HOME to the real `realm mcp` (names logged, never values). Grok Build 1.0.77 sent `tools/list` (Phase 48 open question OQ-48-1), so the wire is the full wire, not handshake only. The window of 2026-11-19 never reached the host command: the install `--dry-run` failed with `config-home-missing` (GAP-48-03).

The wire recorder forwards the host's stdio to the real CLI byte for byte, and logs one line per message: the direction, the kind, the JSON-RPC method name, the request id and, for the response to `tools/list`, the tool names. It never records parameters, results, headers, paths or environment values. For every host the test requires a handshake from the host (`initialize` or `server/discover`, and the failure message names the methods seen), `tools/list` and the six tools (`exec`, `list`, `read`, `retry`, `status`, `write`). The default drive also requires the host command to return below 25000 ms (below OpenCode's 30 s connect timeout) with exit 0, a realm line reporting `connected` and no `failed`.

After the host command, every drive checks the same things: the daemon shows no live session and an empty presence directory, `realm down` succeeds (a refusal that says the daemon is absent or the session never became active is accepted, because the health check may have left before the realm was ready), no sandbox or container remains, `realm host uninstall` removes the entry, and the operator's real host configuration file is byte-identical. The session drive also requires that the provider saw no Authorization header (for Kimi Code, only the one fixed placeholder key) and only loopback peers. The tiers do not assert that the realm became active or that an attached boot report exists after the host has left: that proof is the cold attach probe.

## The window

A production run happens in a human-owned window on the production stack's account, under the shared live lock, one host test at a time. The person who runs it keeps the evidence outside the repository (versions, counts, hashes and results, never paths or environment values), takes a before and an after snapshot of containers, sandboxes, state-directory entries and processes, and compares the real host configuration hashes. A failed step is reported with its catalogue code and the plan that owns the behaviour; it is not retried silently and nothing is patched in the window. No agent runs the production tests. The results are recorded here, in the registry and on the gaps page from that evidence only.

The passing cold window of 2026-11-18 (window 3 of the cold series, on `main` after PRs 166 to 169, account `realmlive`, rootless Podman 5.7.1) ran the cold attach probe and the three production tiers with no warm-up: nothing started the daemon or the sandbox before the host or the probe did, each run used a new project directory, and the stack was clean before and after (0 containers, 0 sandboxes, an empty workspace). 14 of 14 tests passed. The diagnostics recorded per run are the host command elapsed milliseconds (claude 2438, opencode 2155, codex 896, against the 25000 ms bound), the wire summary (handshake method, `tools/list`, the six tool names), the zero residue and the byte-identical real host file; for the probe, the millisecond marks listed above. The earlier cold windows of the same day failed and are recorded as such, not retried silently; between them they showed that the probe's `list` call needed its required `depth` argument (a probe defect, fixed in PR 167), that the host health-check tiers had been given the wrong criterion (they required `realm status` active after the host left, but a health check leaves before the realm is ready, and the child `realm mcp` is then stopped mid bring-up; PR 169 changed the tiers to assert the bounded connect and the six tools). An interrupted run also left the host receipt behind in the shared state directory, which the next run's gate refuses until it is removed; the cleanup is finally-based, so it removes the receipt on any failed assertion but cannot run in a killed process.
