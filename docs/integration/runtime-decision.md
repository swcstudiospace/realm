### Audit: two lines per call (D-90)

A dispatcher call writes two audit lines: an admission line before execution and a result line after. Both use the Phase 2 entry format (D-42) with one additive, optional field, `phase`, valued `admission` or `result`. Outcome alone cannot separate the two lines, because a successful call has outcome `ok` on both. Phase 7 review must read both lines of one call as one call.

The admission and result lines of a call also carry `upId` when the call arrives over an attached session (Phase 17, O-g). It is the correlation id of the `up` that admitted the call, the same id that the `up.end` and `tool.result` log lines carry, so each audit line names the session that admitted it. The field is additive and optional, and a call made with no attached session carries none.

### Audit: reconciliation and sweep lines (Phase 14, CRASH-02)

Phase 14 adds two values to the audit line format. Both are additive, and a log written before this change still parses.

- **`phase: "reconciliation"`** (`AuditPhase`, `src/audit/log.ts`). A reconciliation line has outcome `AUDIT_OUTCOME_UNKNOWN` (see "Catalogue extension (Phase 14)"). It closes an admission line that has no result line.
- **`tool: "temp-sweep"`**, on lines with no `phase`. These are the orphan temp-file sweep lines (next section). With no `phase`, a sweep line keeps the pre-stage shape and is never counted as an admission, a result or a reconciliation.

**Torn-tail rule.** A process killed in the middle of an append can leave a last line with no newline. `writeAuditLine` (`src/audit/log.ts`) checks an existing, non-empty file: if its last byte is not a newline, the next write is a newline followed by the new line, in one write call. The torn line stays in the file as an unparseable line, and the new line is not glued onto it. The rule lives only in `writeAuditLine`, so it covers every writer of the file.

**How reconciliation pairs lines** (`reconcileAuditLogs`, `src/audit/reconcile.ts`).

- It reads each `<stateDir>/audit/<sessionId>.jsonl`. The file stem is the session id and must match the same pattern `appendAudit` enforces; the reconciliation line is appended for that session id.
- Per file it counts, for each key, the admission lines against the result and reconciliation lines. The key is built by the one exported function `pairingKey`: `tool`, `path` (empty when absent) and the JSON of `execSummary` (`null` when absent), separated by NUL. Order is not used, because calls may overlap and their lines interleave.
- For each key with more admissions than closing lines it appends one reconciliation line per missing closing line, through `appendAudit` only. The line copies `tool`, `path` and `execSummary` from the admission and never `bytes` or `sha256`.
- It is idempotent. After the append the counts are equal, so a second run appends nothing (VERIFIED_BY_CODE_READING).
- Ignored lines: a line that is not JSON, not an object, has no string `phase` or `tool`, has a `path` or `execSummary` of the wrong type, or has a `phase` other than the three named. A torn last admission is therefore ignored, which is right: the admission is appended before execution, so nothing ran.
- A missing audit directory is zero work. Every failure is counted in `failed` and has a catalogue code in `failures`, with the base name of its log when it has one. None is fatal: the other logs are still reconciled, and the caller reports the counts. A symlinked, non-directory or unreadable audit directory examines no log; the result has `complete` false, `listingTruncated` true and one PATH_ESCAPE failure with no file. A symlinked log, or a name that is not a safe session id, is PATH_ESCAPE. A non-regular entry is SCHEMA_INVALID, and so is a log over the cap (`RECONCILE_MAX_FILE_BYTES`, 256 MiB; the log has no rotation, so it is read in 1 MiB steps and never held whole). An unreadable log, or an append that throws, is counted with the code its error carries, and PATH_ESCAPE when it carries none. A run-level failure, a clock that throws in the per-log loop or while the logs are ordered, is one AUDIT_WRITE_FAILED entry with no file: the run returns its counts and does not throw, and the logs not yet reconciled are unfinished. A clock that throws inside one log's scan is counted against that log as PATH_ESCAPE; one that throws while the directory is listed gives the unlisted result above (owner item 6). The result is `{ files, appended, failed, unfinished, complete, skippedUnchanged, listingTruncated, failures }`; `files` counts the logs checked completely, scanned or skipped as unchanged, and `skippedUnchanged` how many of them were skipped.
- Listing, ordering and the per-start scan cap. The directory is read entry by entry (never as one array) and every `*.jsonl` name is kept, up to `RECONCILE_MAX_LISTED_ENTRIES` (100 000) entries (names and other entries alike); a further entry, or the deadline, makes the listing truncated (`listingTruncated`, `complete` false, `maintenanceComplete` false). The record, its temp files and any other file are ignored. The listing takes no prefix of the directory, so a stable directory order cannot hide logs from later starts. There is ONE ordering: all listed logs newest modified first, ties by name. A crash leaves unmatched admissions in the logs written last, so the logs that matter are reached first, whether they are recorded or not. A recorded log whose size and mtime are unchanged is skipped after its `lstat`; stats are cheap and bounded by the deadline and the listing bound, so a skip does not count against the cap. `RECONCILE_MAX_FILES` (10 000) caps only the logs whose content is scanned per start, applied in the newest-first order; a log that needs a scan after the cap is spent is reported in `unfinished`. The deadline is checked every 256 entries while listing and before each `lstat` of the ordering pass; logs not stat'ed in time are reported unfinished, in listing order. A log the run refuses (an unsafe name, not a regular file, over a size or key limit) is not counted against the cap, because it is never recorded and would otherwise use the cap on every start. Because the record holds every log one start can list (below), each start records what it finished and the unscanned remainder shrinks until it is empty. If the audit directory holds more than 100 000 entries the remainder cannot be listed and is reported only as `listingTruncated`; an operator should then prune old audit logs. A record that holds fewer logs than exist (injected limits, or names near the 134-character maximum that cut the 16 MiB bound) makes the oldest scanned logs fall out of it; they are then scanned again after every newer log, which costs time only up to the deadline, and logs older still may wait; pruning old logs is the remedy there too.
- Progress record. `<stateDir>/audit/.reconciled.json` maps each completely checked log's base name to `{ size, mtimeMs }`, measured after the reconciler's own appends. A log whose current size and mtime equal its record is skipped without being read, so repeated starts with the same budget make progress through the history instead of re-reading the same old logs from byte zero. The map is kept in memory for the run and written once, with `atomicWriteFile`, when the run ends (complete, out of time, or after an unexpected error) and only if it changed or the stored record needed healing; a kill during a run loses only that run's progress. A log cut off by the deadline records nothing. A log is recorded only when what was scanned is what the stat before the scan described (the descriptor's size and mtime after the last byte equal that stat) and nothing but this run's own appends changed it since; otherwise it is scanned again next run. The writer and the reader share one set of limits: at most `MAX_PROGRESS_ENTRIES` (100 000, the listing bound, so the record can hold every log one start can list) entries and `MAX_PROGRESS_BYTES` (16 MiB, about 85 bytes per entry for ordinary session-id names). The writer drops entries of logs that are no longer listed (only when the listing was complete), then the entries of the oldest modified logs until both limits hold, so a record it wrote is always one the reader accepts. The reader opens the record without following a link, reads through the descriptor at most the size it reported (refusing a record over the byte limit, or one that grew meanwhile), and treats an unreadable, corrupt, oversized, over-entry-limit, non-regular or wrong-shaped record, or an entry of the wrong shape, as empty, never as an error; the run then rewrites it. A record that is a link, not a regular file, or over the byte limit is removed before the write, so the atomic writer never hashes a foreign or huge file (a directory in its place cannot be removed this way and makes the write fail, which is counted once in `failed`). The record is a cache: deleting it only costs one rescan. It is a dot file that does not end in `.jsonl`, so it is not read as a log, and its name is not a temp name, so the orphan sweep never touches it. A log whose content changed while keeping both size and mtime would be missed; the log is append-only, so a change moves both.
- Scan bounds. A log is read in 1 MiB steps. A line over `RECONCILE_MAX_LINE_BYTES` (16 MiB) is skipped, not held, and the lines after it are still counted. A log with more than `RECONCILE_MAX_KEYS` (200 000) distinct (tool, path, exec) keys is refused like an over-sized log, as `SCHEMA_INVALID`, and counted in `failed`. Each reconciliation line is one `appendAudit` (the single writer), which opens, writes and fsyncs the log; that is the one repeated disk cost, and the deadline is checked before each append.
- Why no append races with the scan. The reconciliation runs inside `runStartupMaintenance` before the gate opens. The control socket is bound first, so a second daemon on the same state directory fails with `LOCK_CONFLICT` before it reaches its own maintenance, and every connection waits on the gate, so no tool call reaches the dispatcher and this process appends no audit line while the scan runs (the only audit writer in that window is the temp-file sweep's sink, which runs before the reconciliation, not alongside it).
- Deadline. `ReconcileOptions` takes an optional absolute `deadline` on an injectable `now` clock (default `performance.now()`). It is checked between logs, before every 1 MiB read and every 5000 lines of a scan, and before each append. A log whose scan is cut off gets no line, because a partial count could label a call unknown that has its result line further on. That log and every log not reached are listed by base name in `unfinished`, and `complete` is false. A deadline that expires between two appends of a fully scanned log leaves the rest of that log's lines to the next run, which finds the written lines as closings; the lines of both runs together are those one complete run appends. Without a deadline nothing is bounded.
- Precondition: run it before any dispatcher exists in the process, as the startup reaper does (D-87). A call that is still running would otherwise be labelled unknown.

**What "unknown" covers.** A reconciliation line says only that no closing line exists. A lone admission has two origins. Either the process ended after the admission and before the result, so the call may have run, or the admission append itself threw `AUDIT_WRITE_FAILED`, so nothing ran. The second case can leave the line in the file anyway: a failed fsync after a successful write reports `AUDIT_WRITE_FAILED` although the line is already there (`writeAuditLine` comment). A lone admission from a failed append is labelled unknown too, because the log cannot tell the two apart.

**Status.** `reconcileAuditLogs` and `sweepOrphanTempFiles` are libraries, and the daemon calls both at start, before it serves, inside `runStartupMaintenance` (`src/daemon/startup.ts`; see "Startup maintenance (Phase 14, CRASH-04)" below). A running daemon therefore writes reconciliation lines and sweep lines at each start, as long as there is something to reconcile or to remove.

### Orphan temp-file sweep (Phase 14, CRASH-01)

`atomicWriteFile` writes a temp file beside its target and renames it. A process killed between the two leaves the temp file. `sweepOrphanTempFiles(roots, options)` in `src/fs/temp-sweep.ts` removes such files and only such files. As built:

- **Name.** The file name must match `TEMP_NAME_PATTERN`, `^\.(.+)\.realm-tmp-[0-9a-f]{16}$`, exported from `src/fs/atomic-write.ts`. The writer builds its names with `tempFileName` in the same file, so the writer and the sweep share one definition.
- **Regular files only.** A directory entry must be a regular file (`Dirent.isFile`) and again an `lstat` regular file. A symlink named like a temp file is not removed.
- **Owner.** The file's uid must equal `options.ownerUid`. The caller supplies the uid.
- **Age.** `now - mtimeMs` must be at least `options.minAgeMs`. `ORPHAN_TEMP_MIN_AGE_MS` is 60 000 ms and is what production is meant to pass; the library takes the bound as an option. A user file that is named like a temp file, is owned by the daemon's user and is older than the bound is removed by design.
- **Same device.** A subdirectory is entered only when its device equals the root's device. A root is skipped when its bound device and inode differ from the opened descriptor's.
- **No symlinks.** Each directory is opened with `O_NOFOLLOW|O_DIRECTORY` through the parent descriptor, and later steps act through `/proc/self/fd/<fd>/<name>`, as `atomic-write.ts` does. A symlinked directory is not entered: it is skipped and audited. If that audit line is refused, the sweep counts it in `failed` and adds `AUDIT_WRITE_FAILED` to `errors`, as for any refused exclusion line. A directory swapped for a symlink during the walk cannot redirect the sweep. A root that exists and cannot be pinned (for example without `/proc`) is counted in `failed` with `PATH_ESCAPE`.
- **Audit before unlink.** The injected `audit` callback is called with `{ tool: "temp-sweep", outcome: "ok", path, bytes }` before the unlink. If it throws, the file is kept and that refused line is a failure: it is counted in `failed` and `AUDIT_WRITE_FAILED` is added to `errors`. If the unlink then fails, the failure is counted in `failed` with `CLEANUP_FAILED`, and a second line with that outcome is passed to the callback; if that callback throws too, it is counted in `failed` again and `AUDIT_WRITE_FAILED` is added to `errors`. The entries have no `phase` (see the audit section above).
- **Bounds.** The walk stops with `truncated: true` when it has examined `maxEntries` directory entries (default `DEFAULT_SWEEP_MAX_ENTRIES`, 500 000) or when its wall budget `deadlineMs` (default `DEFAULT_SWEEP_DEADLINE_MS`, 15 000 ms) is spent. A truncated walk skips the remaining roots.
- **Result.** `{ removed, skipped, failed, errors, truncated, unfinishedRoots }`. `errors` holds the catalogue code of each failure, in order, and `failed` is its length. A design exclusion (a symlinked directory, another device, a root whose bound device and inode changed, a root that does not bind, or a subdirectory whose pin check fails) is skipped and audited. Its audit line adds nothing to `errors` when it is written. When it is refused, the exclusion is also counted in `failed` and `AUDIT_WRITE_FAILED` is added to `errors`, as for a refused removal line. Startup counts a root's bind code once, in `failureCodes`, separately from the sweep. The sweep reads no file content, no process state and no environment: the clock, owner, age bound and audit sink are all injected.

The roots are the caller's choice, and the library does not call itself. The daemon passes these roots (`sweepRootsOf`, `src/daemon/startup.ts`): every entry of `policy.workspaceRoots`, then `<stateDir>/sessions`, then `<stateDir>/runtime`, then `<stateDir>/audit`. The audit directory is a root because the reconciliation's progress record is written atomically there, and a kill during that write leaves a `..reconciled.json.realm-tmp-<hex>` temp file that no other root reaches when the state directory is outside the workspace roots. Each root is bound with `bindRoot`; a root that lies inside an earlier root is dropped only when that root's walk reaches it, that is when both are on the same device (`statSync(...).dev` of the two real paths, injectable as the third argument of `sweepRootsOf`), so no directory is walked twice. The walk never crosses a device boundary, so a root on its own mount (for example `/projects/ssd` under `/projects`) is kept. A root whose device cannot be read is kept too, and the stat's code is counted in `failureCodes`. A root that does not exist (for example a `runtime` directory that was never created) is skipped and is not a failure. A root that exists but does not bind is passed on unchanged: `bindRoot` fails with `POLICY_DENIED`, startup counts that code once in `failureCodes`, and the sweep records the root as skipped with an audit line. If that audit line is refused, the sweep also counts it in `failed` with `AUDIT_WRITE_FAILED`, so such a root can report two codes. There is no skip list (VERIFIED_BY_CODE_READING).

### Startup maintenance (Phase 14, CRASH-04)

Decision D-1409 (`.planning/phases/14-crash-safety-pack/14-CONTEXT.md`). `startDaemon` runs one function, `runStartupMaintenance` (`src/daemon/startup.ts`), after the control socket is bound and before the gate opens, so no request is served before it finishes. Order:

1. **The reap** (`reapStartup`, `src/session/reap.ts`): every realm container is removed and proven gone, then every session record is deleted.
2. **The orphan temp-file sweep** (`sweepOrphanTempFiles`, `src/fs/temp-sweep.ts`) over `policy.workspaceRoots`, `<stateDir>/sessions`, `<stateDir>/runtime` and `<stateDir>/audit`. The daemon passes `now`, `ORPHAN_TEMP_MIN_AGE_MS` (60 000 ms), its own uid (`process.getuid()`) and an audit sink that appends each sweep line to `<stateDir>/audit/<sessionId>.jsonl` through `appendAudit`, under the daemon's own session id.
3. **The audit reconciliation** (`reconcileAuditLogs`, `src/audit/reconcile.ts`) over `<stateDir>/audit`, under the same deadline as step 2.
4. **The report**: the `StartupReport` is built, the notice is derived from it, and the `onStartup` observer receives it.
5. **The gate opens** (`openGate()`).

**Budget.** Steps 2 and 3 are optional cleanup, so they share one deadline, `STARTUP_MAINTENANCE_BUDGET_MS` (10 000 ms, `src/daemon/startup.ts`), computed when the reap has ended; the budget and a monotonic clock are injectable (`StartDaemonOptions.startupMaintenanceBudgetMs` and `monotonicNow`). The sweep may spend at most half of what remains, and never more than its own 15 s budget, so a very large workspace cannot starve the reconciliation start after start; the reconciliation gets what is left. Work the deadline cuts off is not lost: the sweep reports the root it was walking and every root it did not reach (`unfinishedRoots`), the reconciliation reports its unfinished logs, and a later start does the work. The reconciliation takes all logs newest modified first and skips those its progress record shows as unchanged since they were last checked completely, so repeated small budgets reach the whole history instead of re-reading the same old logs; the record is a cache whose deletion only costs one rescan. The gate therefore opens at most the budget plus one chunk of work (one directory read batch, 1 MiB of log, or one audit append) after the reap ends. The reap itself keeps its own 60 s bound and is not part of this budget. Unfinished maintenance does not change the notice, which is about a destroyed sandbox only.

**Failure handling.** Only the reap can stop the start: a reap that does not prove zero containers rejects (and a timeout of 60 s, `REAP_SWEEP_TIMEOUT_MS`, rejects with `PODMAN_MACHINE_DOWN`), and `startDaemon` aborts, because nothing may be served while an old sandbox might survive. A failure in step 2 or 3 never aborts the start. When the reap fails after it had already removed containers or deleted records, the daemon still builds a partial report from what was collected (the ids through `onRemoved`, the record deletions it counted, `reapFailure` set to the failing code, `failures` 1, `maintenanceComplete` false), hands it to `onStartup` so `daemon.log` has it, and then rethrows the original error; no sweep or reconciliation runs. Each is counted in `failures` and the start goes on. `failures` is the length of `failureCodes` plus the failures that carry no code: 1 when the process has no uid (`process.getuid` is unavailable), in which case nothing is swept because the owner rule cannot be applied, and one for each adopted session whose hydration did not come back active. The coded part is a registry cleanup that threw, a sweep root that did not bind or whose device could not be read, every error the sweep reports, a sweep or a reconciliation that threw, and every failure the reconciliation reports. Entries the sweep counted as `skipped`, and work the budget left unfinished, are not in `failures`; they are reported through `unfinishedSweepRoots`, `unfinishedAuditFiles` and `maintenanceComplete`. The reason for the rule: a skipped cleanup costs disk space and a missing reconciliation line, while a daemon that will not start costs the user the sandbox (VERIFIED_BY_CODE_READING of the comment on `runStartupMaintenance`). An `onStartup` observer that throws does abort the start.

Request and lifecycle records go to `<stateDir>/requests.log`, which the file sink rotates at 4 MiB to one `requests.log.1`. They do not share `daemon.log`: a detached daemon inherits that file as stderr, and rotating it would leave a later `daemon.failed` line on an unlinked inode. If `requests.log` cannot be opened, each line falls back to stderr. The owner ratified this layout on 2026-11-02 in the amended form of D-1704 (`.planning/phases/17-observability-and-tamper-evident-audit/17-CONTEXT.md`): request and lifecycle lines go to `requests.log`, and `daemon.log` remains the startup and failure sink.

Every line starts with `ts`, `level` and `event`, then `code` when present. `REALM_LOG_LEVEL` sets the threshold (`debug`, `info`, `warn` or `error`; default `info`), and the entry reads it once, in `src/daemon/main.ts`. Lines lost to a failing sink are counted in the metrics snapshot. The records in `requests.log`:

- `daemon.starting` (info), `daemon.listening` (info), `daemon.stopping` (info) and `daemon.stopped` (info): the daemon's lifecycle. `daemon.stopped` carries `code` when a session teardown failed; it is the first failure code. The number of failed teardowns is not reported (owner ruling 5).
- `lifecycle.transition` (info): a state change, with `from` and `to`, the catalogue `code` when the reason carries one, and `upId` when one is known.
- `up.begin` (info) and `up.end` (info): with `correlationId` and `upId`; `up.end` carries `durationMs`, and `code` when the attach failed.
- `tool.result` (info): one per tool call, with `correlationId`, `upId` when known, `tool`, `outcome` (`done`, `refused` or `error`) and `durationMs`; `code` for a refused or failed call.
- `health.probe_failed` (warn): a failed health probe, with `code` or, when the state carries no catalogue code, `reason`; and `upId` when known.
- `anda.listener_failed` (warn): a bridge listener threw or rejected while an event was delivered, with `kind` (the event kind) and `code` when the listener threw a catalogue error. The other listeners still receive the event.
- `control.request` (debug): one per control request, with `method`. It is written only at level `debug`.
- `control.refused` (warn): a control request refused, with `method` and `code`.
- `daemon.log-level` (warn): `REALM_LOG_LEVEL` held an unrecognised value, so the level is `info`.

Counters and timings are read with `realm metrics`, which sends `metrics` on the control socket. There is no network listener and no MCP or ACP tool for them. The counts reset when the daemon starts.

**The daemon log records.** The daemon entry (`src/daemon/main.ts`) writes these records through its own logger to its standard error. A detached daemon's standard error is `<stateDir>/daemon.log` (`startDetachedDaemon`, `src/cli/main.ts`); a foreground entry writes them to the terminal. The records are written by `emitStartup`, `emitAuditHead` and `emitFailure`, and by the unreadable-audit check that writes `audit.unreadable` (below):

- `daemon.startup` (info, `emitStartup`): once per start. The object has `level` `info` and `event` `daemon.startup`, then the report fields in the table above except `truncated`, `failureCodes` and `unattributedRecordCodes`, which the line does not carry. `unfinishedAuditFiles` and `unfinishedSweepRoots` are a sample of at most ten names; `unfinishedAuditFileCount` and `unfinishedSweepRootCount` are the full counts. `code` and `reapFailure` are present only when the reap failed, and both hold the reap's code. No line count is recorded: the former `line` field is removed. The read is bounded to two 4 MiB windows, so its cost does not grow with the file size. It covers only the file of session id `daemon`, the session the entry passes to `startDaemon`.
- `audit.unreadable` (warn, reason `unreadable`): an audit file that exists but cannot be read. It is logged to `<stateDir>/daemon.log` through the entry writer, at startup and at shutdown. ### Lost-container retry in `create` (Phase 14, TD-04)

`LifecycleController.create` (`src/lifecycle/controller.ts`) now recovers a recorded container that no longer starts. The rule as built:

- It applies only when the session record already names a container and no create ran in this call, so the container being started is the recorded one.
- It applies only when the start fails with `OPENSHELL_START_FAILED`. A port failure that is not a `RealmError` is mapped to that code (`portFailureCode`), so it qualifies too. Any other code, such as `AGENTOS_CRASH_LOOP`, goes to the usual failure path and the container is kept; a dead runner in a live container is recovered in place by `/realm-retry` (`docs/integration/omp.md`, "Runner killed in the sandbox").
- Recovery runs once per `create` call. `recoverStaleContainer` destroys the recorded container within the remaining startup budget, writes the record with no container id (before the new create, RT-07), creates a new container and starts it. If that second start fails, the failure takes the usual path and the new id stays recorded.
- If the destroy fails, it throws its own code and the old container id stays recorded. A stop that took the session over during recovery makes `create` return the snapshot the stop left.

**Known limit.** The trigger is the code alone (VERIFIED_BY_CODE_READING). The port gives no distinction between a container that is gone and one that is stopped but still present, so a stopped-but-present container is destroyed and recreated as well, and what the old container held is dropped with it.

When the gateway answers, the supervisor asks `driverAnswers()`, which connects to the compute driver's socket under a 5 s bound (`DRIVER_PROBE_TIMEOUT_MS`, `src/runtime/agentos-driver.ts`). The socket path is `REALM_DRIVER_SOCKET`, which the daemon reads from its environment (`src/daemon/main.ts`) and passes only when it is set. `driverAnswers()` answers true only when an absolute socket path accepts the connection, and false when that path is absent, refused, not a socket or timed out; when no absolute socket path is configured it answers null, the driver is not probed, and it is not claimed down. The driver is probed only when `REALM_DRIVER_SOCKET` is set to an absolute path: an unset or relative socket is not evidence that the driver is lost (`driverAnswers()` is null).

## Closure decisions (2026-10-22)

These decisions were recorded by the user on 2026-10-22. Each is checked against the source named in its line. Nothing in this section is a live host run.

- **Session owner.** The daemon owns sessions: the sandbox, the policy, and the session. Hosts attach to the daemon and do not own the sandbox (`src/omp/extension.ts`, `src/omp/plugin.ts`).
- **Attach.** A surface attaches by connecting to the control socket and calling `up`. `up` is idempotent (`src/daemon/client.ts`). There is no attach or detach protocol.
- **Lifetime.** The sandbox persists until `realm down`. A host shutdown closes that host's client and never sends `down` (`endSession`, `src/omp/plugin.ts`).
- **Grace-period detach.** The grace-period detach is deferred. It is recorded as a deviation from the spec.
- **Tool method.** The `tool` method carries `{ tool }`. Its reply is the tool outcome (`done` or `refused`) or a catalogue code (`src/daemon/client.ts`, `call` and `isToolOutcome`; `src/daemon/daemon.ts`, case `tool`). TD-01 (Phase 14): a refusal's error reply now also carries `causeCode` when the dispatcher's refused outcome has one. The refused `ToolOutcome` variant gained an optional `causeCode` (`src/tools/dispatch.ts`, `refused`), and the `tool` case copies it into `{ code, causeCode }` (`src/daemon/daemon.ts`). Without a cause the reply is `{ code }` as before. The shapes seen over the daemon and in process are not unified: in process a caller gets the refused outcome (`outcome`, `tool`, `code`, `retryable`, optional `causeCode`), and over the daemon it gets an error reply of `code` and optional `causeCode` only, which `DaemonClient` rethrows as a `RealmError`. Unifying them is a recorded candidate owner decision and is not made here.
- **Control line cap.** A control line is capped at 1 MiB (`MAX_CONTROL_LINE_BYTES`, `src/daemon/channel.ts`). An oversized request is refused unread with a null-id `SCHEMA_INVALID` reply, and the connection then closes (`oversizedLineReply`, `src/daemon/channel.ts`; `src/daemon/daemon.ts`).
- **Policy mode in replies.** `status` and `up` replies carry the policy mode, `advisory` or `fail-closed` (`DaemonStatus.mode`, `src/daemon/client.ts`). A policy with no `mode` reports `fail-closed`; `advisory` appears only when the policy file sets it.
- **Directory modes.** On a fresh start the state directory and the run directory are created at 0700. An existing run directory must be exactly 0700 and owned by the current user, or the call is `SCHEMA_INVALID` (`ensureSocketDir`, `src/daemon/channel.ts`).
- **Omp guard with unknown mode.** When the status read fails and no mode has been reported yet, the Omp guard blocks the host write. With a known explicit advisory mode, the write proceeds with a warning; with `fail-closed`, the default, it is blocked (`src/omp/plugin.ts`, the fallback in `stateVerdict` and the status-failure path).


## Closure follow-ups (2026-10-22)

**Startup output.** A detached daemon's stdout and stderr go to `<stateDir>/daemon.log`. `startDetachedDaemon` and the CLI's `withDaemonLog` (`src/cli/main.ts`) open that file in append mode at mode 0600, set it to 0600 with `fchmodSync`, and close the parent's descriptor after the spawn returns. The stderr hint `realm: the daemon's startup output is in <path>` comes from `daemonLogHint`. `up` adds it when its ensure step throws or when its `up` request throws, which covers a transport failure. An `up` reply that carries an error or a non-active state does not add it; that refusal is written as `CODE: reason` alone. `mcp` and `acp` add it through `attachFailure` when their ensure step throws or when their `up` call throws, and a daemon error reply reaches that catch as a throw. `acp` does not add it when its `up` returns a state other than active or degraded; that refusal is written as `CODE: reason` alone. The log is never printed.

**Reply cap.** Replies from the daemon are capped at `MAX_CONTROL_LINE_BYTES` (1 MiB), as requests are. `readBounded` in `src/daemon/channel.ts` counts the bytes before the reply's newline. Past the cap it destroys the socket and rejects with `SCHEMA_INVALID`, and `sendRequest` passes that error through, so the client's `request` in `src/daemon/client.ts` rejects with `SCHEMA_INVALID`. The reply is never buffered past the cap.

**Ensure timeout.** `ensureDaemon` (`src/daemon/ensure.ts`) asks a probe what the control socket holds: a daemon that answers, a daemon that holds the socket but has not answered yet (a reply cut short while it binds, or a timeout while it is busy with its startup reap), or nothing. It spawns at most once, and only when the socket is absent: a second daemon spawned over one that holds the socket would only refuse with `LOCK_CONFLICT` (found by the Greptile review of the pull request that shared this probe between the CLI and the Omp extension). A held socket is waited for, for the whole bound. It then polls until a daemon answers or its bound elapses. When the bound elapses it throws `DAEMON_START_TIMEOUT`. That code is retryable (`src/core/errors.ts`). Its reason reads: "The daemon did not answer on its control socket within the daemon start timeout after it was spawned."

**Control request limits.** `CONTROL_TIMEOUT_MS` (`src/daemon/channel.ts`) bounds each request per method: `status` 5 s, `down` 45 s, `doctor` 60 s, `tool` the dispatcher's 30 s plus a 10 s reply margin, and `up` 230 s, which is the default startup budget of 200 s plus a 30 s margin. The caller reports `TOOL_TIMEOUT` when its limit passes. No CLI or plugin caller reads the daemon-owned policy, so a policy that sets `startupBudgetMs` above 200 s can still exceed the `up` limit; the plugin's own 200 s startup timer is unchanged and fires first.

**Directory modes.** `withDaemonLog` (`src/cli/main.ts`) creates the missing ancestors of the state directory with no mode argument, so they take the default mode, which the umask narrows. It then creates only the state directory, with `mkdirSync(stateDir, { recursive: true, mode: 0o700 })`. `ensureSocketDir` (`src/daemon/channel.ts`) applies the same rule on the daemon side: missing ancestors of the state directory are created at `DEFAULT_DIR_MODE` (0777), which the umask narrows, and only the state directory and its run directory are created at `RUN_DIR_MODE` (0700).

## Per-project sessions (Phase 18, MULTI-01)

Status: recorded 2026-10-30, before the code that needs it. Source: owner decision D5 item (i) (2026-10-29, `.planning/MILESTONE-CONTEXT.md`) and requirements MULTI-01 to MULTI-06 (`.planning/REQUIREMENTS.md`). Not live-verified.

**Decision.** The daemon holds one session per project workspace. A project workspace is a directory that is a descendant of a configured root. This supersedes "one session per daemon". The code still has the superseded form: `src/daemon/main.ts` sets `SESSION_ID = "daemon"`, so every `up` on the host shares one record, one sandbox and one audit file.

**Reasons.**

- The driver pins one workspace root in `config.json` (`workspaceRoot`, see "Driver roots (Phase 15, ONB-03)"). One daemon therefore cannot give two projects separate `/workspace` contents.
- Owner decision D5 item (i) approves the change. Proposal 3 of `.planning/quick/261029-g7m-lifecycle-and-persistence-findings/IMPROVEMENT-PROPOSALS.md` asks for a recorded decision that supersedes one session per daemon.

**Consequences.**

- **Session id.** The session id is derived from the pinned project workspace. It is a deterministic function of the workspace's canonical path, fixed when the session is created, and it must match the session-id pattern that the store and `appendAudit` already enforce. The fixed id `"daemon"` is removed, and no alias is kept.
- **Sandbox.** One sandbox per workspace, named `realm-<sessionId>`.
- **Per-session state.** Each session owns its record, its pinned subdirectory under the workspace root, its audit file `<stateDir>/audit/<sessionId>.jsonl`, its lock table and its status snapshot. No file is shared between sessions.
- **Lifecycle.** `realm down` for one session removes that session's sandbox and leaves the other sessions active.
- **Maintenance.** The startup reconciliation already reads every `<stateDir>/audit/<sessionId>.jsonl`, so it needs no change for several logs. The startup reap is per session (RES-01 below).
- **Resource bound.** The aggregate memory and CPU of concurrent sessions is bounded and documented with existing configuration and no new catalogue code (MULTI-06).

**What does not change.**

- **One container per session.** A session is one container, and no two sessions share one. V2-02 (one container per workspace, with cross-session lock leases and refcounted reaping) stays deferred.
- **The daemon owns sessions.** Hosts attach by calling `up` on the control socket and do not own the sandbox ("Closure decisions (2026-10-22)").
- **Lifetime.** A sandbox lasts until `realm down` for its session. A host shutdown still never sends `down`.
- **Single owner.** One host daemon owns the state directory (D-87, OQ-P4-06).
- **Driver scope.** This decision does not amend PRD-DRV-01. MULTI-04 handles it only as far as Phase 18 needs.
- **Catalogue.** No error code is added.

**Reversibility.** Costly. Session ids, sandbox names, paths and audit file names all depend on it.

## Per-project session contract (Phase 18, MULTI-01 to MULTI-06, 2026-11-02)

**C1 identity. Engineering ruling, ratified by owner 2026-11-02, within the accepted D5(i).** The session id of a project is `p` followed by the first twelve lowercase hexadecimal characters of the SHA-256 of the canonical project path (the realpath, UTF-8 encoded, no trailing separator). The id is thirteen characters and matches the session-id pattern that `isSessionId` applies. The sandbox name is `realm-p<12 hex>`, nineteen characters, which is the value of `GATEWAY_SANDBOX_NAME_MAX_LENGTH`. The function is `sessionIdOfWorkspace` in `src/session/paths.ts` (plan 02). Collision rule: when a persisted record for the id names a different canonical path (`SessionRecord.workspaceRoot`), or a registry entry for the id (C3) names one, the request is refused with `SANDBOX_NAME_IN_USE` before any runtime I/O. Reason: D5(i) fixes the id as a function of the canonical path; the choice of hash, prefix and twelve hexadecimal characters is the engineering step that keeps the sandbox name within the gateway limit. A 48-bit id is not collision-free in principle, so the refusal, not the hash, is the guarantee; the birthday bound for a thousand projects is about 1.8e-9. (evidence: src/session/paths.ts, `isSessionId`; src/runtime/openshell.ts, `GATEWAY_SANDBOX_NAME_MAX_LENGTH`; src/contract/validate.ts, `SessionRecord`)

**C2 containment. Engineering ruling, ratified by owner 2026-11-02: the explicit reading of MULTI-02.** Containment equality: a canonical path equal to a configured root counts as inside that root. Eligibility of a requested path is `bindWorkspaceUnderPolicy(policy.workspaceRoots, requested)` (existing) and, in addition, the canonical path equals or lies below the canonical `workspaceRoot` of `config.json`. Equality is allowed for both checks. The containment rule of MULTI-02 is read as "inside or equal to a configured root", which is what the existing helper does. Reason: `isInsideRoot` already admits equality, and `init` writes the project directory as the one policy root, so refusing equality would break the single-project layout that `init` writes. The owner-facing wording, "a descendant of a configured root" (`.planning/REQUIREMENTS.md`, MULTI-02; `.planning/MILESTONE-CONTEXT.md`, D5(i)), is unchanged; this section is where the reading is stated. A path failing either check is `POLICY_DENIED` before any container, record, registry or driver call. For every later use of a selected project, the daemon runs `verifyPinnedAt` on the pinned identity and requires the id to equal `sessionIdOfWorkspace` of the pinned realpath. A renamed or swapped directory is `POLICY_DENIED`. `verifyPinnedAt` is not weakened. (evidence: src/fs/root.ts, `bindWorkspaceUnderPolicy`, `verifyPinnedAt`, `isInsideRoot`; src/cli/init.ts, the written `workspaceRoots`)

**C3 mount authority. Engineering decision.** Each admitted project gets a registry entry `<stateDir>/workspaces/<sessionId>.json` (directory mode 0700, file mode 0600, written atomically) holding `{ "schema": 1, "sessionId", "workspaceRoot", "dev", "ino" }`. The daemon writes it before the driver create, and removes it when the session is released (C5) or at startup (C9). The driver resolves the sandbox name `realm-<id>` to the registry entry and checks, in order: the sandbox name carries the `realm-` prefix and its remainder passes `isSessionId`; the id recomputed from `workspaceRoot` equals `sessionId`; `workspaceRoot` equals or lies below the driver's own `config.workspaceRoot` (equality is inside, as in C2); `verifyPinnedAt` of the stored device and inode at that path passes. Any failure is a driver refusal with check name `create.workspace` and code `SCHEMA_INVALID`, the driver's default refusal code (src/runtime/driver/refusal.ts), with no container, no state directory and no secret entry. The driver mounts the resolved path at `/workspace`. The session verifier compares the inspected mount with the binding of the request, which the controller has verified against the session pin, so a driver that resolved a different directory fails the create closed. The session-side refusal of a request whose `workspaceRoot` differs from the pinned root (`requireSameDirectory` in `src/runtime/session-execution.ts`) is removed for that reason. The same resolution runs in `ValidateSandboxCreate`, because the two RPCs share `planCreate` (`src/runtime/driver/compute-driver.ts`). That is intended: validation refuses what create would refuse and writes nothing. Reason for the carrier: the gateway sandbox identity (`DriverSandbox.name`, which the driver already consumes) is the one identity the driver receives; the pinned create argv has no workspace selector, and the gateway normalizes an empty `ObjectMeta.workspace` to `default`. If a read-only capture of the pinned CLI create help, taken at execution time, shows a workspace selector, this choice is revisited before plan 04 starts, not after. The registry is a daemon-written, account-owned file, the same trust base as `config.json`; the driver's recomputation and containment checks make a wrong entry fail closed, and they do not trust the daemon's canonicalization blindly. (evidence: src/runtime/driver/proto/compute_driver.proto, `DriverSandbox.name`; src/runtime/driver/proto/datamodel.proto, `ObjectMeta.workspace`; src/runtime/session-execution.ts, `requireSameDirectory`; src/runtime/driver/compute-driver.ts, `planCreate`)

**C4 selection. Engineering decision.** Every stateless control request that addresses a project carries `selection`: `{ "workspaceRoot": <string>, "sessionId": <string> }`. `up` carries `workspaceRoot` only; the daemon derives the id and returns it on the reply. `status`, `tool`, `down` and `metrics` carry both fields. `doctor` carries an optional selection; without one it reports the agent-OS reading as unbound. A missing, malformed or self-inconsistent selection (the `sessionId` differs from the id derived from `workspaceRoot`) is `SCHEMA_INVALID`. A selection whose `workspaceRoot` lies outside every policy root, or outside the configured workspace root, is `POLICY_DENIED` for each of the four methods `status`, `down`, `tool` and `metrics` before any runtime I/O. This check runs before the no-live-session answer, so an outside directory never receives the unbound snapshot; `realm status`, `realm metrics`, `realm down` and the `tool` call run outside every project therefore report `POLICY_DENIED` (plan 12 records it). For `status` and `down`, a valid selection inside the roots with no live session answers the unbound snapshot, which keeps the idempotent `down` of CORE-06; `tool` with no live session is `REALM_NOT_ACTIVE`. The daemon never infers a session from the socket's lifetime, from the last `up`, or from a global implicit session. The client holds its selection; `close()` detaches the client's transport and removes no session. Reason: MULTI-03 requires each control request to name its project, because the control socket carries no session state. (evidence: src/daemon/channel.ts, `CONTROL_METHODS`; src/daemon/client.ts, `connectDaemon`)

**C5 lifecycle. Engineering decision.** A session `down` is `controller.destroy()` on that session's handle: it stops and removes its container, releases its locks, and deletes its record. Then the daemon deletes its registry entry and releases its admission slot. Each step runs only after the previous one succeeded. If the destroy fails, the session stays registered and its slot stays committed. A `down` that leaves no live session arms the daemon stop, including a `down` whose selection names a project with no live session, which replies with the unbound snapshot. A `down` of one project while another session is live never stops the daemon. The wait for the session lock that a `down` takes is bounded as C11 states. This keeps HEAD's effect: HEAD's `down` always closed the server, so a daemon that holds no session would otherwise keep the control socket after its last session ended. The reply for an unbound project is unchanged, so the idempotent `down` of CORE-06 keeps its answer; only the daemon's exit follows it. A daemon signal (SIGTERM or SIGINT) runs the in-process stop of every handle with `controller.stop()`, which keeps records and registry entries for the next start's reap, as today. Signal shutdown sends no control message and is never the session `down`. A host shutdown never sends `down`. This record changes HEAD's reading of `down` (every `down` closed the daemon), and plan 12 lists that change. (evidence: src/lifecycle/controller.ts, `LifecycleController.destroy` and `stop`; src/daemon/daemon.ts, `stop` and `shutdown` at HEAD)

**C6 per-session state. Owner ruling, 2026-11-02 (an owner ruling in this record; C1, C2 and C7 are owner-ratified or owner-set).** Each session owns its record, its pinned project directory, its sandbox, its bind mount, its audit file `<stateDir>/audit/<sessionId>.jsonl`, its lock table (created by `createRealmHandle`), its controller, its dispatcher and its status snapshot. Metrics stay daemon-wide, because the counters are not listed in MULTI-03. Log lines for session events carry `sessionId` and never a path. `audit.head` is emitted per session when its handle is created and when it is destroyed; it is not emitted at daemon start or on signal shutdown. This amends Phase 17 ruling O-d by owner choice on 2026-11-02 (`audit.head` covers the daemon's own session file), because the daemon no longer owns one; the amendment is a consequence of this contract and is listed in plan 12's verification. (evidence: src/realm/compose.ts, `createRealmHandle`; src/audit/chain.ts, `readAuditHead`)

**C7 aggregate bound. Set by owner 2026-11-02 (4 GiB, 4e9 nanoCpus, 2 sessions).** Two constants are added to `HARDENING_PROFILE` in `src/runtime/hardening.ts`: `aggregateMemoryBytes = 4 * 1024 ** 3` (4 GiB) and `aggregateNanoCpus = 4_000_000_000` (4e9 nanoCpus). They bound the sum over all concurrent sessions. They are derived from the existing per-container caps already in `HARDENING_PROFILE`: `memoryBytes = 1024 * 1024 * 1024` (1 GiB) and `nanoCpus = 2_000_000_000` (2e9). The session count is computed, not stored: `maxSessions = min(floor(aggregateMemoryBytes / memoryBytes), floor(aggregateNanoCpus / nanoCpus))` = min(floor(4 GiB / 1 GiB), floor(4e9 / 2e9)) = min(4, 2) = 2. Reason for the choice: the only existing numeric resource limits live in `HARDENING_PROFILE`; the bound needs one number that no existing setting holds; a config key or a policy key would be a schema change and a new catalogue entry would be a second one, and neither is needed. These are the only new resource numbers; the down lock wait of C11 is a timing budget, not a resource bound. They are an engineering choice, not a user setting. Plan 03 records the host's observed memory and CPU count (read-only) beside them as an executor step; this section does not assert that observation. If the host cannot hold two sessions at these bounds, plan 03 reports BLOCKED; only the owner can change these values. Admission is a synchronous reservation in the daemon, performed before the probe's first `await` in `up`: the committed set is the union, by session id, of the persisted record ids, the in-flight reservations and the ids whose removal is not yet proven. A reservation that would make the set exceed `maxSessions` is refused with `POLICY_DENIED`. Reason for that code: it exists, and the bound is a realm policy; it is not retryable, a trade-off recorded here. A reservation is released only after proven removal, or when no container was created for the id. The driver does not count sessions; the daemon is the single owner of the count, so there are no competing counters. Effect on provisioning evidence: the two fields change `HARDENING_PROFILE`, and `hardeningEvidenceDigest` hashes the whole profile, so every sandbox created after the change carries a different evidence digest. That is intended: the digest names the profile the verifier checked, and the profile now carries the aggregate budget. No stored digest is compared (the digest is sent to the sandbox runtime as provisioning evidence), so no existing sandbox is affected. (evidence: src/runtime/hardening.ts, `HARDENING_PROFILE` and `hardeningEvidenceDigest`; src/runtime/openshell.ts, `GATEWAY_SANDBOX_NAME_MAX_LENGTH`; src/runtime/session-execution.ts, `SANDBOX_CPUS` and `SANDBOX_MEMORY`; src/runtime/driver/runtime-channel.ts, `evidenceDigest`)

**C8 legacy. Engineering decision.** The fixed id `daemon` is retired with no alias. The startup reap removes `sessions/daemon.json` as it removes every record, so no record conversion is needed. `audit/daemon.jsonl` is kept as history: verification and reconciliation still read it, and no new line is written under the id `daemon`. The session-record schema, the audit line format and the error catalogue are unchanged. Reason: the reap already removes every record at start, so a conversion would have nothing to convert, and a retained alias would be a second identity. (evidence: src/daemon/main.ts, `SESSION_ID`; src/session/reap.ts)

**C9 startup maintenance attribution. Engineering decision.** Before the reap deletes records, the daemon captures the recorded canonical workspace of each session. An orphan temp-file sweep line is written to the audit file of the session whose recorded workspace contains the removed path. A removed path that no captured workspace contains is counted in the startup report and logged as an entry-log count; it is written to no session audit, so no daemon session is fabricated. Reason: records are deleted before the sweep runs, so the owner of a removed path can be known only from a capture taken before the reap. Registry entries left by a previous generation are removed at startup and counted (plan 09). Sequence is unchanged: reap, then temp-file sweep, then audit reconciliation, then serve. Phase 19 changes the reap and adds adoption; that change builds on C9. (evidence: src/daemon/daemon.ts, `runStartupMaintenance`; src/fs/temp-sweep.ts, `sweepOrphanTempFiles`)

**C10 driver reservations. Engineering decision.** The driver's process-global `rootReserved` exclusion and its single-pinned-root liveness check are replaced by two per-sandbox rules. First, an in-flight reservation, held from before the first await to the end of the create, is keyed by the sandbox name: a create whose name is already reserved is refused with the driver check `create.pinned_root_held`, which maps to the catalogue code `REALM_INVALID_TRANSITION` as the driver already maps it. Second, a liveness check refuses a create when a live container of this driver already binds the resolved workspace (same device and inode), where the resolved workspace is the one the registry entry of the name names, not `config.workspaceRoot`; it is refused with the same check and code. One live container per workspace, not one per driver. Reason for the pair: a create in flight has no container yet, so the name key covers the window before the container exists. Under C1 a directory has one sandbox name, and under C3 the registry check refuses a second name whose entry names a directory it does not derive, so no second name can reach one workspace through a valid entry. A reservation keyed by the workspace as well as by the name was considered and rejected for that reason: no valid input could reach it, so it would be dead state. The rules do not replace the daemon's count (C7). (evidence: src/runtime/driver/compute-driver.ts, `rootReserved`, `pinnedRootHeld` and `holdsPinnedRoot`)

**C11 down lock wait budget. Engineering decision.** The daemon-side wait for a session lock during `down` is bounded by `DOWN_LOCK_WAIT_MS = 10_000` (10 s), a named constant defined beside `withSessionLock` in `src/daemon/sessions.ts`. It is strictly shorter than the client bound for `down`, `CONTROL_TIMEOUT_MS.down = 45_000` (45 s, `src/daemon/channel.ts`), which the CLI applies through `controlTimeoutOf` (`src/cli/main.ts`) and the client applies in `connectDaemon` (`src/daemon/client.ts`). Derivation: 45 000 ms = 10 000 ms (lock wait) + 30 000 ms (`TEARDOWN_TIMEOUT_MS`, the bound of the down's own destroy, `src/lifecycle/bounds.ts`) + 5 000 ms (margin for the reply). A `down` whose lock wait would exceed `DOWN_LOCK_WAIT_MS` abandons the wait, applies nothing, and replies `TOOL_TIMEOUT`, which is retryable; C12 defines the abandonment. Reason: a daemon-side wait equal to the client bound lets the daemon still be waiting, or still applying a destroy, after the CLI has reported a timeout. (evidence: src/daemon/channel.ts, `CONTROL_TIMEOUT_MS`; src/daemon/client.ts, `connectDaemon`; src/cli/main.ts, `controlTimeoutOf`; src/lifecycle/bounds.ts, `TEARDOWN_TIMEOUT_MS`)

**C12 cancelable session lock waiter. Engineering decision.** `withSessionLock<T>(sessionId, fn)` (`src/daemon/sessions.ts`) is an in-process FIFO lock keyed by session id. A waiter queues behind the current holder and holds no lock until it is granted. A `down` waiter carries a cancel deadline of `DOWN_LOCK_WAIT_MS` (C11); an `up` waiter carries none, and its wait is bounded by the holders' own bounds. When a waiter's deadline expires before it is granted, the waiter is removed from the queue, its `fn` is never called, nothing is applied, and the rejection is `TOOL_TIMEOUT`. The lock then passes to the next waiter in FIFO order, so an abandoned waiter never blocks a later one. A granted waiter runs `fn` to completion; a grant is not cancelled. The lock is released in a `finally`, so a throwing `fn` releases it too. Status, tool and metrics take no lock. Reason: a waiter that keeps its place after its caller has given up would apply a `down` the CLI already reported as timed out, and an abandoned place in the queue would hold later requests. (evidence: src/daemon/channel.ts, `CONTROL_TIMEOUT_MS`; src/daemon/daemon.ts, `stop`)

**Rejected alternatives**, recorded so they are not reopened silently: a workspace selector in the gateway (no evidence in the pinned CLI, C3); a new `config.json` key listing projects (static, not per `up`); a per-session container shared between projects (V2-02, deferred); a new catalogue code for admission (C7 uses `POLICY_DENIED`); a new control method for daemon shutdown (C5 uses the in-process stop); a `down` that never stops the daemon when no session is live (rejected in C5 for the reason given there); a `down` lock wait equal to the client bound (rejected in C11).

## Startup reaper and scratch volume (Phase 19, RES-01)

**D19-2 (2026-11-03). Scratch volume mount options. Engineering decision.** The scratch volume, the named volume mounted read-write at `/scratch` (see `scratchVolumeNameOf` in `src/runtime/hardening.ts`), is mounted with the options `noexec`, `nosuid` and `nodev`. **D19-5 (2026-11-03). Startup cutover: adoption and registry rebuild. Engineering decision.** The driver's start no longer runs the destroy-all sweep (`startupSweep`, and with it `removeAllSecrets`, both removed). At every start it claims its socket, then runs `DriverLifecycle.adoptSurvivors`, which keeps each realm container that conforms to its retained binding and removes the rest with their secret entries and scratch volumes. It then rebuilds the registry entry of each kept sandbox and respawns its host supervisor (`src/runtime/driver/registry-rebuild.ts`). The supervisor is started through the spawn `createSandbox` uses, from the sandbox id in the runtime descriptor and the launch material. A survivor whose supervisor cannot be respawned is destroyed, and the start fails with the RealmError that refused it. Reason: a restarted driver must show a live sandbox to the gateway (List, Get, Delete) without destroying its container, its scratch volume or its secrets. Limits, recorded so they are not reopened silently: `createSandbox` keeps the gateway's workspace identifier in memory only and no artifact retains it, so an adopted record carries the session id its sandbox name names; List, Get and Watch wait for the adoption and the registry rebuild for at most `READY_WAIT_MS` (4 seconds, `src/runtime/driver/compute-driver.ts`) and then fail with UNAVAILABLE (`REALM_NOT_ACTIVE`) when that bound passes first; CreateSandbox is refused at once while either step is still running.

DeleteSandbox is refused at once while the adoption or the registry rebuild runs, as CreateSandbox is, so that no request acts on a container or a secret ahead of the adoption. List, Get and Watch wait for the same two steps instead, and Stop and Start are unimplemented.

**D19-6 (2026-11-03). Workspace snapshot mechanism. Engineering decision.** The workspace snapshot is a scripted full copy (`copyTree`), not a reflink or a filesystem snapshot. Reflink is not available: `cp --reflink=always` fails with `Operation not supported` on the ext4 root (`/dev/sda1`, no LVM, no btrfs or zfs under `/`). A snapshot is accepted only when the source manifest is identical before and after the copy and the copy manifest equals the before manifest (the quiescence rule). A concurrent append is detected and the snapshot is rejected. Restore keeps the workspace root directory, so its `st_dev` and `st_ino` do not change. It stages the snapshot in a directory on the same device and outside the root (`EXDEV` and `STAGE_INSIDE_ROOT` refusals), moves each root entry into a backup outside the root, moves each staged entry into the root, and deletes the backup only after the restored manifest equals the snapshot manifest. On any failure the entries move back. The swap is not atomic across the tree: each move is an atomic rename, and the rollback covers a failure part way through. The rollback is implemented and was not exercised by the recorded run. Limits: the copy costs time and space proportional to the tree (a 64 MiB tree copies in about 0.61 s and restores in about 0.60 s, plus about 0.80 s of manifest verification); the staging and backup directories must sit outside the Phase 18 `workspaceRoot` as well as outside the project root; the restore must run with the sandbox stopped, because a bind mount sees an empty root while entries are moved out; ownership and extended attributes are not preserved. Evidence and exact commands: `docs/integration/workspace-snapshot-spike.md` and `scripts/spike/workspace-snapshot.mjs`.

**D19-7 (2026-11-03). Hydration pin, bounded hydration, serve then hydrate. Engineering decision.** An adopted session is hydrated only on the workspace pin its workspace entry recorded at create: the device and inode in `<stateDir>/workspaces/<sessionId>.json`. `storedPinOf` (`src/lifecycle/session-state.ts`) verifies the record's workspace against that pin with `verifyPinnedAt`, and `LifecycleController.hydrate` verifies `deps.pinnedRoot` the same way before any state change or port call. A session whose entry is absent or lacks the device and inode is refused as `SCHEMA_INVALID`, and a session whose workspace no longer matches its pin is refused as `POLICY_DENIED`; in both cases the reap removes the container, deletes the record and never starts it. Reason: the pin is the only proof that the directory a survivor binds is the one created for it. Hydration runs `HYDRATE_CONCURRENCY` (4) sessions at a time (`hydrateAdopted`), because that bounds libpod requests and open descriptors, and each session runs under its own `startupBudgetMs`, so one that expires fails with `STARTUP_BUDGET_EXCEEDED` alone. The daemon opens its gate after the reap, the sweep and the reconciliation, then hydrates; while a session's hydration is pending, a request for it is refused at once with `REALM_NOT_ACTIVE`, which is retryable. Reason for the order: the reconciliation assumes no call is in flight, so it cannot run after the gate.
**Definitions.**

- **Adopted.** A realm sandbox container for which all of these hold: its container id is the one its session record names; its name is `realm-<sessionId>`; its `openshell.managed` label is `true` and its `openshell.ai/sandbox-name` label names that sandbox; it is running; and it passes the hardening verifier with the mount list in the second part of this section. The check is `verdictOf` in `src/runtime/session-execution.ts`. The list is not the whole test: adoption is also subject to the workspace pin check (D19-7) and the runner guard (D19-8). A container that meets every condition above is still not adopted when either refuses, and an unadopted container is an orphan under the rule below.
- **Orphan.** A realm container that is not adopted. Two causes give an orphan: no session record names it, or it fails the verifier (including an inspection that fails, because such a container cannot be proven good).

**The no-orphan guarantee.** After startup maintenance, and before the gate opens, every realm container is either adopted, or was removed and its removal proven by the same listing as before. No realm container that is not adopted survives startup, and no orphan is skipped silently. If a container cannot be removed or proven gone, the start aborts as it does now, because nothing may be served while an unknown container might survive.

**Records.** A session record that names no adopted container is deleted, as today. The session starts again on the next `up`.

**Logging.** The `StartupReport` and the `daemon.startup` record in `daemon.log` carry the removed container ids (`containerIds`) and the count of adopted sessions (`adopted`), but no cause for any removal. A refused adoption is logged on its own as `startup.adoption_refused` (owner item 8). The notice on `status`, `up` and `down` (D-1404) is emitted when a container was removed, a record was deleted or a session was adopted (`startupNoticeOf`, `src/daemon/startup.ts`).

**Order.** Adoption runs inside the reap, before any `LifecycleController` or `ToolDispatcher` exists (D-87). The reap timeout (`REAP_SWEEP_TIMEOUT_MS`) still applies.

**Decision (scratch volume).** RT-01's mount list gains one session-owned scratch volume. The earlier RT-01 wording is not edited; this section amends it.

- **Name and labels.** A Podman named volume `realm-scratch-<sessionId>`, labelled `io.realm.managed=true` and `io.realm.session=<sessionId>`.
- **Mount.** Read-write at `/scratch` in the sandbox. `/scratch` is the stated path. It is not `/workspace`, and no other mount uses it.
- **Policy.** The OpenShell policy must grant `/scratch` too, in the same change as the mount and the verifier. `buildPolicyDocument` (`src/runtime/openshell.ts`) renders `filesystem_policy.read_write` as `/workspace`, `/tmp`, the scratch mount point `/scratch` and `/dev/null` only. The `/scratch` entry is `HARDENING_PROFILE.scratchDestination` (`src/runtime/hardening.ts`), appended to `SANDBOX_SCRATCH_PATHS`; `/dev/null` comes from `SANDBOX_WRITABLE_DEVICE_PATHS`. Without that entry the policy does not grant writes at `/scratch`, even with a read-write mount there. The mount, the policy entry and the verifier rule land together.
- **Rest of the list.** Unchanged in substance. Three binds are preserved from `sandboxBindingOf` (`src/runtime/driver/sandbox-binding.ts`), and the `mounts` property of `verifyInspect` (`src/runtime/hardening.ts`) requires each one:
  - The pinned project workspace, read-write at `/workspace`.
  - The sandbox's state directory, `<sandboxStateRoot>/<sandboxName>`, read-only at `/realm-state` (`stateDestination`; the check requires `RW` false).
  - The channel directory, under the sandbox's secret directory, read-write at `/run/openshell/channel` (`channelDestination`; the check requires `RW` true).
  The scratch volume is added to these three. All three are host paths, so the workspace is not the only host path mounted. The verifier refuses any other mount: its `mounts` check holds exactly four, the three binds and the scratch volume.
- **Verifier.** The mounts property admits exactly one volume mount: the volume `realm-scratch-<sessionId>` for the adopted session, at destination `/scratch`, read-write. A tmpfs, any other volume and any other destination still fail the mounts property (RT-01).
- **Ownership.** The volume belongs to one session. No other session mounts it.
- **Lifetime.** The volume outlives the container and the daemon, so a restart that adopts the container keeps it. `realm down` removes the session's sandbox and then its volume, and the volume's removal is checked by a listing, as the container sweep is.
- **Cleanup.** A scratch volume is removed in two cases.
  - `realm down` removes it after the sandbox, as the Lifetime rule above states.
  - The startup reaper removes any scratch volume that no surviving session record references. A volume is referenced by a surviving record when that record's session id is the `<sessionId>` in the volume's name. The reaper deletes every record that names no adopted container, so a volume is removed when its session has no adopted container. This covers a volume left by a failed create or by a rejected container.
  The reaper runs this step after its container and record steps, so "surviving" means the record is still present after them. The volume's removal is checked by a listing. A volume that cannot be removed or proven gone aborts the start, as an orphan container does (the no-orphan guarantee). Each removal is logged once per start, with cause `no-record`.

**Not verified.** Attachment at create goes through OpenShell, and the pinned surface does not document an extra-mount option. This is recorded as OQ-P19-01. Realm creates no fallback mount and no fallback container (D-47).

**D19-8 (2026-11-03). Runner identity and duplicate guard. Engineering decision.** A runner is recorded when it is spawned: its pid, its process group, its process start ticks and the boot id go to a per-session runner record, written atomically. A runner is refused before its spawn when no state directory is configured, so no runner runs without a record. If the record cannot be written after the spawn, the runner is terminated and the start fails with OPENSHELL_START_FAILED. Before a session is adopted, hydration reads that record. A recorded live runner is terminated: SIGTERM to its process group, a bounded wait, then SIGKILL, and the identity is checked immediately before each signal. A pid whose start ticks differ from the record is never signalled. A session is not adopted when its record is absent or unreadable, comes from another boot, or its group still has members after the stop. Every such refusal uses OPENSHELL_START_FAILED, the code a failed start already records. Known gaps: a clean stop leaves the record, which is harmless because the next start overwrites it; members of an orphaned group are refused and not killed, because a reused process group id cannot be told apart from a new group. This entry closes register row 39. The live proof of the scenario is R6, which remains with the owner.

**D19-9 (2026-11-03). Checkpoint library decisions. Engineering decision.** The checkpoint library (`src/session/checkpoint.ts`, `src/session/checkpoint-lock.ts`, `src/session/proc-identity.ts`) takes the decisions below, in this order. Each has its reason.

1. **The registry entry is the trust anchor.** The library verifies the pinned root from the session's workspace registry entry with `verifyPinnedAt` before the copy, after it, and before the first restore move (and before recovery moves anything). A directory placed at the project path later is refused with `POLICY_DENIED`. Reason: the path alone names nothing. The entry names the device and inode the workspace was bound to, so a directory swapped in later receives neither a snapshot nor a restore.
2. **A manifest carries no stamps.** The snapshot compares the device, inode, size, mtime and ctime of every entry before and after the copy, and refuses with `LOCK_CONFLICT` when any of them differs, so a change-and-revert is refused. Reason: an identical content hash cannot show a write that was reverted before the second scan, but an entry's change time moves with every write, and no process can set it back.
3. **The lock is an O_EXCL-free publication.** The owner record (pid, process start ticks and boot id) is written and synced to a temporary file, then linked to `.lock` with `link(2)`. The lock path is never opened for writing, so it never exists empty. Only a provably gone owner is taken over: its pid is not alive, its start ticks differ, or its boot id differs. A live or unprovable owner is refused with `LOCK_CONFLICT`. Reason: a crash cannot leave a half-written lock, a pid is reused so the start ticks identify the process, and a pid from an earlier boot names another process, so the boot id is needed.
4. **The lock has two modes.** A "start" share is held by `create` and by `hydrate`, the two sandbox start entry points. It is shared by the starts of one process: the file is held while any start is in flight and released when the last one settles. A start that finds a checkpoint holding the lock is refused with `REALM_NOT_ACTIVE`. A "checkpoint" hold is exclusive, in the process and across processes. A checkpoint that finds a start's share, or another checkpoint, is refused with `LOCK_CONFLICT`. Reason: many starts of one session share one file, while a checkpoint must exclude every start and every other checkpoint.
5. **A restore writes a backed-up marker before it moves in.** The restore writes the marker after every root entry is in the backup and before the first move into the root. Recovery reads the marker as "every root entry is staged", sets every root entry aside, and only then returns the originals. Without the marker, recovery sets aside only the root entries whose names are also backed up. The in-process rollback removes the marker before any original moves back. Reason: a crash after a snapshot-only name, one that exists only in the checkpoint, has moved in would otherwise leave that name in the restored root beside the originals.
6. **A throwing sandbox predicate refuses with `REALM_NOT_ACTIVE`.** Reason: a sandbox whose state cannot be read is not assumed stopped, and `REALM_NOT_ACTIVE` is retryable.

The crash defect, a restore that crashed after a snapshot-only name moved in, is recorded by decision (5), the backed-up marker. The quiescence design of row 58 holds the session lock for every sandbox start, so a start and a checkpoint exclude each other, and a sandbox in any state other than unbound refuses both checkpoint operations.

Open items:

- **Orphaned start.** A start that never settles holds the session lock until it settles or the process exits.
- **Stopped projects.** Resolved by D19-10: a stopped project checkpoints from its workspace pin. Pin removal is open and is recorded in D19-10.
- **CLEANUP_FAILED after completed work.** A checkpoint or restore that completed can still exit 1 with `CLEANUP_FAILED` when only the lock unlink or the work-directory removal failed, so that exit must not be read as a failed snapshot.

**D19-10 (2026-11-03). Workspace pin for stopped projects. Engineering decision.** The workspace identity of a session outlives its registry entry. `up` binds the session's directory: it writes the session's pin in the workspace-pins directory of the state directory, or rewrites an existing pin to the identity of the directory it binds (`src/session/workspace-pin.ts`; the directory is mode 0700 and each file mode 0600). A directory replaced at the same path while the project is down is bound by the next `up`. Until then, create and restore refuse it with `POLICY_DENIED`. Before this change `up` refused a same-path replacement and nothing cleared the pin, so the session could not be bound again. `down` removes the registry entry and keeps the pin. Startup removes registry entries only. Checkpoint and restore resolve the workspace from the registry entry when one exists, and the sandbox state then comes from the daemon as before. Without an entry they resolve it from the pin, treat the sandbox as stopped, and make no daemon call. A workspace with neither refuses with `REALM_UNBOUND`.

Evidence: `test/cli/checkpoint-pin-e2e.test.ts` runs up, down, checkpoint create, a change to the workspace, checkpoint restore and up again through the control path. On the pre-change commit `f815416` it fails at the checkpoint after down with `REALM_UNBOUND`. With this change it passes.

Restart route. A daemon restart is a second recovery route, and it needs no original directory. Startup adoption refuses a session whose stored pin no longer matches the directory at its path (property workspace-pin, through storedPinOf in src/lifecycle/session-state.ts, called from src/daemon/startup.ts). The reap then removes its container and deletes its record (src/session/reap.ts), the registry entry is cleared, and a later up binds the replacement. This is expected behaviour, read from the code. No test exercises it yet, because the realm daemon fixture has no stop-only method and its libpod double does not track containers.

Open: pins accumulate, one per session id, and no command depends on a pin being absent; the removal rule is open. A moved root derives a new session id and is not refused; refusing a move needs its own decision. A directory replaced while its session is live fails the identity check of resolveSelection for status, tool and down with its path (test T1 (g) in test/daemon/daemon.test.ts pins the refusal for a renamed directory; a replacement is not tested). Putting the original directory back at the path lets down release the session. A release by session id is not available, and whether to add one is open.
