# Realm

Canonical, vendor-neutral instructions for AI coding agents and human contributors. CLAUDE.md imports this file.

## Project

Realm is the agent sandbox component of the GSD-Core USSR Stack (Ultrathink, Substrate, Swarm, Realm). Its tagline is "Realm, the home of AI Generated Code" (README.md).

Realm runs an agent's execution and file mutations inside a locked-down sandbox. The layering is settled in `docs/integration/runtime-decision.md` (S-08, with the 2026-10-26 and 2026-10-28 decisions recorded in `docs/integration/openshell.md`): the OpenShell gateway runs on the host; the Realm compute driver (`src/runtime/driver/`) creates one rootless, digest-pinned sandbox container per session through the libpod API; and AgentOS runs in that sandbox as a managed `openshell sandbox exec` child of the realm. Nothing nests OpenShell inside the Realm container, and nothing runs privileged.

Realm ships three things over one tool contract:

- an Omp plugin that autostarts per session;
- a standalone CLI, `realm`, with a long-running local daemon;
- MCP and ACP surfaces, so other agent hosts use the same sandbox.

Core guarantee, under the fail-closed policy: every file mutation either lands inside the realm under policy or fails closed, and the user can always see whether the realm is active or disconnected for the session. The policy `mode` defaults to `fail-closed` (decision D4): while the realm is not active, the Omp guard refuses host `edit` and Realm `write` calls. With the realm active, fail-closed asks Omp to remove its built-in tools outside the Realm allowlist, and Realm `write` replaces the built-in `write`; that is a guard, not containment: the spike recorded a `write` transport that survived removal of the built-in write, and the live check is pending. Advisory mode (warn and allow host `edit` and Realm `write` while the realm is not active and the daemon is reachable; Realm `write` refuses with the daemon unreachable) requires the explicit value `"mode": "advisory"`.

## Commands

Requires Node.js 22.13.0 or later (`engines` in `package.json`). CI runs Node 22.x and 24.x (`.github/workflows/ci.yml`). Realm does not install or upgrade Podman.

- `npm ci`: installs from `package-lock.json`.
- `realm init --image <name@sha256:digest> --workspace <absolute path> --state-dir <absolute path>`: writes fail-closed templates without overwrite and creates missing private state/secrets/sandboxes roots at 0700. Use `node <absolute checkout>/dist/src/cli/main.js` if `realm` is not installed. It does not provision Podman, a gateway, a supervisor or the compute driver. Driver and daemon must select the same physical generated config and matching image; see README Quick start. `realm up` uses `--workspace <absolute path>` or cwd, not the workspace saved by init.
- `realm doctor`: diagnostics; without a daemon it runs local checks. `realm doctor --fix --dry-run` previews the local safe subset; `realm doctor --fix` applies it and an idempotent repeat reports `fixes: []`. Only the configured state directory and its run/sessions children are created or tightened to 0700; symlinks, unsafe home/workspace targets, foreign owners and unreadable paths are refused. The parent must exist. No driver/gateway/private-root provisioning or workspace chmod is performed. Fix mode needs valid config, runs locally even with a daemon, and reports `dryRun`, `fixes`, `checks` on stdout and actions/refusals on stderr; inspect check results, not just exit 0. `--dry-run` alone is a usage error. The parent recorded 31 nonroot doctor passes/0 skips and actual CLI dry-run/apply/idempotence on 2026-10-31, before current docs edits.
- `realm host token status` and `realm host token rotate [--revoke-previous]`: read and rotate the capability keyring under the state directory without a daemon; `status` prints the policy mode (the default is `enforce` when the policy says nothing), the active key id, the retired key ids with their ages and the key file mode, never a key or a token. `realm doctor` has a `capability-tokens` item after `host-plugins`.
- `npm run typecheck`: `tsc -p tsconfig.json --noEmit`.
- `npm run lint`: `eslint .`, configured by `eslint.config.js`.
- `npm test`: compiles with tsc, then runs `node:test` over every compiled test under `dist/test/`. That glob includes `dist/test/integration/`, so the Podman-gated suites also run here and skip when Podman 5.x is absent.
- `npm run test:integration`: compiles, then runs `dist/test/integration/*.test.js`. Podman-gated tests skip with a stated reason: `PODMAN_UNSUPPORTED_VERSION` when Podman is older than 5.x, or `PODMAN_MISSING` when Podman is absent.
- The production live suite (`test/integration/production-driver.test.ts`, ten scenarios) is also gated: it runs the real stack and skips, naming the first missing prerequisite, unless `REALM_LIVE_PRODUCTION=1`, Podman 5.x, `REALM_LIVE_IMAGE`, `REALM_LIVE_DRIVER_CONFIG` (the absolute path of the `config.json` the running driver reads; the secret, workspace and sandbox-state roots come from that file, and a stale `REALM_DRIVER_SECRET_ROOT`, `REALM_DRIVER_WORKSPACE_ROOT` or `REALM_DRIVER_STATE_ROOT` is ignored), a rootless Podman socket, the `openshell` CLI and the built CLI are all present. Run the live file alone with `npm run build && node --test --test-concurrency=1 dist/test/integration/production-driver.test.js`. `npm run test:integration` runs the integration files in parallel, and this suite counts every container on the host, so the safe alternative is `node --test --test-concurrency=1 "dist/test/integration/*.test.js"`. Preconditions are in `docs/integration/openshell.md` (Running the production live suite). Scenario 10 stops the gateway user unit `REALM_LIVE_GATEWAY_UNIT` (default `realm-openshell-gateway.service`) and restores it in cleanup.
- `REALM_DRIVER_SOCKET` is also a prerequisite of the production live suite and of the Omp live OMPX-05 case: the absolute path of the socket the running compute driver binds. Unset, or not a socket, both suites skip with that name.
- The Omp live harness (`test/integration/omp-spike.test.ts`, `test/integration/omp-guard.test.ts`) uses isolated profiles and a scripted local provider, not an LLM or production Podman sandbox. `REALM_LIVE_OMP=1` opts in to starting real Omp; a test never sets it. `REALM_OMP_BIN` optionally selects the executable; otherwise `omp` must be on `PATH`. `REALM_OMP_NET_TRACE=1` opts in to strace assertions; missing prerequisites skip with a named reason (`ompSkipReason`). Cold catalog-refresh skips are separate from measured warm evidence. A refusing-proxy spike lever is not a built-Realm HARN-03 pass: only the stub and three documented loopback discovery ports may be allowed, with zero external/DNS/offenders. The original spike repair is implemented-unverified and built-Realm strict warm coverage is the separate signed prerequisite; no current warm pass is recorded. Fake-backed guard/network tests do not prove containment or production audit. Run guard cases alone, after `npm run build`, with `REALM_LIVE_OMP=1 node --test --test-concurrency=1 dist/test/integration/omp-guard.test.js`; the separate measured network case also needs its trace opt-in. See `docs/integration/omp-lifecycle-runbook.md` for evidence and proof limits.
- `npm run test:scripts`: runs `node:test` over `scripts/**/*.test.mjs`.
- A weekly scheduled mutation run (`node scripts/mutation/run.mjs`, `.github/workflows/mutation.yml`) is non-blocking and covers `src/fs`, `src/core/policy.ts` and `src/audit/redact.ts`; Stryker was not installed because research recorded a 188-package tree and an unproven fit with `node:test` on compiled output.
- `npm run test:coverage`: compiles, runs the whole compiled suite under `--experimental-test-coverage` with the lcov reporter, sums lines, branches and functions for `src/fs`, `src/core` and `src/tools`, and prints a table against the floors in `scripts/check/coverage-floors.json`, followed by the current sources (`src/<dir>/**/*.ts`) that no test loads (compiled file present but no lcov record), the ones that are not built (run `tsc` first), and a count of type-only modules and of stale compiled files (output whose source is gone), which are ignored. Below a floor, or with an unloaded or not-built source, it exits 1. The suite runs with source maps off: the command line carries `--no-enable-source-maps`, which overrides `--enable-source-maps` in `NODE_OPTIONS` (the environment is passed through untouched), because mapped records would fall outside the `dist/src/**` include filter. The floors are enforced (`"reportOnly": false`): each is floor(measured) minus the tolerance of 1, taken from CI runs of the gate leg, which is Node 22.x (`gateNode`); the `Coverage floors` step of the `verify` job runs it there, so a failing floor fails the job and blocks the release. `node scripts/check/coverage.mjs --lcov <file>` evaluates an existing lcov file, and `--write` only raises floors; lowering a floor is a hand edit with a reason in the pull request. Node writes the lcov file even when a test fails, so the table is printed even if the suite fails in that run; the suite's non-zero exit code is then still the command's exit code, and without an lcov file only that code is returned.
- `npm run check:docs`: scans the published docs for host-local absolute paths, runs the AGENTS.md and CLAUDE.md sync check, then scans the docs for stale statements about the default policy mode (`scripts/check/default-mode.mjs`).
- `npm run check:image-digests -- --dir <dir>` or `-- --image <ref>`: verifies the sandbox image inputs against `sandbox/expected-digests.json`. `--image` needs Podman. It is not part of CI.
- `npm run build:image`: builds the sandbox image with the digests recorded in `sandbox/expected-digests.json` and verifies it. Needs Podman. It is not part of CI.
- `npm run build`: compiles with `tsc -p tsconfig.json` into `dist/`.
- `npm run check:gates`: runs `scripts/check/gate-closure.mjs`, which verifies that the exec gate modules' import closure reaches no forbidden module and no `child_process` (TOOL-02), then `scripts/check/module-size.mjs`, the module-size ratchet described under Conventions, then `scripts/check/export-usage-gate.mjs`, which fails on a src export that only its own file or only test files use, unless `scripts/check/export-usage-allowlist.json` names it, then `scripts/check/lockfile-integrity.mjs`, which fails when a `package-lock.json` entry with a `resolved` URL lacks a sha512 `integrity`, resolves outside `registry.npmjs.org`, or is a `file:` or git dependency (it re-hashes no tarball).
- `npm run check:breaking`: runs the breaking-change marker guard, `scripts/check/breaking-change-guard.mjs`, on the range `origin/main` to `HEAD`. It reports and exits 0 by default. The pull request fields come as flags (`--base`, `--head`, `--title`, `--merge-method`) or as JSON in `REALM_PR_JSON` or the pull request event file, and a finding exits 1 only with `--enforce` (or `REALM_BREAKING_GUARD=enforce`); an input error exits 2. It is not part of `npm run check:gates` (that CI job checks out one commit and has no pull request context). The `Breaking change guard` workflow (`.github/workflows/breaking-change-guard.yml`) runs it with `--enforce` on every pull request into `main`, including when the title or body is edited. It is a check of the title and commit subjects it is given, not proof that a change is not breaking.
- `npm run check:pack`: packs the package, installs the tarball into a throwaway consumer and loads every schema and adapter manifest from it. Run `npm run build` first; it does not build.
- `npm run check:mcp`: spawns the built `realm mcp` over stdio and drives one session in both MCP protocol eras (a legacy `initialize` handshake, then modern requests and an unsupported version), checking the result shapes and the status call against `realm status`. Run `npm run build` first; it does not build.
- `node scripts/check/export-usage.mjs --list`: informational reference analysis of every `src/**/*.ts` export (TD-09). It errs towards keeping an export and classifies each as `used-in-src`, `forwarded` (another src file re-exports it), `test-only` (a documented seam, kept), `public-signature` (a type, class or enum used in the declaration of another export of its file: stays exported), `self-only` (drop the `export` keyword; delete the declaration if `noUnusedLocals` then flags it), `unclassified` (a re-export that does not resolve to an analyzed file, with the reason listed: never a removal candidate) or `excluded` (`src/core/errors.ts`, `src/core/ports*`, `src/contract/`, entry modules). `--json`, `--dir src/<dir>` and `--class <name>` filter it. It never fails the build (exit 2 only for a usage error); rerun it before adding an `export` that only a test needs. It parses the sources with the TypeScript compiler API (`ts.createSourceFile`, no program), the one documented exception to the Node-built-ins-only rule for scripts: `typescript` is already a devDependency, and the script is informational, not a CI gate.
- The `audit` job in CI runs `npm audit --omit=dev --audit-level=high` on Node 24.x. It needs the npm registry, so it is not part of the local gates; run the same command by hand when you change dependencies.

Every gate must pass before a change is reviewed (`CONTRIBUTING.md`).

## Layout

- `src/`: strict TypeScript. `npm run build` emits it to `dist/src/`.
  - `cli/main.ts`: entry for the `realm` CLI; `cli/init.ts` holds `realm init`, its preflight and its no-clobber publish of the two templates.
  - `cli/stdio-host.ts`: the boot sequence of `realm mcp` and `realm acp` (resolve, ensure, up, readback, settle, expose), their exit contract and their teardown on stdin end and on signals. `realm mcp` serves its handshake and `tools/list` at once and runs ensure, up and readback behind a not-active gate: tool calls are refused `REALM_NOT_ACTIVE` (retryable) until the boot driver has adopted a verified client, and `cli/stdio-settle.ts` decides the one diagnostic and whether the process exits 1 at stdin end. `realm acp` still answers only after the boot settles. Both write a one-time stderr hint on the first refused `POLICY_DENIED` (`host/refusal-hint.ts`). It reads no environment and never sends `down`. `--host <id>` and `--reattach` are parsed in `cli/main.ts`.
  - `cli/checkpoint.ts`: the realm checkpoint CLI.
  - `daemon/`: control socket (`channel.ts`), client, daemon, `ensure.ts` (starts the daemon once, only when the socket is absent, and waits for it; the status probe the CLI and the Omp extension share), `startup.ts` (the startup maintenance block and its adoption and reap seams), `seams.ts` (the status, socket and libpod helpers the daemon uses), `node-runtime.ts` (finds the Node a Bun host runs the daemon with), `host-boot.ts` (the recorder of the `host-boot` control method: metrics, one `host.boot` log line and the daemon-only `host-boot` audit chain), and `main.ts`, the daemon entry.
  - `omp/`: Omp plugin logic (`plugin.ts`, which takes its bounds, code lists, sub-state table and jitter from `host/boot.ts`), its host tool set (`host-tools.ts`), and its entry (`extension.ts`, which takes the bounds from the omp manifest, attaches through the shared `host/attach.ts` and reports boot through the shared `host/boot-observer.ts`).
  - `host/`: the host plugin contract and installer, host-neutral (reads no environment): the shared boot rules (`boot.ts`), the one daemon attach every entry shares (`attach.ts`), the production boot driver for the `mcp-config` hosts (`boot-driver.ts`), the boot report vocabulary and parser (`boot-report.ts`), the host-side boot observer (`boot-observer.ts`: log line, presence marker and report), the 22-host runtime table (`runtimes.ts`, with the install recipes of 19 hosts: `omp`, `claude`, `opencode`, `codex`, `kimi`, `kimi-code`, `cursor`, `copilot`, `qwen`, `augment`, `pi`, `cline`, `antigravity`, `kilo`, `codebuddy`, `hermes`, `muse-code`, `prime-agent` and `grok-build`; `windsurf`, `trae` and `zcode` are owner-approved deferrals that refuse as `recipe-pending`), the manifest (`manifest.ts`), the adapter (`adapter.ts`, which also runs the table's `shadows` guard), the install recipes and engine (`recipe.ts`, `install.ts`), the Codex owned-block TOML table guard, a line scanner and not a parser (`toml-table.ts`), the Hermes `yaml-map` owned-entry line scanner and planner (`yaml-scan.ts`, `yaml-owned.ts`), the receipt (`receipt.ts`), and the presence markers (`presence.ts`). `adapters/omp` at the package root is the shipped Omp shim that `realm host install omp` writes.
  - `mcp/`: MCP stdio server (`server.ts`: transport and routing) and the protocol versions and result shapes of both eras (`protocol.ts`). It serves revision 2026-07-28 and answers the `initialize` handshake of the legacy revisions that Claude Code speaks (`docs/integration/mcp.md`, Q6).
  - `acp/`: ACP agent (`agent.ts`) and its stdio entry (`stdio.ts`).
  - `realm/`: composition root (`compose.ts`) that wires the adapters into the controller and dispatcher.
  - `lifecycle/`: `controller.ts` (the lifecycle controller), `session-state.ts` (live-state and stored-pin helpers), `bounds.ts` (the teardown and hydrate bounds), `adoption.ts` (hydrating adopted sandboxes), and `mutation-gate.ts`.
  - `tools/`: the single shared tool dispatcher (`dispatch.ts`) and the workspace file handlers (`workspace.ts`).
  - `runtime/`: Podman probe and version check, libpod client and routes, OpenShell adapter, hardening verifier, seccomp evidence (`seccomp-evidence.ts`), egress rules, session execution, and runtime config. The AgentOS pieces are `agentos.ts` (the port), `agentos-driver.ts` (the OpenShell-carried driver, always bound; its sandbox image is the configured digest-pinned `config.image`, and each session's runner acts on its own sandbox, `realm-<sessionId>`), and `agentos-workload.ts`. `runtime/driver/` holds the compute driver: gRPC server, lifecycle, channel and secret store, supervisor spawn, and seccomp profile delivery.
  - `runtime/driver/registry-rebuild.ts`: the startup registry rebuild.
  - `runtime/driver/` modules: `fs-guards.ts` (the containment helpers the driver shares), `lifecycle-guards.ts` (sandbox state, spec and overlap guards), and `compute-driver-create.ts`, `compute-driver-state.ts` and `compute-driver-output.ts`, the helpers that `compute-driver.ts` calls.
  - `session/`: session record store, state-directory paths, the startup reaper (`reap.ts`), the workspace checkpoint library (`checkpoint.ts`, RES-04), the runner identity record (`runner-record.ts`), and the workspace pin (`workspace-pin.ts`), which `down` keeps.
  - `fs/`: canonical paths, root allowlist, credential-path denial, advisory write locks, atomic writes, read, list, glob, and write, and `temp-sweep.ts` (`src/fs/temp-sweep.ts`, which removes orphaned atomic-write temp files; the daemon calls it at start, before it serves).
  - `audit/`: redacted JSONL audit log, and `reconcile.ts` (`src/audit/reconcile.ts`, which appends `AUDIT_OUTCOME_UNKNOWN` reconciliation lines for admissions with no result; the daemon calls it at start, before it serves).
  - `observe/`: the JSON-line logger (`logger.ts`), its file and stderr sinks (`log-file.ts`, size-capped, rotated to one `.1` file), correlation ids (`ids.ts`), and the in-memory metrics registry with its strict snapshot validator (`metrics.ts`). The daemon uses them: the entry writes its records to stderr, which is `daemon.log`, through the logger; the daemon writes its lifecycle, control and tool records to `requests.log` through the logger and the file sink; and it counts metrics in memory.
  - `doctor/`: prerequisite checks behind `realm doctor`, with the host-binary checks in `checks-host.ts`, and `fix.ts`, the local safe subset that `realm doctor --fix` applies.
  - `capability/`: capability tokens for stdio hosts (policy key `capabilityTokens`, default mode `enforce`; `off` is the opt-out): the `rcap1` token mint and verify (`token.ts`), the keyring at rest with rotation (`keyring.ts`), the tool-to-capability mapping and per-host profile (`admit.ts`), the gate the daemon runs before the dispatcher (`gate.ts`) and the bound on its audit lines (`limiter.ts`). The doctor item is `doctor/capability-checks.ts`.
  - `contract/`: tool and session-record schemas and the schema validator (`validate.ts`).
  - `core/`: frozen shared contracts: states and the state machine, status labels, policy loading with `policy.schema.json`, the typed error catalogue (`errors.ts`), the event bus, ports, backoff, and `withTimeout` (`timeout.ts`); and the package version reader (`package-version.ts`).
- `test/`: `node:test` suites by area, largely mirroring `src/`. `test/integration/` holds the Podman-gated suites and the Omp live harness. `test/support/` holds shared fakes, `property.ts` (the shared `fast-check` configuration, 200 runs from a fixed seed; `REALM_PROPERTY_SEED` overrides it, used by the `*.property.test.ts` files in `test/fs/` and `test/core/`), and the Omp harness: `omp-live.ts`, `scripted-provider.ts`, `omp-profile.ts`, `omp-rpc.ts`, `realm-daemon-fixture.ts`, `net-trace.ts`, and `omp-spike-extension.ts`. The hermetic Omp stall probe (`test/omp/attach-stall.test.ts`) rests on `stall-probe.ts` (the slice recorder and the confirmed blocking verdict), `scripted-control-socket.ts` (a stand-in daemon socket with scripted reply latencies) and `cpu-burner.ts` (worker-thread CPU burners). The Omp responsiveness measurement rests on `omp-contention.ts` (the readings and the attribution of every stall interval), `omp-verdict.ts` (run validity, the derivation of the calibrated bounds, the order rule and the verdict table), `omp-calibration.ts` (the single home of the four calibrated constants, unset until frozen), `omp-window-analysis.ts` (the recomputation of a window or a calibration from its records and CSVs) and `omp-arm-run.ts` (the scope wrapper, the contention sampler and the run record).
- `scripts/`: plain ESM `.mjs` using Node built-ins only (`scripts/check/export-usage.mjs` and `scripts/check/export-usage-gate.mjs` are the two exceptions: both use the `typescript` devDependency, and the gate does so through `export-usage.mjs`). `scripts/check/` backs `npm run check:docs`, `npm run check:image-digests` (`verify-image-digests.mjs`), `npm run test:coverage` (`coverage.mjs` with `coverage-floors.json`) and `npm run test:scripts`, and holds the export usage gate: `scripts/check/export-usage-gate.mjs` (the gate that `npm run check:gates` runs; it fails on self-only and test-only exports unless `scripts/check/export-usage-allowlist.json` names them with a reason, and fails on stale allowlist entries (an entry that matches no failing export)), `scripts/check/export-usage.mjs` (the analysis that the gate imports), and the tests `export-usage-gate.test.mjs` and `export-usage.test.mjs`. `scripts/image/` backs `npm run build:image` (`build-image.mjs`). `scripts/release/` backs the build and publish jobs (`next-version.mjs`, `version.mjs`, `sync-version.mjs`, `changelog.mjs`, and `assets.mjs`, which writes `SHA256SUMS` and the CycloneDX SBOM).
- `scripts/spike/`: `workspace-snapshot.mjs`, the RES-04 workspace snapshot spike. It is not a gate.
- `scripts/check/module-size.mjs` (Q0-002): the module-size ratchet that `npm run check:gates` runs. Its allowlist, `scripts/check/module-size-allowlist.json`, holds the ceilings for `src/**/*.ts` files over 1000 lines. Its unit tests are `scripts/check/module-size.test.mjs`, run by `npm run test:scripts`.
- `docs/`: `integration/` (integration and decision notes, such as `runtime-decision.md`), `hosts/snippets/` (host config snippets), `policy-reference.md`, `checkpoint.md` (the `realm checkpoint` reference), and `specs/realm-spec.xml` (the product spec).

- `release/milestone.json`: the milestone and its minor number, which set the release line.
- `assets/brand/`: logo and banner artwork.
- `.github/`: `dependabot.yml`, `workflows/ci.yml` (verify, site, audit, build, and publish jobs), `workflows/breaking-change-guard.yml` (the breaking-change marker guard on pull requests), `workflows/pages.yml` (site build and deploy), `workflows/rollback.yml` (manual prerelease marking of a release, which also dispatches `pages.yml` for the known-good tag and its commit SHA), `PULL_REQUEST_TEMPLATE.md`, and `ISSUE_TEMPLATE/`.

## Conventions

- TypeScript in strict mode, ESM only (`"type": "module"`). `tsconfig.json` enables `strict`, `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, and `noUnusedLocals`. Public APIs are typed and documented.
- Tests use `node:test` and assert observable behaviour. No source-text tests: a test must not assert on the text of a module.
- Errors are `RealmError` values (`src/core/errors.ts`). Each carries a machine-readable `code` from `ERROR_CODES`, a human-readable `reason`, and a `retryable` flag. An optional `causeCode` is itself a catalogue code, so raw runtime text never enters an error.
- Every async boundary has a timeout (`withTimeout`, `src/core/timeout.ts`).
- No silent catch blocks, except the named exceptions under QUAL-01 in `.planning/REQUIREMENTS.md`. ESLint's `no-empty` rule rejects empty catch blocks.
- `process.env` is read only at the entry edges: `src/cli/main.ts`, `src/daemon/main.ts`, `src/omp/extension.ts`, and `src/runtime/driver/main.ts`. Other modules take their environment as an argument.
- No version string is copied into source: the MCP and ACP surfaces read the package manifest through `packageVersion()` (`src/core/package-version.ts`), because the release rewrites the manifest and a copied string goes stale (release 0.2.0 advertised `0.0.0`).
- No suppression comments. `eslint.config.js` bans `@ts-ignore`, `@ts-expect-error`, and `@ts-nocheck`; fix the cause instead.
- Module-size ratchet (`scripts/check/module-size.mjs`, Q0-002): a `src/**/*.ts` file over 1000 lines fails `npm run check:gates` unless `scripts/check/module-size-allowlist.json` lists it with a ceiling at or above its current line count. A listed file fails when it grows past its ceiling, when it drops to 1000 lines or below, and when it is deleted, so its entry is removed in the change that shrinks or deletes it. A change that grows a listed file or adds an over-limit file splits it or raises its ceiling in the same pull request, with the new count stated there. The merge that brings a lane's growth into `main` re-measures every ceiling on the merged tree. Never raise a ceiling silently.
- No new npm dependency unless the pull request records a justification, a licence check, and a maintenance check (`CONTRIBUTING.md`). Scripts use Node built-ins only, except `scripts/check/export-usage.mjs` and `scripts/check/export-usage-gate.mjs`, which use the existing `typescript` devDependency: the gate imports `export-usage.mjs`.
- Commit subjects start with a Conventional Commit type (`feat`, `fix`, `perf`, `refactor`, `docs`, `test`, `build`, `ci`, `chore`, or `security`), with an optional scope. The changelog groups entries by type.
- A breaking change carries the `!` marker after the type and scope in the subject of each commit that makes it, and in the pull request title. A change is breaking when a documented contract, default, wire shape or schema changes incompatibly. A `BREAKING CHANGE:` footer line is read by `npm run check:breaking` but not by the changelog, so the footer alone does not put the change in the release notes.
- No host-local absolute paths in committed files: no home-directory, temporary-directory, or Users-directory paths. `npm run check:docs` enforces this for the published docs.
- Settled runtime decisions (`docs/integration/runtime-decision.md`). Change them only through a new recorded decision:
  - The OpenShell gateway runs on the host, and the Realm compute driver creates the session container. Do not nest OpenShell inside the Realm container.
  - One container per session. The daemon owns sessions. A surface attaches by connecting to the control socket and calling `up`, which is idempotent. There is no attach or detach protocol.
  - The sandbox lasts until `realm down`. A host shutdown closes that host's client and never sends `down`.
  - The OpenShell CLI is pinned to the 0.1.5 verbs, re-verified on 2026-10-26: `sandbox create` with `--policy`, `--detach`, `--cpu`, `--memory` and `--from` (no create command and no `--no-keep`), `sandbox exec` with `--name`, `--workdir`, `--no-tty` and `--no-login-shell` (the workload after `--` of a dispatcher exec is prefixed by the in-sandbox bash watchdog `/usr/bin/bash -c SCRIPT realm-exec-wd 28.5`, Phase 39; the pinned form itself is unchanged), and `sandbox delete`. A create command does not run in 0.1.5, so the AgentOS runner starts as an exec child after create. Recorded decision: the pin moves from 0.1.2 to 0.1.5 on 2026-10-26, and the create-command finding is its reason (`docs/integration/openshell.md`). Re-verify the pin on any upgrade. Phase 17 adds the verb `status` (`openshell status`, no flags): the health probe runs it on the failure path only, to tell a lost gateway from a dead runner (`OPENSHELL_GATEWAY_LOST`; `docs/integration/runtime-decision.md`, "Catalogue extension (Phase 17)").
  - The Anda bridge is removed (owner decision D-27-01, 2026-11-17; `docs/integration/runtime-decision.md`, section "Anda bridge removal"). Realm does not dial Anda: no `andaUrl` key, no `ANDA_` error codes, no `degraded` state. Phase 28 of milestone v4.0 removed it, and the module `src/anda` is deleted. MCP over stdio stays the transport for agent hosts (D-27-02), and Anda may still consume Realm as an MCP client over stdio.

## Versioning and release

- The release line is `0.<milestone minor>.<part>`. `release/milestone.json` holds the minor: v1.0 was minor 1 (line `0.1.x`), v2.0 was minor 2 (line `0.2.x`), v3.0 was minor 3 (line `0.3.x`), v4.0 was minor 4 (line `0.4.x`), v5.0 was minor 5 (line `0.5.x`) and v6.0 is minor 6 (line `0.6.x`).
- A new milestone starts in a pull request that sets the next minor number in `release/milestone.json`. Its first release is `0.<minor>.0`.
- Each push to `main` that passes the `verify` job, the `site` build job and the `audit` job runs the release: the `build` job, then the `publish` job. Together they publish the next part: `0.<minor>.0` first, then `0.<minor>.1`, and so on. `scripts/release/next-version.mjs` derives the next part from the latest `v0.*` tag. A milestone minor that is behind the latest tag fails the release.
- The release owns `CHANGELOG.md` and the `version` field in `package.json`, `package-lock.json`, and the four adapter manifests that carry a release version: `adapters/claude-plugin/.claude-plugin/plugin.json`, `adapters/muse-code/.muse-plugin/plugin.json`, `adapters/hermes-agent/plugin.json`, and `adapters/prime-agent/package.json`. Pull requests never edit those files' version fields or `CHANGELOG.md`. `node scripts/release/sync-version.mjs --files` lists the version files.
- Build job (`.github/workflows/ci.yml`). It runs dependency and build code, so it has `contents: read` only: no write grant, and no checkout credential persisted in `.git/config`. It installs with `npm ci --ignore-scripts`, then:
  - plans exactly one action for the push before any remote write: `skip` when the target tag's GitHub release is published with every expected asset; `superseded` when `origin/main` is no longer this commit, which exits green so only the newest push releases; or `normal`. A target tag that exists with no release, a draft release, or a published release lacking an expected asset fails the plan. It reads one UTC release date for the whole run.
  - repairs the latest milestone tag when its GitHub release is missing, a draft, or published without every expected asset (a failed earlier attempt). It first checks that the tag is on `origin/main`, and only then builds that tag's files in a separate worktree, so no build step runs on the tag's code before that check.
  - for a normal release, bumps the versions (`scripts/release/sync-version.mjs`); generates the `CHANGELOG.md` section from `git log --no-merges <previous tag>..HEAD`, grouped by Conventional Commit type, leaving out `chore(release)` commits and commits scoped `planning` unless the subject carries `!`, and the features a later commit removes (`scripts/release/changelog.mjs`). A feature is removed by a `git revert` pair, or by a commit that names each feature commit it removes in its own `Removes: <sha>` trailer line (one line per commit); the removing commit leaves too, unless it names a commit from an earlier release, so that removal stays visible. A revert of the removing commit restores the features. Write the trailer on any non-revert removal; selection is by commit id, never by subject or file. Builds and packs the tarball; runs `scripts/check/pack-smoke.mjs` before any tag or push; and writes `SHA256SUMS` and a CycloneDX SBOM (`scripts/release/assets.mjs`).
  - uploads the `release-files` artifact: the tarball, `SHA256SUMS`, the SBOM, and `plan.txt`, which records the action, tag, version, previous tag and release date. A repaired milestone's files go in `milestone-files`.
- Publish job (`.github/workflows/ci.yml`). It holds the `contents`, `actions`, `id-token` and `attestations` write grants, runs in the `release-main` concurrency group, and downloads only the build job's artifacts. It runs no npm install, build or pack. It reads the plan, then:
  - regenerates the version files and `CHANGELOG.md` with the plan's date and previous tag, and fails unless its `CHANGELOG.md` matches the copy packed in the tarball byte for byte;
  - attests build provenance for the tarball, `SHA256SUMS` and the SBOM, and for the milestone files when present, before any tag is pushed;
  - creates the milestone's GitHub release if none exists;
  - commits `chore(release): v<version> [skip ci]` as `github-actions[bot]`, then pushes `main` and the tag `v<version>` in one atomic push. A rejected push while `origin/main` has moved is superseded: publish exits green and the newer push releases;
  - creates the GitHub release, with the tarball, `SHA256SUMS` and the SBOM, if none exists for the tag, and dispatches `pages.yml` when the tip of `main` is a release commit.
  - Only the git push step holds a write credential for git. It passes the token through its environment and ignores the global and system git configuration and hooks, because build code ran earlier as the same user. The `gh` steps receive the token as `GH_TOKEN`.
- Retries. Re-running the publish job after a failure is safe. A tag already on `origin` is reused only when it names this run's release commit: the triggering commit itself when no release file changed, or a commit whose parent is the triggering commit and whose subject is `chore(release): v<version> [skip ci]`. Its release files must equal this checkout's regenerated files, and it must be on `origin/main`. Any other commit at the tag stops the run. A reused tag skips the commit and push steps, and a GitHub release is created only when none exists for the tag. A retry uses the plan's values, because `next-version.mjs` reports the following release once the tag is on `origin`.
- Attestation. The publish job creates the attestation after the build job's files are downloaded and checked, so it records the `ci.yml` workflow run that built them, and the digests of those files. Verify a downloaded file with `gh attestation verify <file> --repo <owner>/<repo>`. The release carries no signature.
- Rollback. `.github/workflows/rollback.yml` is a manual `workflow_dispatch` with a `tag` input (`v<major>.<minor>.<patch>`, the release to withdraw) and a `docs_tag` input (`v<major>.<minor>.<patch>`, the known-good release whose documentation is published, and not the same as `tag`). It resolves `docs_tag` to its peeled full 40-character commit SHA (annotated and lightweight tags alike), runs the checks, and writes that SHA to the step output `sha` only if all of them pass. The checks: `docs_tag` is an existing tag whose commit is on the default branch, and its GitHub release is published (not a draft or prerelease). Only then does it mark `tag` as a prerelease and dispatch `pages.yml` on the default branch with the pair `source_ref` (the `docs_tag` value) and `source_sha` (that output). The tag and the SHA reach each shell only through environment variables and the dispatch arguments, never through shell source.
  - Pages verification of a source pair. `pages.yml` treats the pair as untrusted input and verifies it before it checks out any selected source or runs any of its code. The pair is accepted only when both inputs are set, `source_ref` is `v<major>.<minor>.<patch>` and `source_sha` is 40 lowercase hexadecimal characters. It then asks the GitHub API for the tag as it is now (peeling annotated tags) and requires its commit to equal `source_sha`. It requires the tag's release to be published (not a draft or prerelease) and `source_sha` to be an ancestor of the default branch. Only the verified SHA reaches the checkout step. Empty `source_ref` and `source_sha`, as the publish job dispatches them, build the dispatched branch as before. A manual dispatch with a tag alone or a SHA alone is refused. Every dispatch, with a pair or without, must come from the default branch's workflow: `pages.yml` refuses any other branch. That check is in-workflow defense in depth, not an enforced boundary (see the residual limits).
  - Tag movement. If `docs_tag` is moved or deleted after `rollback.yml` validated it, `pages.yml` finds that the tag no longer resolves to the validated SHA, fails before any checkout, and publishes nothing; the SHA that rollback validated is never replaced by the new target. `tag` is already marked as a prerelease by then. Inspect the tag, then run `rollback.yml` again: it validates the tag as it now is and dispatches the SHA it now resolves to (marking an existing prerelease again changes nothing). The rollback changes no tag, release asset, commit or `main`; the tag stays, so the next release takes the next part number.
  - Residual limits. Every release, rollback, Pages and mutation job runs on a GitHub-hosted runner (`ubuntu-24.04`; each job gets a fresh virtual machine), as `verify` does; the omega-ci self-hosted pool was removed from these workflows on 2026-11-16 (owner decision) because its autoscaler served no runner. The build job runs the known-good commit's site build with no write grant, and the deploy job runs no code from that commit. Job tokens separate permissions, not the code that runs inside a job. The in-workflow checks are not a control outside the workflow: a different workflow revision that omits them is not stopped by them. The control outside the workflow revision that this repository relies on is the `github-pages` environment's deployment branch policy, which allows only `main`; a real denial from another branch was recorded on 2026-11-16 (run 43889942123: "Branch ... is not allowed to deploy to github-pages due to environment protection rules"). That policy does not stop a revision pushed to `main`, which has no branch protection (repository settings are owner-held, TD-10). A bad `docs_tag` that passes the checks would publish its documentation, so the checks are the only gate.
- Nothing is published to npm: `package.json` has `"private": true`.

## Merge and release flow

1. Branch from `main`. Changes reach `main` through a pull request; the publish job is the only other writer, pushing its release commit and tag.
2. Open a pull request into `main`. Complete `.github/PULL_REQUEST_TEMPLATE.md`: requirement IDs, the gate checklist, and risk and rollback.
3. `ci.yml` must be green: the verify job (typecheck, lint, unit, integration and script tests, docs, gate-closure, build, pack and MCP checks, on Node 22.x and 24.x), the site build job and the dependency audit job (`npm audit --omit=dev --audit-level=high`). The build job waits for all three. The `Breaking change guard` check (`.github/workflows/breaking-change-guard.yml`, job `Breaking change marker`) must be green too; it is a separate workflow that the build job does not wait for, and `main` has no branch protection, so the ship flow reads it as it reads the Greptile score.
4. The Greptile review must reach 5 out of 5 with no open comments before merge. This is a process rule that the ship flow enforces: `main` has no branch protection, so GitHub does not enforce it.
5. Merge only through the ultrathink ship flow, which reads `ship.mergeMethod` from the Ultrathink user configuration (default `squash`; it is not stored in this repository). Never run `gh pr merge` from a shell. The merge method decides the release notes. A pull request whose commits are individually meaningful Conventional Commits lands with a merge commit, so the notes list each commit. A single-commit or throwaway-commit pull request may be squash-merged with a Conventional Commit title, which becomes its one entry. Set `ship.mergeMethod` to match. A pull request with a breaking commit lands as a merge commit, or is squash-merged with a title that carries the `!` marker. The ship flow runs `npm run check:breaking -- --enforce` with the merge method before merging; the guard checks the title and commit subjects it is given, not the commit that reaches `main`. The CI check does not know the merge method, so it applies the strict rule (a marked title and a marked commit) to every pull request that is breaking. PRs 1 to 4 were squash-merged and PR 5 was merged with a merge commit; PR 6 is to be merged with a merge commit.
6. Never force-push `main`. Never rewrite history without an explicit user decision.
7. A push to `main` that passes verify, the site build and the audit runs the release: the build job, then the publish job. Its release commit carries `[skip ci]`, so it starts no CI run of its own. See Versioning and release.

## Safety and high-risk paths

- Human review is required before merge for `.github/workflows/**`, `release/**`, `scripts/release/**`, `LICENSE`, and `NOTICE`.
- The sandbox is a security boundary. Policy violations fail closed when the policy mode is fail-closed, and a file-mutating tool must never run outside the realm when the active policy requires the realm. The default mode is fail-closed (a policy with no `mode` loads as fail-closed); advisory, which warns and allows, is the explicit opt-in and is not containment. Never write documents that call advisory the default: `npm run check:docs` fails on them (`scripts/check/default-mode.mjs`).
- No host secrets are injected into the sandbox by default, and no secrets belong in the repository, images, or logs. There is no telemetry that sends data off the machine.
- Podman runs rootless only. Never use privileged containers, and never mount a host Docker or Podman socket into a container.
- The control socket is user-only: its directory is mode 0700 and the socket is mode 0600.
- With the default `capabilityTokens.mode` of `enforce` (set `off` to opt out), the daemon creates the keyring at start, verifies a per-host token on every tool call and refuses a missing or invalid one with `POLICY_DENIED`, and the token can only narrow what the policy grants. This does not stop a process of the same user that can read the token or the key file, and a model with a native shell in its host is such a process (`docs/integration/mcp.md`, Q10).
- Metrics are read only over that control socket (`realm metrics`). The daemon has no metrics listener, and no tool exposes metrics. The snapshot carries `hostBoot` counters and the `timings.hostBootMs` histogram, fed by the self-reported `host-boot` control method.
- Report suspected vulnerabilities privately through GitHub private vulnerability reporting (`SECURITY.md`). Do not open a public issue, pull request, or discussion for one, and do not put secrets in the report. Only the latest release line is supported: currently 0.6.x, and 0.7.x from its first release, 0.7.0.
- `.env` and `.env.*` files are git-ignored (`.gitignore`).
