## Requirement definitions

- **HOST-01:** A `HostPluginManifest` (schemaVersion 1) states a host id, integration kind (`extension` or `mcp-config`), launch or entry, requested capabilities and, for `extension` only, boot bounds; it is validated strictly and fails closed with `SCHEMA_INVALID`.
- **HOST-02:** Each capability maps to exactly one existing policy fact; `resolveCapabilities` reports admitted and denied requests against a `Policy`, with catalogue codes, and a manifest cannot request beyond its integration ceiling.
- **HOST-03:** The runtime table is a compile-time-complete `Record<HostId, HostRuntimeEntry>` with flag, aliases, tier, home candidates, optional env override and binaries, pinned to 21-DISCOVERY.md by test.

<threat_model>
## Trust Boundaries

| Boundary | Risk |
| --- | --- |
| Manifest input (a file or a plugin author's object) to the validator | A crafted manifest smuggles a secret, a path, a shell string or extra authority past review. |
| Plugin-requested capability to Policy | A plugin asks for more than the operator's policy admits; a resolver bug widens it. |
| Runtime table to the user's home | A wrong or attacker-influenced home resolves outside the intended config directory. |
| Plugin code inside the CLI agent to the sandbox | A malicious or compromised workload or plugin uses the contract as a new route around the gates. |

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |

| T-21-01 | Tampering | manifest validator | high | mitigate | Task 3: unknown keys refused, no env or secret keys, bare-name `command`, whitelisted `args`, relative `.js` entry without `..`, prototype keys refused; fixed error message. |
