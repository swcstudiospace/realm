## Requirement definitions

- **HOST-05:** `createHostAdapter(entry, manifest, deps)` implements detect, install, uninstall and status for a recipe-driven host: atomic, idempotent, optimistic, confined to the resolved config home, receipt-owned, with a side-effect-free dry run, resumable after a crash, and a typed refusal reason for every refusal.
- **HOST-06:** Every non-dry-run operation that changes something is bracketed by `admission` and `result` audit lines on the shared chain under session id `host-plugins`, emits redacted structured log events, never records content or secrets, and refuses to start if the admission line cannot be written.

It returns a list of `PlannedChange { path (relative), action: "create" | "update" | "noop" | "remove", before: string | null, after: string | null, beforeSha256, afterSha256, bytes }`, or throws `HostRefusal` (extends `RealmError`, pattern of `FixRefusal` in `src/doctor/fix.ts`) with a fixed `reason`.

Absent file: create `{...}` with the key. Present file must parse as a JSON object (invalid JSON, a JSON array or scalar root: refuse `unparseable`, code `SCHEMA_INVALID`, nothing planned); JSON with comments is therefore refused. Unrelated keys keep their value and order; the detected indentation (tab, 2 or 4 spaces; default 2) and the presence of a trailing newline are preserved. Key absent: `update` (or `create` for a new file). Key present and deep-equal to `value`: `noop`. Key present and different: refuse `foreign-content` (`POLICY_DENIED`) unless the receipt entry for this path owns the key with `ownedSha256` equal to the hash of the current canonical JSON value, in which case `update`. An intermediate segment that exists and is not an object refuses `foreign-content`.
    - `text-block { file, block, homeRole? }`: the block is 1..200 lines, must not contain a line that equals the begin or end marker, and is wrapped as `# BEGIN realm host-plugin` / `# END realm host-plugin` (documented as valid for TOML and YAML; `#` is fixed, there is no comment-syntax option). No markers in the file: append after one separating newline (file ending without a newline gets one; an absent file is created). Exactly one marker pair with identical block: `noop`. One pair with a different block: `update` only when the receipt owns it (`ownedSha256` equals the hash of the current block text), else `foreign-content`. A begin without an end, an end without a begin, nested or more than one pair: refuse `unparseable`. After install then uninstall, a file that existed before is byte-identical to the original (including a missing final newline).
    - `bundle-copy { source, dest, homeRole? }`: `source` is a relative directory under the shipped `adapters/` directory (no `..`, no absolute path) whose files are supplied by the caller as `{ rel, bytes }` entries; `dest` a relative directory under the home. Each file is `create`, `update` (only when receipt-owned and unchanged), `noop` (identical bytes) or refuses `foreign-content` when a different file not owned by the receipt exists. More than 256 files or any single file over 1 MiB refuses `unparseable` (a bundle is small by contract).
    - Uninstall planning inverts install using only receipt-owned data. For `json-merge` it removes the key only when its current value hashes to the receipt's `ownedSha256` (then also the parents the receipt marks as created, and the file when the receipt marks it created and it is now empty); for `text-block` it removes the marker block only when the block text hashes to `ownedSha256` (and the `separatorAdded` newline); for `bundle-copy` it removes each owned file whose current hash equals the receipt's `afterSha256` (then the directories the receipt marks as created, if empty). An owned part that is absent, or a bundle file whose hash equals the receipt's `beforeSha256`, was removed already or never applied (a crash left a `pending` receipt) and plans `noop`, so uninstall is idempotent and resumable. An owned part present with any other content refuses `drifted` (`POLICY_DENIED`) for the whole operation and plans nothing (all-or-nothing preflight). Unrelated edits elsewhere in the same file are not drift for `json-merge` and `text-block`.
    - Determinism: the same inputs yield the same plan and the same hashes on every call.

    - HOST-05: a receipt is `{ schemaVersion: 1, hostId, recipeKind, state: "pending" | "installed", configHome, createdAt, entries: [{ path, kind, beforeSha256: string | null, afterSha256: string, ownedSha256?: string, createdFile?: boolean, createdParents?: string[][], separatorAdded?: boolean }] }` (`separatorAdded` records the newline a `text-block` install had to add before its block, so uninstall removes exactly that and the pre-install bytes come back).   <files>src/host/host-audit.ts, src/host/install.ts, test/host/install.test.ts</files>
  <behavior>
    - HOST-05: `planHostOperation(op, ctx)` resolves the config home with `realpath`, requires it to exist and be a directory (else `HostRefusal` `config-home-missing`, `POLICY_DENIED`; Realm never creates a host home), reads each target through an `lstat` walk that refuses any symlink component below the home with `PATH_ESCAPE` (`HostRefusal` `symlink`, whose fix text names `--config-home <real path>`), confirms every target stays under the real home, then calls `planRecipe`.     - `applyHostOperation(plan, ctx)`: (1) if every change is `noop` it returns `status: "noop"`, writes no host file and appends no audit line (an uninstall whose owned parts are all already gone still deletes its now-stale receipt, an unaudited bookkeeping step that touches no host file); (2) otherwise it appends the `admission` audit line, (3) for install, writes a `pending` receipt (planned hashes; uninstall skips this step because the existing receipt already lists everything owned and a rerun resumes through the `noop` rules above), (4) applies each change with `atomicWriteFile(target, content, { expectedPriorSha256: change.beforeSha256 })` (creating missing parent directories under the home only, never above it; `remove` deletes the file, then empty parents the receipt marks as created), (5) rewrites the receipt as `installed` (install) or removes it (uninstall), (6) appends the `result` line with outcome `ok` and returns `status` `installed` (install) or `removed` (uninstall); a dry run returns `planned`. A file changed between plan and apply surfaces as `WRITE_NOT_ATOMIC` and is reported as `HostRefusal` reason `concurrent-change`; the receipt stays `pending`, the result line records the code.
    - Dry run (`options.dryRun`): returns `status: "planned"` with the `PlannedChange` list (paths, actions, hashes, byte counts, never content) and performs no file system write at all: a before and after tree hash of the home and of the state directory are equal, no `hosts/` directory appears, and no audit file is created. The log gets one `host.install.plan` (or `host.uninstall.plan`) event.

The audit function is an injected seam defaulting to `appendAudit`. If the admission append throws, `applyHostOperation` rethrows `AUDIT_WRITE_FAILED` (or the `RealmError` the seam raised) before any write: the tree hashes of home and state directory are unchanged. If the result append throws after the change landed, the error is `AUDIT_WRITE_FAILED`, the change is not rolled back (a retried append could duplicate the line, `src/audit/log.ts` comment), and the log records `host.install.audit_failed`.
    - The chain stays valid: after an install and an uninstall, `checkAuditFile(<stateDir>/audit/host-plugins.jsonl)` reports ok and the file contains four lines (admission and result for each), each with `tool` `host.install` or `host.uninstall`.

    - Bounded async: every `fs/promises` read in planning and detection runs under `withTimeout(work, deps.readTimeoutMs, "TOOL_TIMEOUT")`; a test injects a stalling reader and gets `TOOL_TIMEOUT` with no operation partially applied. The synchronous `atomicWriteFile` calls cannot be interrupted by a timer, so the plan states that bound honestly: the write phase is bounded by the file sizes (1 MiB cap per file) rather than by a timer.
    - Crash resume: a `stageHook` seam on the engine throws after the first of two files is applied. State is `pending`, the first file holds its after-content. A second `install` completes (`done` for the first, `apply` for the second) and ends `installed`; instead a second `uninstall` after the crash restores the home tree to its pre-install hash.

A refusal raised while planning (foreign content, drift, symlink, missing home, unparseable file) logs `host.<op>.refused` and appends no audit line, because nothing was attempted; only a failure after the admission line records its code in the result line.

## Trust Boundaries

| Boundary | Risk |
| --- | --- |
| Host config directory (user-controlled, possibly attacker-planted symlinks) to the installer | A symlink or race redirects a Realm write to another file; the installer overwrites a user's own entry or secrets. |
| Workload or plugin to the installer | A malicious workload with write access to a host config home pre-plants content to make Realm's receipt claim it, or edits Realm's block to inject a different launch command. |
| Installer to the audit chain and logs | Config content, secrets or paths leak into logs or into the tamper-evident record; or an unaudited change lands. |
| Installer to the state directory | A forged or corrupt receipt makes uninstall delete files Realm never wrote. |
