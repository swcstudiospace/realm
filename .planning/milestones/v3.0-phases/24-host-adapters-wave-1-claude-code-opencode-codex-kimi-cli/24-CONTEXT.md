### Findings that shape the plans (verified in the repo, 2026-11-17)

- **F1. A Claude file recipe cannot reach `~/.claude.json` today.** `homes` for `claude` is `[".claude"]`; every recipe `file` is a relative path below the resolved home (`isSafeRelPath` bans `..`); the file lives one level above `~/.claude`. And `resolveHomes` with an env override returns `[override]` for every entry, and `installHome` in `src/host/adapter.ts` filters candidates by `entry.homes[index].role`, an index alignment that breaks as soon as an entry has two homes and an override (Kimi: skills home at index 0, `KIMI_SHARE_DIR` would replace it). D-24-01 fixes both with one pairs-based resolver.
- **F2. The `text-block` primitive cannot see a duplicate TOML table.** It owns the text between `# BEGIN realm host-plugin` and `# END realm host-plugin` (valid TOML comments) and refuses a block it does not own, but it never looks at the rest of the file. A user who already ran `codex mcp add realm -- realm mcp` has `[mcp_servers.realm]` outside any marker; appending a second one makes a file Codex cannot load. D-24-04 adds a conservative guard, not a TOML parser.
- **F3. `status` cannot tell drift from unreadable.** `entryState` maps a refused read (symlink, over 1 MiB, invalid UTF-8) and a missing owned part both to `drifted`. `~/.claude.json` is the file most likely to grow past the cap, and "drifted" would send the user to a reinstall that cannot succeed. D-24-09 adds one state.
- **F4. A leaf-symlink refusal prints a wrong fix.** `symlinkRefusal` always says `use --config-home <realpath>`, right for a directory component and wrong for a file symlink such as `~/.claude.json` (the hint would name the file as a home). 24-01 makes the hint directory-only.
- **F5. `HostRuntimeEntry.binaries` is empty for four of the hosts and wrong for Kimi.** Detection by binary needs `opencode` and `codex` (add them); `kimi` must stay without a binary because the name is shared by two products (E-K6).
- **F6. The recipe value and the boot manifest must agree.** `defaultManifestFor` launches `realm mcp --host <id>` (`src/host/manifest.ts:217-232`). A recipe value that drifts from it would register a server the boot path does not recognise (`--host` accepts only the 18 `mcp-config` ids, `src/cli/main.ts:93-99`). 24-02 pins the equality in a test.
- **F7. Module-size.** `src/host/recipe.ts` is 907 of 1000 lines; the TOML scanner goes in a new `src/host/toml-table.ts`.
- **F8. No fixture files.** `tsc` compiles `test/**/*.ts` to `dist/` and copies nothing else, so goldens are string constants in `test/support/host-config-goldens.ts`, each with its source and date.

### D-24-01. Homes by role, one resolver (ADPT-01)

`HostHomeSpec.role` becomes `"config" | "skills" | "mcp"`. A home of role `mcp` is the directory that holds the host's user-level MCP file when that is not the config home; it is never a detection home (it would make every machine "detected"). New pure `resolveHomeSpecs(entry, env): readonly { path: string; role }[]` in `src/host/runtimes.ts`, with these rules and nothing else: (R1) join each spec's `rel` with `env.home`; (R2) an absolute, non-empty `envOverride` value replaces the path of every home whose role is `config` or `mcp`, never `skills`; an empty or relative value is `SCHEMA_INVALID` as today; (R3) a new optional entry field `envBase: { name, sub }` (OpenCode: `XDG_CONFIG_HOME`, `opencode`) replaces the path of the `config` homes with `join(<absolute value>, sub)` when the variable is set, same validation; an entry never has both; (R4) an `envBase` or `envOverride` value is a base, never a `..` walk: the value must be absolute and is used as is. `resolveHomes(entry, env)` stays and returns the paths of the non-`mcp` specs (deduplicated, so `claude` with an override is still `[override]`; every existing caller and test keeps its behavior). `installHome` in the adapter picks by role from the specs instead of by index. Claude's table row becomes `homes: [".claude" (config), "." (mcp)]` with `homeRole: "mcp"` on the recipe, so `~/.claude.json` is `<home>/.claude.json` with home = `env.home`, or `<CLAUDE_CONFIG_DIR>/.claude.json` under the override (E-C2). `--config-home <abs>` for a host whose recipe has `homeRole: "mcp"` names the directory that holds the file (documented).

### D-24-02. Claude Code: `json-merge` into the user-scope file, value = what `claude mcp add` writes

`claude`: `{ kind: "json-merge", file: ".claude.json", keyPath: ["mcpServers", "realm"], value: { type: "stdio", command: "realm", args: ["mcp", "--host", "claude"], env: {} }, homeRole: "mcp" }`, `envOverride: "CLAUDE_CONFIG_DIR"`, `binaries: ["claude"]`. The value is byte-for-byte (canonical JSON) the entry E-C1 observed, so `claude mcp get`, `claude mcp remove realm -s user` and `realm host uninstall claude` act on the same entry, and a user who already ran that exact `claude mcp add` gets a no-op that Realm does not claim (it is not in the receipt). A different existing `realm` entry is `foreign-content`. The engine already preserves unrelated keys, indent, line endings, trailing newline and mode (`atomicWriteFile` copies the mode of an existing file and creates new files 0600), refuses lossy numbers, and rechecks the file hash right before the rename. Not done: a Claude plugin-registry recipe (E-C5), a local- or project-scope write (a project file is the workspace's, not the user's), and a change to `adapters/claude-plugin` (it is shared with Grok Build, and `--host` accepts only the 18 ids).

### D-24-03. OpenCode: `json-merge` with the V1-shaped entry into `opencode.json`

`opencode`: `{ kind: "json-merge", file: "opencode.json", keyPath: ["mcp", "realm"], value: { type: "local", command: ["realm", "mcp", "--host", "opencode"] } }`, `homes: [".config/opencode"]`, `envBase: { name: "XDG_CONFIG_HOME", sub: "opencode" }`, `binaries: ["opencode"]`. Why the V1 shape: it is read by 1.19.5 (E-O2), supported by V2 (E-O6), and a V2-only `mcp.servers` entry would be an invalid server named `servers` to a V1-only version (E-O6), which could break the whole config load; the V1 shape is the safe superset. The cost is that the docs' preferred shape is V2 (E-O5); the owner may flip the key path to `["mcp", "servers", "realm"]` later by changing one table row (OQ-24-02). No `enabled` and no `$schema` is written. A user's `opencode.jsonc` with comments is never rewritten (a JSONC `opencode.json` is `unparseable`, the Phase 21 residual), and because OpenCode merges `opencode.json` and `opencode.jsonc` in the same directory (E-O3) a missing `opencode.json` is simply created beside it; which file wins for a same-named server across the two is [INFERENCE] (the docs say project beats global, not json beats jsonc).

### D-24-04. Codex: owned `text-block` plus a conservative TOML guard

`codex`: `{ kind: "text-block", file: "config.toml", block: '[mcp_servers.realm]\ncommand = "realm"\nargs = ["mcp", "--host", "codex"]', tomlTable: ["mcp_servers", "realm"] }`, `envOverride: "CODEX_HOME"`, `binaries: ["codex"]`. The block text equals E-X1's table. New optional recipe field `tomlTable` (a path of at most 6 bare key segments, validated with `isSafeKeySegment`): before any text-block install, the text outside the markers is scanned by `src/host/toml-table.ts`, a line scanner, never a parser, and the install is `foreign-content` if the target table or any ancestor key assignment is already defined. The scanner is conservative: it reports "taken" for `[mcp_servers.realm]`, `[ mcp_servers . realm ]`, `[mcp_servers."realm"]`, `['mcp_servers'.'realm']`, `[mcp_servers.realm.env]`, `[[mcp_servers.realm]]`, a `realm = ...` or `"realm" = ...` or `realm.command = ...` line inside a `[mcp_servers]` table, `mcp_servers.realm.command = ...` or `mcp_servers = ...` at the top level, and for any top-level dotted key starting with `mcp_servers`; a header or key it cannot read is `unparseable`. A look-alike inside a multi-line string is a false positive (refused, safe). A multi-line array holding a bare `["x"]` line inside `[mcp_servers]` can hide a real definition from it (residual R-24-03; Codex itself then rejects the file and `codex mcp get realm` in the validator tier shows it, and uninstall restores the file). The block is appended at the end of the file, where a new table header is always valid TOML, so a file that ends inside another table cannot capture its keys. **Residual R-24-04 (host-side removal):** `codex mcp get realm` prints `remove: codex mcp remove realm`, and the host's remover edits the file with its own TOML editor. [INFERENCE] it takes the table and the comment lines attached to it and leaves the `# END realm host-plugin` marker behind. A lone marker makes `locateBlock` refuse (`unparseable`): `realm host status` says `unreadable`, `realm host uninstall codex` and a reinstall refuse, and the way out is to delete the two marker lines by hand, after which `realm host uninstall codex` removes the receipt as a clean no-op. The engine is deliberately not loosened to heal this (a half-present marker is exactly what an edited file looks like); plan 24-03 records what Codex 0.154.0 actually does, and the docs say "uninstall with `realm host uninstall codex`, not with `codex mcp remove realm`". The JSON hosts have no such state: their remover deletes the key and `realm host uninstall` is then a clean no-op.

### D-24-05. Kimi: `kimi` is the archived Python product; `kimi-code` gets the same recipe shape

The flag question is resolved by E-K1: `kimi` = Kimi CLI. Because Kimi CLI is archived (E-K2) and the PyPI stub is inert (E-K3), delivering `kimi` alone would leave current Moonshot users unserved while the owner's "Kimi CLI" slot proves nothing live. Phase 24 therefore ships both rows, with one shared recipe shape and one shared test suite, and changes no tier:

- `kimi`: homes `[".config/agents" (skills), ".kimi" (config)]` as today, `envOverride: "KIMI_SHARE_DIR"` (R2 moves only the config home), `recipe: { kind: "json-merge", file: "mcp.json", keyPath: ["mcpServers", "realm"], value: { command: "realm", args: ["mcp", "--host", "kimi"] } }`, no `binaries` (E-K6). The value follows the documented example (E-K4), not an observation; [INFERENCE] that `kimi mcp add --transport stdio` writes the same shape.
- `kimi-code`: homes `[".kimi-code"]`, `envOverride: "KIMI_CODE_HOME"`, the same recipe with `--host kimi-code`, no `binaries`. Tier stays `config-only`.

The owner may delete the `kimi-code` row and its two parameterised test cases without touching anything else, or promote it in place of `kimi` (OQ-24-01). The honest claim for Kimi is fixture-proven recipes whose formats come from official documentation; no live Kimi session was observed.

### D-24-06. The registered command is the bare `realm`, and `status` says whether it resolves

All four recipes register the command `realm` with args from the manifest, never an absolute path: the host resolves it on its own `PATH`, an upgrade or a package move needs no re-install, and no host-local path enters a user's config. The failure mode is observed (E-C3, E-O2: "Executable not found in $PATH") and silent in the host UI, so `realm host status <host>` adds `launch: "on-path" | "not-on-path"` for an installed `mcp-config` host (the command found as a regular executable file in an absolute directory of the `PATH` that `realm host status` itself sees, same rule as binary detection). It does not claim that the host's own `PATH` (a GUI launcher, a service) is the same, and the doctor, which reads no environment, does not report it. A malicious `realm` earlier on a user's `PATH` is a same-user control and out of the model (written down).

### D-24-07. Three evidence tiers, stated per host; `tier` is not evidence

`HostRuntimeEntry.tier` (`proven`, `config-only`) is the roadmap's classification of where end-to-end effort goes; it is not a claim about what was proven. The docs and each rehearsal state the evidence tier separately:

- **T1, offline fixture** (always runs, in CI): the recipe on a fixture host in a temporary home, against the goldens: detect, dry-run, install, no-op reinstall, drift, foreign content, hostile content, uninstall, doctor, `realm host status`.
- **T2, host validator** (gated, needs the host CLI only): in an isolated `HOME`, the recipe is installed, then the host's own command parses it and, where the command launches the registered server, a stub `realm` on `PATH` records the argv it was started with. Per host: `claude mcp get realm` (launches), `opencode mcp list` (launches), `codex mcp get realm` and `codex mcp list` (parse only, E-X2), `kimi mcp test realm` (launches; only a functional Kimi CLI). Kimi Code has no documented validator command, so T2 does not exist for `kimi-code`.
- **T3, live end to end** (gated, needs Podman 5.x and the production prerequisites, as Phase 22's Omp rehearsal): the real `realm` is on `PATH`, the host's own health check performs a real MCP initialize against `realm mcp --host <id>`, the daemon is opened for a workspace, and the per-host boot counter and presence marker show it. Available for `claude` (`claude mcp list` health-checks user servers, E-C3) and `opencode` (`opencode mcp list` shows connected servers). Not automatable for `codex` (`codex mcp list` does not start servers, E-X2, and a session needs model credentials) and not available for `kimi` (E-K3) or `kimi-code`; those gaps are written down, not skipped silently.

What can run on this machine (2026-11-17): T1 all hosts; T2 `claude` and `codex`; T2 `opencode` and `kimi` skip (no executable); T3 skips everywhere (Podman 4.9.3, needs 5.x).

### D-24-08. Live gate variables and skip reasons

Each live file skips, naming the first missing prerequisite. Variables (a test never sets them): `REALM_LIVE_CLAUDE=1`, `REALM_LIVE_CODEX=1`, `REALM_LIVE_OPENCODE=1`, `REALM_LIVE_KIMI=1` (opt-in per host, hermetic, no Podman), optional `REALM_CLAUDE_BIN`, `REALM_CODEX_BIN`, `REALM_OPENCODE_BIN`, `REALM_KIMI_BIN` (absolute path of the executable; default the name on `PATH`), and for T3 the existing `REALM_LIVE_PRODUCTION=1` set (`productionSkipReason` in `test/support/production-live.ts`). Common reasons, in order: opt-in variable not set; not Linux; executable not found; `--version` unparseable or timed out; for `kimi` the executable prints "no longer maintained" (the archived stub); the built CLI `dist/src/cli/main.js` missing; the isolated `HOME` is not under the temporary directory (a guard against a misconfigured run touching a real configuration); a Realm receipt for the host already exists in the shared state directory (the test must not replace a real install, as in Phase 22). A version newer than the one recorded here runs and is recorded, never blocks (Phase 22 D-1206).

### D-24-09. `status` distinguishes `unreadable` from `drifted` (ADPT-03)

`HostEntryStatus.state` becomes `"ok" | "drifted" | "missing" | "unreadable"`. `unreadable` is a refused read of an owned file (`HostRefusal` from `readHostFile`: symlink, not a regular file, over 1 MiB, invalid UTF-8) or content that cannot be parsed for the owned part (`ownedPartSha256` null because the file is not valid JSON). `drifted` stays "the file parses and the owned part differs or is absent". The host verdict is `installed` only when every entry is `ok`; otherwise `drifted` (no new `HostStatus` value). `HostStatusDetail.detail` appends ", N unreadable" when N > 0, so the doctor's existing drift sentence carries it. The doctor's header comment ("never reads the real home of a host") becomes "reads only the files a receipt names", which is true for `claude` (the receipt names the user's home).

### D-24-10. Allowlist and gates ownership

Exports exist only where a `src` file imports them (`resolveHomeSpecs` is imported by the adapter; the TOML scanner is imported by `recipe.ts`), so the export-usage allowlist gets no new entry. 24-04 runs `node scripts/check/export-usage-gate.mjs` and removes any STALE line, and nothing else edits `scripts/check/export-usage-allowlist.json`. No file under `adapters/` changes (the recipes are table data), so `pack-smoke` needs no new entry.

### Threat model: malicious workload, hostile config content, confinement (summary; each plan carries its STRIDE rows)

The workload is code that runs inside the sandbox plus whatever it writes into the workspace: it controls file content, symlinks and tool-call arguments. It cannot reach the user's host config directories (`~/.claude*`, `~/.codex`, `~/.config/opencode`, `~/.kimi*`, none mounted; the workspace, state and channel binds are Phase 19's exact set and are not changed). What this phase adds on the host side, and how each is held:

| Asset | Attack | Hold |
| --- | --- | --- |
| Host config file (`~/.claude.json`, `config.toml`, `opencode.json`, `mcp.json`) | Symlink or special file planted where the installer writes (a shared account, a hostile shared directory) | Engine: realpath home, lstat walk of every component, symlink refusal (`PATH_ESCAPE`), non-regular refusal, `O_NOFOLLOW` write, write only when the on-disk hash equals the planned one. New: a leaf-symlink refusal never prints a path as a home |
| Existing config content | A huge, deeply nested, BOM-prefixed, invalid-UTF-8, `__proto__`-keyed, lossy-number, duplicate-key or wrongly typed (`mcpServers` an array) file, or a TOML file with a look-alike table | Phase 21 refusals (`unparseable`, `foreign-content`), the 1 MiB cap, `isSafeKeySegment`, `hasLossyNumber`; new TOML guard refuses a second definition; each is a named test per host in 24-02 |
| Config shadowing | The workload writes a host-side project config in the workspace (`.mcp.json`, `.codex/config.toml`, `opencode.json`, `.opencode/`, `.kimi-code/mcp.json`) that names a server `realm` with a hostile command; on the next host start in that project the host launches it outside the sandbox with the user's privileges | Claude Code asks approval for project servers (E-C4), Codex honours project config for trusted projects only (E-X4), Kimi Code asks workspace trust (E-K5). | Registered command | A hostile `realm` earlier on `PATH`, or a relative `PATH` entry | Same-user control, out of the model; `hostEnvFrom` already drops relative `PATH` entries; `launch` reports resolution against absolute entries only (D-24-06) |
| Host's own remover or rewriter | A user (or the host) edits Realm's entry with the host's own tools | JSON hosts: the entry is a key, `status` reports `drifted`, uninstall is a clean no-op. | Secrets inside `~/.claude.json` | The installer reads, rewrites and logs it | Realm parses the file in memory and writes it back whole; the receipt, audit chain and `host.log` carry host id, action, paths relative to the config home, byte counts and hashes only, never a value; mode is preserved (0600) |

| Wrong-product install | Installing into a config the host does not read (Kimi CLI versus Kimi Code, `opencode.jsonc`, `XDG_CONFIG_HOME`, `~/.claude` versus `~/.claude.json`) reports success and does nothing | Table rows verified per host (E-*), `envBase`, no binary detection for `kimi`, T2 proves the host parses what was written, docs name each file |
| Residual (unchanged) | A host path that bypasses the Omp extension pipeline or the MCP tool surface is not covered by the guard (OQ-P5-02) | Not claimed as covered; docs keep saying fail-closed is a host-tool allowlist plus guard, not process containment |
