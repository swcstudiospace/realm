  <name>Task 1: The token module and the seeded refusal matrix</name>
  <files>src/capability/token.ts, test/capability/token.test.ts</files>
  <behavior>
    - Exports TOKEN_PREFIX (the text rcap1), the six-member TokenCapability union taken from the host layer's mcp-config ceiling, the TokenClaims shape (v, kid, sid, host, caps, iat, exp), the RefusalClass union (format, unknown-kid, bad-mac, bad-payload, bad-version, time-window, wrong-session, capability-not-granted), mintToken and verifyToken.
    - mintToken takes a 32-byte key and the claims and returns the wire text. It writes the payload keys in the fixed order v, kid, sid, host, caps, iat, exp, with v equal to 1 and caps sorted. It refuses (throws SCHEMA_INVALID) claims that verifyToken's schema stage would refuse, so a minted token is always schema-valid.
    - verifyToken takes the text (typed unknown), a key lookup function from kid to a 32-byte key or undefined (undefined also stands for a revoked kid), the expected session id and the needed capability (a TokenCapability, or null when the call needs none), and the current time in whole seconds. It returns an ok result carrying the claims, or a refusal carrying one RefusalClass. A refusal of class bad-version, time-window, wrong-session or capability-not-granted (the MAC and the payload schema both passed, so the host and kid are authentic) also carries that host and kid as a principal member; every earlier class carries none. It never throws and never returns the key.
    - The fixed order is: format (three dot parts, first part is rcap1, both base64url parts strictly decoded, tag exactly 32 bytes, payload parses as a JSON object with a string kid); unknown-kid; bad-mac (HMAC-SHA256 over the bytes realm-capt-v1, a zero byte and the payload bytes, compared with timingSafeEqual); bad-payload (exactly the seven keys in order, kid pattern, sid pattern, host in HOST_IDS, caps sorted unique and inside the six, iat and exp safe integers); bad-version (v is not 1); time-window (iat not more than 60 seconds ahead of now, exp not in the past, exp minus iat between 1 and 86400); wrong-session; capability-not-granted.
    - Matrix, one test row per defect, each asserting the exact class and that the valid token is accepted: valid token; tampered payload byte (bad-mac); tampered MAC byte (bad-mac); MAC truncated to 31 bytes (format); wrong key (bad-mac); unknown kid; revoked kid (lookup returns undefined); version 2 signed with the right key (bad-version); payload with an extra key (bad-payload); exp as a string (bad-payload); caps unsorted; caps with a duplicate; caps containing net.egress; host outside HOST_IDS; kid of 17 characters; sid with a slash; exp in the past; iat 120 seconds ahead; lifetime 86401 seconds; lifetime 0; session mismatch; capability outside the set; no token (undefined, null, a number, an object); a string that is not a token; padded base64url MAC; payload part with a non-canonical final character; a fourth dot part; prefix rcap2; uppercase prefix.
    - Ordering rows: tampered MAC before wrong session gives bad-mac; unknown kid before MAC gives unknown-kid; bad-version before time-window; time-window before session; session before capability. Each row signs with the right key so only the intended defect and the earlier-stage defect are present.
    - Property (fast-check): for a valid token, every single-character substitution at every position with a different base64url character, and every single-character deletion, is refused; the property never sees an accepted result.
    - Round trip: every host id times a sample of capability subsets (empty, one, all six) mints and verifies for its own session; the empty set is accepted for a call that needs no capability and refused for any other.
    - A failed verify result never contains the key, the token text or the payload text (assert on the JSON of the result).
  </behavior>

<threat_model>
## Trust Boundaries

| Boundary | Risk |
| --- | --- |
| Token text to the verifier | A forged, tampered, replayed or malformed token is admitted |
| Key file to the daemon | A same-user reader or a symlink swap exposes or substitutes the key |
| Policy file to the schema | A malformed profile widens or breaks the policy |
| Token text to any sink | The token is written to a log, audit line or error |

## STRIDE Threat Register

| ID | Category | Threat | Severity | Disposition | Mitigation |
| --- | --- | --- | --- | --- | --- |
| T-32-01 | Spoofing | A forged or modified token is accepted | high | mitigate | HMAC-SHA256 with domain separation, timingSafeEqual after a length check, strict base64url, exact-key payload schema; the 26-row matrix and the single-substitution property prove every mutation refuses |
| T-32-02 | Tampering | Attacker swaps the payload for a wider capability set | high | mitigate | The MAC covers the payload bytes; capabilities are sorted and unique inside the signed payload; bad-mac precedes every other payload stage |
| T-32-03 | Information disclosure | The verifier leaks which stage failed | medium | mitigate | Classes are internal; later plans put none on the wire (the wire matrix of plan 32-02 proves exactly POLICY_DENIED) |
| T-32-04 | Information disclosure | Key or token text appears in an error, inspect output or log | high | mitigate | Errors are catalogue errors with no payload; tests assert no key text in any error, toString, JSON or inspect output; the redaction pattern covers the token shape in every position |
| T-32-05 | Tampering | The key file is replaced through a symlink or has loose modes or another owner | high | mitigate | lstat guards, mode and owner checks, a size cap, atomic replace through the pinned-directory helper; every failure is POLICY_DENIED |
| T-32-06 | Denial of service | A very long input to the verifier or the redactor stalls the daemon | medium | mitigate | The token text is length-bounded by the caller (512 characters, plan 32-02) and the verifier decodes only after the format stage; the redaction pattern is linear and tested at 100000 characters |
| T-32-07 | Repudiation | Rotation leaves no record of what was valid | low | accept | The keyring file records kid, creation and retirement times; the audit trail of attaches is plan 32-02; the key itself is never recorded |
| T-32-08 | Elevation of privilege | A policy profile outside the catalogue widens a host | medium | mitigate | The schema enums the six capabilities and 19 hosts; tests pin them to the host layer so they cannot drift |
| T-32-09 | Elevation of privilege | A same-uid reader reads the key file and mints any token | high | accept | Stated limit (32-CONTEXT, What this phase does NOT give): there is no defence against a same-uid reader; the file is outside every default sandbox mount |

Accepted residuals: a same-user process that can read keys.json mints any token; the clock is the machine clock; a token is a bearer credential for its lifetime.
</threat_model>
