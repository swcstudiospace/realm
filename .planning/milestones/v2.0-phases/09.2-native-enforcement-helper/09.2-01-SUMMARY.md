# Phase 9.2 summary: native enforcement helper (plan 09.2-01)

Status: partial. The helper, its native tests, the probe, SECCOMP.md, and the image definition are built and pass their gates on this host. The image build is phase 9.3 (HC-08). The in-container probe is phase 9.6. The security gate returned PASS WITH CONDITIONS C1 to C6, and those conditions are owned by phases 9.3 and 9.6.

## Delivered and verified on this host

- `sandbox/realm-helper`: C source with a static build under `-std=gnu11 -Wall -Wextra -Werror`. `make clean all check probe` exits 0 from clean.
- Native tests: three binaries pass. `test_policy` checks the ABI gate, path and root rules, PROG rules, argument parsing, the environment filter, exit codes, and the seccomp program. The filter is checked with a small classic-BPF interpreter on synthetic syscall data. `test_idle` checks the reap seam and SIGTERM. `test_probe` checks the decision logic of all eleven probe checks with fake results.
- Live run of the helper on this host (kernel 6.8, Landlock ABI 4, root start, so the capability drop is what removes capabilities):
  - The workload shows `CapInh`, `CapPrm`, `CapEff`, `CapBnd`, and `CapAmb` all zero, `NoNewPrivs` 1, and `Seccomp` 2.
  - A write inside the workspace succeeds. A write outside the workspace is refused with EACCES. A redirect to the null device succeeds.
  - A user namespace cannot be created from the workload.
  - Exit codes: 126 for a PROG that the ruleset does not allow to execute, 127 for a missing PROG, 2 for a usage error, and 2 for a scratch path under the temporary directory.
- Denylist: 57 entries on x86_64 (54 EPERM, `clone` with a CLONE_NEW* flag filter, `clone3` as ENOSYS, `personality` restricted to 0x0 and 0xffffffff). It has 52 entries on aarch64. The seccomp program has 74 instructions on x86_64 and 68 on aarch64. `memfd_create` and `fanotify_init` are deliberately absent, with reasons in SECCOMP.md.
- The helper binary is static. Its SHA-256 on this host's build is `b8b50242…`. This is not the image's digest: the image's toolchain is pinned in 9.3, and the reproducible digest is recorded there.
- `sandbox/Dockerfile`: builder on the gcc 13.3.0 bookworm image pinned by digest (`1d71f0f3…`), with no apt. The builder computes a sorted-manifest source digest and fails when it differs from `SOURCE_SHA256`. It runs `make clean all check probe`. The runtime stage is the node bookworm-slim image pinned by digest (`2dd9a4f7…`). That digest was confirmed on this host as Debian 12 with glibc 2.36 and no gcc. The runtime creates the sandbox user (uid and gid 1001), sets `USER sandbox`, and fails closed when `HELPER_SHA256` or `SOURCE_SHA256` is empty.
- SECCOMP.md: all 57 rows with reasons, architecture differences, exit codes, residual risks, and the conditions section.

## Security gate (A10, read-only)

- First review: CHANGES REQUIRED. Six MAJOR and two MINOR findings: the clone namespace flags, the new mount API, io_uring, capability drop and non-root user, the source digest, the unpinned toolchain, the environment, and the root rules. All MAJOR findings are closed in code.
- Re-review: PASS WITH CONDITIONS. Two minor fixes followed (`fspick` and `quotactl_fd` added; inheritable set cleared). Both are built and tested here.
- Conditions:
  - C1 (9.3): `/workspace` is mounted noexec. Landlock EXECUTE is enforced only at `execve`. This also gates the probe's LOADER_WORKSPACE_REFUSED check.
  - C2 (9.3): the runner lies under the usr tree or the state path. Landlock denies execution elsewhere, and the helper checks only the syntax of PROG.
  - C3 (9.6): the probe runs in the built image.
  - C4 (9.3, image only): `useradd` and `groupadd` work on the node base; the clone3 ENOSYS fallback works in glibc 2.36; libuv falls back from io_uring under Node 24.
  - C5 (9.3): the state root holds no secret readable by the sandbox user. The state root gets read and execute, so the gateway key material must not live there.
  - C6 (9.3): the workload runs without a tty (TIOCSTI is not denied), and the container uses hidepid=2 (`/proc/<pid>/mem` is readable under the `/proc` read rule).
- Denylist for v2.0: acceptable as one layer under C1 to C6. It is not the primary boundary. Landlock, the capability drop, and no_new_privs carry that. An allowlist is the v2.x target.

## Deviations from the plan, all deliberate

- The runtime base is bookworm-slim, not the alpine base in the plan's T5. D-020 supersedes it, because the sidecar needs glibc.
- The denylist has 57 entries on x86_64, not 29. The security gate's must-add set accounts for the difference.
- The workspace has read and write but no execute. The plan's wording permits this, and the gate agreed.
- The probe has eleven checks, not five. The additional checks came from the security gate.
- The helper also refuses a scratch path under the temporary directory, and it refuses a writable root under the usr, etc, proc, or dev trees. The gate required both.
- The helper grants write on the null device only, so ordinary redirects work. The rest of the device tree stays read and execute.

## Not verified here

- aarch64: the helper was not compiled for aarch64. No cross toolchain or aarch64 headers are installed on this host. The architecture guards compile out the x86-only entries.
- The image build and the image record digests (phase 9.3, HC-08).
- The in-container probe (phase 9.6), and the image-only checks listed as C4.
