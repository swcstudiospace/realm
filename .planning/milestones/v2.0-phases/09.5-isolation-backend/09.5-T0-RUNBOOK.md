# Phase 9.5 T0 runbook: supervisor placement evidence

Status: prepared in wave 1. Nothing in this file has been run. Every step below is a LEAD STEP, run by the lead on the host.
Wave 1 did not create a sandbox, start the backend, or change the realm gateway or driver units.

This runbook collects evidence only. It names processes and records observations. It does not decide PD-15 (supervisor
placement, RT-03) or PD-10 (enforcement authority). The owner decides both from the VERIFICATION record this run produces.
Names only: record process names, PIDs and container identifiers. Do not record host paths.

## What the lead runs

- The realm gateway unit (`realm-openshell-gateway.service`) and the compute driver unit (`realm-compute-driver.service`),
  both under the realm account, are already running. The lead leaves them as they are for this run.
- The isolation backend is started from the repository build. Wave 1 provides `startIsolationBackend` in the built
  backend module. It has no launcher unit yet. The lead supplies the launch, and the verification keys it provisions come
  from the driver's launch authentication. No key is read from the repository or from a file the backend writes.
- The OpenShell supervisor binary (`openshell-sandbox`, from the v0.1.5 source tree) is placed where the realm account can
  execute it. The lead chooses the placement; no host path is written into the repository.

## Attach flow the stub workload must produce

LEAD STEP. The stub workload is `realm-helper idle` with no agent started. Drive the RPC order below through the backend
and record the status code of every call. The order is the spike order (G3). No call before `StartAgent` may run a
workload.

1. `Describe` on the backend endpoint.
2. `DiscoverPolicy` on its own stream, before `Attach`.
3. `Attach` with the supervisor bearer. The backend checks the bearer against the provisioned keys.
4. `Confirm`. The process list of the container must contain only `realm-helper idle`.
5. `OpenMediation`, on the mediation stream.
6. `StartAgent`. This is the first point at which a workload may run.
7. `AttachProcess`, then `Wait`, which reports the exit status after all output is sent.
8. `UpdateProviderEnvironment`, twice.

Note: this wave serves `Describe` only. Every other RPC returns `UNIMPLEMENTED` until its task is built. A live run of this
flow therefore needs the T3 and T4 work. Until then, the lead records the `UNIMPLEMENTED` status of each call as the
observed result, and the steps above as not run.
