## Constraints

- Every RPC is served on the authenticated endpoint the gateway configured. The backend trusts only the verification keys the driver provisioned (from the gateway's launch authentication). It never reads keys from the repository or from configuration files it writes itself.
- Frames: control messages at most 1 MiB; I/O payloads at most 64 KiB (`sandbox_protocol.proto` header). Larger writes are chunked by the server and reassembled, with the same byte stream on read-back.
- No workload code runs before `StartAgent`. At `Confirm`, the only process in the container is `realm-helper idle` (spike G3).
- Exec and forwarding are allowed only in the `Running` state (`sandbox_protocol.proto` header).
- Unimplemented RPCs return the gRPC `UNIMPLEMENTED` status and do not advance the lifecycle state (`isolation_backend.proto` header).
- The protos are vendored in this phase's first wave with the same provenance rules as phase 9.4.

## Tasks and waves

### Wave 0 (blocking evidence, owner decision after it)

- T0, supervisor placement evidence (PD-15, PD-10). With the realm gateway (9.1) and the driver (9.4) running, and the backend from task T1 running in its first form, run one sandbox with a stub workload through `Attach`. Record, in this phase's VERIFICATION file with names only (no host paths): the process tree on the host, the process tree in the container, which process connects to the backend socket, and where the supervisor's network traffic leaves. Also record whether the supervisor applies any Landlock or seccomp policy of its own to the workload. The owner then decides PD-15 (RT-03) and PD-10 (enforcement authority). The rest of this phase waits on that decision for the enforcement tasks only (T5). The upstream example in the OpenShell source tree runs its backend natively on the host; that fact is recorded but does not settle RT-03 for a container.

### Wave 1 (sequential: the backend's shape comes first)

- T1, backend skeleton and vendored protos. Vendor `isolation_backend.proto`, `sandbox_protocol.proto`, and their imports into `src/runtime/driver/proto/` (update `PROVENANCE.md` with digests). Add `src/runtime/driver/isolation/backend.ts` with the gRPC server on the configured endpoint, and the TLS or socket policy from the gateway configuration (the endpoint kind is `unix` in the gateway entry; it is restricted to the realm account's socket directory).
- T2, boundary handles. Add `src/runtime/driver/isolation/boundary.ts`. `OpenBoundary` binds the provisioned resource to the authenticated sandbox and generation. Reopening the same session and generation returns the same handle. A different resource fails. Driver deletion invalidates every handle (`DeleteSandbox` calls `invalidateAll(sandboxName)`).

### Wave 2 (parallel after T1 and T2: disjoint files)

- T3, lifecycle over the sandbox protocol. Add `src/runtime/driver/isolation/protocol.ts`: `DiscoverPolicy` on its own stream before `Attach`; `Attach` (verifies the supervisor bearer against the provisioned keys); `Confirm` (checks the container's process list contains only the idle init); `StartAgent` (the first point at which a workload may run); `AttachProcess`, `Wait`, `Signal`, `Terminate`, `TerminateBoundary`, `Resize`, `UpdateProviderEnvironment`. The state machine is `Attached`, `Confirmed`, `Running`, and `Terminated`, and a call in the wrong state fails with a typed error.
- T4, mediation. Add `src/runtime/driver/isolation/mediation.ts`: `OpenMediation`, then correlated DNS queries and responses on `Mediate`. Allowed names and ports come from the validated egress list (`validateEgressAllow`, `src/runtime/egress.ts`). `AAAA` queries are refused (IPv6 off). Connections go through `LoopbackConnect` and `AcceptNetwork` as decided in PD-12.
- T5, workload exec (PD-11). Add `src/runtime/driver/isolation/workload.ts`. Start the workload through the libpod REST exec API (PD-11 default), through the socket already used by the driver, with the helper's `run` entry (`realm-helper run -- PROG`). Stream stdout and stderr as `AttachProcess` frames; report the exit status from `Wait` after all output has been sent. If PD-10 chooses another enforcement authority, this task changes to match and is re-planned first.
- T6, RPC surface. Add the `IsolationBackend` handlers (`Describe`, `OpenBoundary`, and `SuspendBoundary` and `ResumeBoundary` per PD-09, default `UNIMPLEMENTED`). `Describe` advertises only capabilities that are implemented.

### Wave 3 (after wave 2)

- T7, frames and I/O. Add `src/runtime/driver/isolation/frames.ts`: framing with the limits above, and a reassembly test that writes 16 MiB to stdin and reads it back byte for byte.
- T8, tests. Add `test/runtime/isolation-conformance.test.ts`: a fake supervisor replays the spike's RPC order (`Describe`, `OpenBoundary`, `DiscoverPolicy`, `Describe`, `OpenBoundary`, `Attach`, `Confirm`, `OpenMediation`, `StartAgent`, `AttachProcess`, `Wait`, `UpdateProviderEnvironment` twice) against the fake libpod, and asserts zero exec calls before `StartAgent`. Add tests for: a 64 KiB plus one byte I/O frame is rejected; a control frame over 1 MiB is rejected; a DNS query for a non-allowlisted name is refused; an `AAAA` query is refused; a stale handle after delete fails.
- T9, gateway registration. Add the isolation backend section to `src/runtime/gateway-config.ts`: `[[openshell.supervisor.isolation_backends]]` with a unique name and a `unix` endpoint with an absolute socket path. Add a test that rejects a relative path and a duplicate name.

## Acceptance

1. Given T0 has run, When the owner reads the VERIFICATION evidence, Then PD-15 and PD-10 are decided and recorded (PRD-SUP-01). RT-03 is not amended without owner approval.
2. Given the fake supervisor replays the spike order, Then no exec call is made before `StartAgent`, and exec is refused in every state other than `Running` (PRD-ISO-03).
3. Given a 16 MiB write to stdin, When it is read back, Then the bytes are identical (PRD-ISO-04).
4. Given a 64 KiB plus one byte I/O frame, Then it is rejected; given a control frame of 1 MiB plus one byte, Then it is rejected (PRD-ISO-04).
5. Given a DNS query for a name not in the allowlist, Then it is refused and no connection is opened (PRD-ISO-05).
6. Given an `AAAA` query, Then it is refused (PRD-ISO-05, IPv6 off).
7. Given `DeleteSandbox` ran, When a previously opened handle is used, Then the call fails and no state changes (PRD-ISO-06).
8. Given `Describe`, Then it advertises only implemented capabilities, and `SuspendBoundary` returns `UNIMPLEMENTED` without changing state under PD-09 option (a) (PRD-ISO-01).
9. Given the gateway configuration, Then the backend section is rendered with an absolute unix socket and a unique name, and invalid input throws (PRD-GW-04).
