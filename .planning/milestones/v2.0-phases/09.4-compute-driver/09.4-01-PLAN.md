## Constraints

- The driver is a separate process (PD-05 default): entry point `src/runtime/driver/main.ts`, run by the user unit in HC-04. The daemon `src/daemon/main.ts` is not changed by this phase.
- `process.env` is read only in `src/runtime/driver/main.ts`, the entry edge.
- Errors use the existing catalogue (`src/core/errors.ts`). A new code is an owner decision (D-018). gRPC status codes are mapped in one table, `grpc-status.ts`, and tested.
- The admission acknowledgement is captured from the pinned OpenShell 0.1.5 build (the default policy's acknowledgement string) and stored as a constant with a test that pins it. It is not derived by hand in TypeScript. The gateway's expected policy comes from `[openshell.drivers.<name>]` in its configuration.
- The protos are EXPERIMENTAL upstream. They are vendored at a recorded revision with per-file SHA-256 digests, and the protos directory is listed in `package.json` `files`.

## Tasks and waves

### Wave 1 (sequential: dependency and call-site evidence first)

- T1, PD-07 check and pin. Check the candidate packages (`@grpc/grpc-js`, `@grpc/proto-loader`) for licence (Apache-2.0 expected; verify from the package file), maintenance (registry time and versions), and advisories (`npm audit --omit=dev`). Then `npm install --save-exact` each pin. Record the licence, maintainer count, last-modified date, and audit result in the SUMMARY. If a check fails, stop and return to the owner. Rollback: `npm uninstall`.
- T2, call-site evidence (PD-08). Run the realm gateway against the driver (from T5 once it exists, in a first pass where the driver logs each RPC). Drive the flows the owner needs: create, delete, list, get, watch, and the CLI's stop and start if the CLI offers them. Record each RPC the gateway calls, with the flow that caused it, in the SUMMARY. The PD-08 decision cannot be made without this list.
- T3, vendored protos. Copy `compute_driver.proto` (package `openshell.compute.v1`) and every file it imports: `extension.proto`, `options.proto`, `sandbox.proto`, and any file those import in turn. Its Google well-known imports (`struct`, `timestamp`) come from the loader package, not the vendored tree; confirm at check time. Copy the files into `src/runtime/driver/proto/`. The isolation and sandbox-protocol files are vendored in phase 9.5. Add `src/runtime/driver/proto/PROVENANCE.md` with the upstream revision (the spike's clone commit, `c4688aa`, for OpenShell 0.1.5) and a SHA-256 per file. Check: a script-free test loads the protos with the pinned loader and checks the service name `openshell.compute.v1.ComputeDriver` (confirm the exact package name from the file).
- T4, package files. Add `src/runtime/driver/proto` to `files` in `package.json`. Check: `npm run check:pack` (phase gate) lists the protos and the provenance file.

### Wave 2 (parallel: disjoint files)

- T5, service implementation. Add `src/runtime/driver/compute-driver.ts`. Implement:
  - `GetCapabilities`: driver name (the realm name, one value in config), resource admission acknowledgement (the constant from `admission.ts`), protocol extension capabilities without `openshell.compute.isolation-backend` until phase 9.5 is merged.
  - `ValidateSandboxCreate` and `CreateSandbox`: refuse, before any libpod call, any request whose image digest differs from the configured digest, whose CPU and memory differ from `SANDBOX_CPUS` and `SANDBOX_MEMORY`, whose network is not `none`, whose mounts are not exactly the two allowed binds, whose capabilities are not empty, or whose workload argv is empty. On accept, call `lifecycle.create` (phase 9.3).
  - `GetSandbox`, `ListSandboxes`, `WatchSandboxes`: from the realm session records and the labelled containers.
  - `DeleteSandbox`: `lifecycle.delete`.
  - `AuthenticateSandbox`, `EnsureWorkspace`, `DeleteWorkspace`: implemented to the protos' contract; the workspace path must be under the configured workspace root.
  - `StopSandbox`, `StartSandbox`: per PD-08 (default: refuse with the gateway's precondition status).
  Check: unit tests (T7).
- T6, socket server. Add `src/runtime/driver/server.ts`: bind a Unix socket. Create the parent directory with mode 0700 and the socket with mode 0600 (umask set before bind). Refuse to start if the path exists and is not a socket owned by the realm account; remove a stale socket only when it is owned by the account and nothing listens on it. Check: unit tests for both modes and the refusal cases.
- T7, status mapping. Add `src/runtime/driver/grpc-status.ts`: one table from catalogue codes to gRPC status codes, with a test for every catalogue code the driver can return.
- T8, admission constant. Add `src/runtime/driver/admission.ts` with the captured acknowledgement string and a test that pins its exact value.

### Wave 3 (after wave 2)

- T9, entry and gateway. Add `src/runtime/driver/main.ts`: read configuration at this edge, call `startupSweep`, start the server, and log the driver name and the socket path. Start the realm gateway (phase 9.1 HC-05) with the driver's name in `compute_driver`, then check the gateway log line that the driver connected under the production TLS and JWT configuration (PR-02).
- T10, docs. Update `docs/integration/openshell.md` with the driver's RPC table and the PD-08 result.

## Acceptance

1. Given the driver running under HC-04 and the gateway's production configuration, When the gateway starts, Then its log shows the compute driver connected with the realm driver's name (PRD-GW-03).
2. Given `GetCapabilities` is called twice, Then the admission acknowledgement is the same constant both times and equals the value pinned in `admission.ts` (PRD-GW-03).
3. Given a `CreateSandbox` whose image digest is not the configured digest, When the RPC runs, Then it returns `INVALID_ARGUMENT` and the fake libpod records zero create calls (PRD-DRV-02).
4. Given the socket is bound, Then its parent directory mode is 0700 and the socket mode is 0600 (PRD-DRV-01).
5. Given `StopSandbox` and `StartSandbox`, Then each returns the status decided in PD-08 and the sandbox state does not change (PRD-DRV-03).
6. Given the packed artifact, Then it contains the vendored protos and `PROVENANCE.md` (PRD-LIB-01, PR-14).
7. Given `package.json`, Then every new dependency is an exact pin (no `^` or `~`) and the SUMMARY records the T1 checks (PRD-LIB-01).
8. Given the T2 call-site list, Then every RPC the gateway calls on the observed flows has a handler (PRD-DRV-01).
