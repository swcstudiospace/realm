## Proposed workflow change (for the owner's review; an agent does not apply it)

Why the existing gates cannot enforce: the `verify` job checks out one commit with no `fetch-depth` (for a pull request, the merge commit), so the base and head commits are absent; the pull request event runs on opened, synchronize and reopened only, so editing a title or ticking the template line starts nothing; and the job's checkout has `persist-credentials: false`. `npm run check:gates` and `npm run check:docs` therefore cannot run the guard with a range. Both needs (history, the edited activity type) are under `.github/workflows/**`.

**Option A (recommended): a new workflow file `.github/workflows/breaking-change-guard.yml`.** A title or body edit re-runs only this small job, not the 30-minute Node matrix, the site build and the audit.

```yaml
name: Breaking change guard

on:
  pull_request:
    branches:
      - main
    types:
      - opened
      - synchronize
      - reopened
      - edited

permissions:
  contents: read

concurrency:
  group: breaking-change-guard-${{ github.event.pull_request.number }}
  cancel-in-progress: true

jobs:
  guard:
    name: Breaking change marker
    # Fork pull requests are skipped, as in ci.yml: this repository's own code is the only code that runs.
    if: github.event.pull_request.head.repo.full_name == github.repository
    runs-on: ubuntu-24.04
    timeout-minutes: 5
    permissions:
      contents: read
    steps:
      - name: Checkout source with history
        uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
        with:
          fetch-depth: 0
          persist-credentials: false

      - name: Set up Node.js 22.x
        uses: actions/setup-node@949feb2413d6458794dcd2491c4babbbce0c15c1 # v7.1.0
        with:
          node-version: 22.x

      - name: Check the breaking-change marker
        run: |
          set -euo pipefail
          node scripts/check/breaking-change-guard.mjs --enforce
```

The step passes nothing from the event into the shell: the script reads the title, the body and the two commit ids from the event file named by `GITHUB_EVENT_PATH` (the event name is `pull_request`). The merge method is not known in CI, so the landing is `unknown` and the strict rule applies (a marked title and a marked commit when the change is breaking). The new job is not part of the `ci.yml` jobs that the build job waits for, and `main` has no branch protection, so the red check is read by the ship flow, as the Greptile score is; AGENTS.md step 3 names it when the owner applies this.

**Option B: a step and an activity type in `ci.yml`.** Change the trigger to `pull_request` with `branches: [main]` and `types: [opened, synchronize, reopened, edited]`; set the `verify` checkout to `fetch-depth: 0` (the same value for every event is the simplest form); add after Check docs a step `Breaking change marker` with `if: github.event_name == 'pull_request' && matrix.node-version == '22.x'` whose run is `set -euo pipefail` and `node scripts/check/breaking-change-guard.mjs --enforce`. Cost: every title or body edit re-runs the whole workflow (verify on two Node versions, site, audit), and `concurrency` cancels in-flight pull request runs. Benefit: the guard is part of "ci.yml must be green" and the build job's `needs` chain, with no new file.

**Option C: no workflow change.** The guard stays report-only in CI. The ship flow (user configuration outside this repository) runs `node scripts/check/breaking-change-guard.mjs --enforce --base BASE --head HEAD --title TITLE --merge-method METHOD` before the merge, where BASE and HEAD are the pull request's base and head commits, TITLE the title that will be the squash subject and METHOD the configured merge method; this works with any option and is the only form that knows the merge method.

Risk common to A and B: `base.sha` of the event is the base branch tip at the event time, and the merge-ref checkout may be built against an older tip, so the base commit can be missing from the checkout. The guard then reports `range-unavailable`, which fails under `--enforce` (fail closed), and a re-run after the merge ref refreshes fixes it. If this proves frequent the owner may add `git fetch --no-tags origin BASE_SHA` as a step; that is a further workflow change and is not proposed now.
