### D-43-04. What each tier is for the two hosts

### D-43-05. Credentials (hard rule)

No operator credential, token or API key is used, read, forwarded or written. Kimi Code needs a key variable to define a provider at all (E-43-07), so the session drive sets `KIMI_MODEL_API_KEY` to one fixed literal that is not a secret (a constant in `test/support/host-live-kimi.ts`, for example `rehearsal-key-not-a-secret`), `KIMI_MODEL_NAME` to a fixed model alias, `KIMI_MODEL_PROVIDER_TYPE` to `openai` and `KIMI_MODEL_BASE_URL` to the refusing provider's loopback URL. The refusing provider records, for each request, whether an Authorization header was present and whether it equals the literal (booleans, never the header); a request that carries any other credential fails the run. The environment of the host process is built from an allowlist: any `KIMI_*`, `MOONSHOT_*`, `*_API_KEY` or `*_TOKEN` name of the operator's shell is dropped, never forwarded (the window preflight also checks the shell holds none). Because Kimi Code forwards its whole environment to a stdio server (E-43-08), the literal reaches `realm mcp`; that is harmless by construction and is recorded.

### D-43-06. The legacy CLI's reduced environment (finding GAP-43-01)

Observation E-43-09 says the legacy CLI forwards only `HOME`, `PATH` (and the shell's `PWD`) to a stdio server unless the entry has an `env` object, and the recipe writes none; the production scenario needs `XDG_CONFIG_HOME` (the scenario's realm config), `XDG_RUNTIME_DIR` and `REALM_DRIVER_SOCKET` to reach the production stack, as Codex needed `env_vars` (GAP-31-01). Decision: the recipe stays as it is (OQ-43-03 asks the owner whether a recipe may write an `env` block). The production command drive for `kimi` restores exactly those three names inside the wire recorder (new `restoreEnv` option of `writeWireRecorder`: names absent from the forwarded environment are added for the target only, and the recorder logs the restored NAMES, never values), so the run proves the host side (the host started the registered command, sent the handshake and listed the tools against the production stack) and states honestly that stack reachability for a real user of the legacy CLI is not shown (a new gap row, GAP-43-01, class unverified-behavior). The validator tier pins the forwarded set on the version run (names only, from the fake server's start line). A different observation on the day (more names forwarded) is recorded and the gap row says so.

### D-43-07. Containment of the third-party CLIs' own network use

Documented switches are set in every tier: `KIMI_DISABLE_TELEMETRY=1`, `KIMI_CODE_NO_AUTO_UPDATE=1` and `KIMI_CLI_NO_AUTO_UPDATE=1`. The two validator tiers (no Podman, no stack) also set `HTTP_PROXY`, `HTTPS_PROXY` and `ALL_PROXY` to a closed loopback port and `NO_PROXY` to the loopback names, so a call to a non-loopback host fails at once instead of leaving the machine (the refusing provider is loopback and bypasses the proxy). The production tiers do not set a dead proxy (the realm, the daemon and the gateway share the environment, and a proxy setting could change them). Accepted residual R-43-01: a Kimi CLI may contact a Moonshot endpoint in a production run despite the switches; the run does not measure that, and the docs say so.

### D-43-08. The window (blocking-human)

One window, run by a person as the `realmlive` account under the shared live lock (the mechanism the Phase 14, 17, 18, 31 and 36 windows used), on the production stack, serialized with any other v6.0 window (Phases 38, 39 and 41 also use it). Order: the two validator tiers first (no stack), then the production tiers one at a time, each cold: nothing starts the daemon or a sandbox before the host does, each uses a new project directory under the pinned workspace root, no warm-up, and before each production step the stack shows no realm daemon, 0 containers and 0 sandboxes. The tests never set a gate variable; the person sets them for the command. Evidence (versions, counts, hashes, millisecond marks and results, never paths, environment values or header values) is kept outside the repository. A failed step is reported with its catalogue code and the plan that owns the behaviour, not retried silently, and nothing is patched in the window. No agent runs the production tests. If the window cannot open, the install and the code of Plans 43-01 and 43-02 Task 1 stand, every unrun tier is recorded as a named blocker (D-43-09), and the phase closes on those blockers.

### D-43-09. Outcomes and named blockers (KIMI-02)

Each of the four (host, tier) results is one of: `passed` (dated, versioned), `failed` (a run happened and an assertion failed: the registry T3 is a gap whose note starts `rehearsal failed`, the page row is `failed`, a gap row names the finding), or `blocked` with one named blocker and its evidence (the registry T3 stays a gap, the page row stays `gap`, and the row says what lifts it). The blocker names:
- **B-43-01, install blocked.** The CLI cannot be installed (registry unreachable, integrity mismatch, Node older than 22.19.0, Python older than 3.12, no free space). Evidence: the exact error, the versions and the free space.
- **B-43-02, runtime blocked.** The installed CLI does not run as the `realmlive` account or does not return (`--version` fails, a command does not return within its bound; the existing `did not return` sentence).
- **B-43-03, no non-interactive drive.** Kimi Code starts no MCP server before it fails the model call, or needs a credential the rehearsal may not use, so no session can show the handshake. Evidence: the stub or recorder log of the validator session.
- **B-43-04, archived product regression.** The legacy 1.51.0 does not return from `kimi mcp test` against a fake server or answers no handshake (the product is archived, so no fix is expected). Evidence: the observation.
- **B-43-05, window not opened.** The owner or person did not open the window; the production tiers are recorded as not run, the validator tiers may have run by themselves (they need no stack).

The fallback the owner asked for is B-43-01 and B-43-02 for an unusable CLI and B-43-03 for the absence of a non-interactive MCP validator: the row records the named blocker with its evidence and nothing stronger.
