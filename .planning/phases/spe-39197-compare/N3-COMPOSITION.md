Issue: SPE-39197 `n3-compare-compositions-and-plugin-mechanisms` (node n3 of SPE-39196 decomposition) — https://linear.app/swcstudio/issue/SPE-39197/n3-compare-compositions-and-plugin-mechanisms. Marks: FACT = observed in file/probe; INFERENCE = scored judgement drawn from facts.

## 0. What exists today (baseline FACT)

- Leader is the daemon: single control socket, `ensureDaemon` probes and spawns the daemon at most once per attach (`src/daemon/ensure.ts`), `spawnDaemon` injected because `src/host` may not import `child_process` (`src/host/attach.ts:1-3`).
- Session execution is composed in `src/runtime/session-execution.ts` (D-39/D-67): libpod info for rootless, policy document written before create, label-idempotent OpenShell create, inspect-verify before anything is returned as running. Without an AgentOS supervisor every runtime-touching path fails closed with `AGENTOS_NOT_CONFIGURED` and creates no container (`session-execution.ts:11-14, 460-464`).
- Naming: `realmSandboxName(sessionId) = "realm-" + sessionId` (`src/runtime/openshell.ts:55-57`); gateway caps names at 19 chars (`GATEWAY_SANDBOX_NAME_MAX_LENGTH`, observed live rejection `47 > 19`, `openshell.ts:37-40`). Session id is the idempotency key (`session-execution.ts:191`).
- One container per session, never reused across workspaces: `LifecycleController` compares the stored record's `containerId`/`workspaceRoot` before create and refuses a foreign workspace with `POLICY_DENIED` (S-02) (`src/lifecycle/controller.ts:228-237`). Hydration never creates; a live create/start is a snapshot no-op.
- OpenShell create is warm-idempotent by label: look up the labelled container first and return it without running anything; poll every 250 ms otherwise; ambiguous (>1) match is refused at once with `OPENSHELL_LABEL_AMBIGUOUS`, never retried (`openshell.ts:281-288`).
- AgentOS supervision (`src/runtime/agentos.ts`): initial start retries 500 ms→8000 ms capped jitter, 5th consecutive failure holds with `AGENTOS_CRASH_LOOP`; once active the supervisor never restarts a runner — a runner exit or failed probe holds the session in error. Recovery is `realm down` + `realm up` (or retry command) or explicit `start()` reusing the stored container.
- Host boot (`src/host/boot.ts` + `src/host/boot-driver.ts` + `src/host/attach.ts`): `resolveBoot(manifest)` carries defaults (`enabled:true`, `startupBudgetMs:200_000`, `guardStatusBudgetMs:5_000`, `statusPollMs:2_000`, `reattach{enabled:false,retryCap:8,base:1_000,cap:60_000}`). One attempt = attach + one workspace-validated status readback under the startup budget. Retry only for `attachFailureDisposition == retryable` (`REALM_NOT_ACTIVE`, `TOOL_TIMEOUT`, `STARTUP_BUDGET_EXCEEDED`, `DAEMON_START_TIMEOUT`); every other failure is terminal. Shutdown closes the client and never sends `down` — the sandbox outlives every host (`boot-driver.ts:18`, `stdio-host.ts:18-20`).
- Stdio exit semantics (`src/cli/stdio-host.ts` + `src/cli/stdio-settle.ts`): MCP exposes immediately, serves `tools/list` at once, refuses every tool call with retryable `REALM_NOT_ACTIVE` until a verified client is adopted; ACP exposes only after settle, and a non-ready boot exits 1 before any frame. `exitCodeAfterClose` is 1 only when no client was ever adopted and the outcome is `failed`; stdout carries protocol frames only, diagnostics go to stderr. Teardown is idempotent on stdin end / `SIGTERM` / `SIGINT` / `SIGHUP` / any other exit; observer flush bound 1000 ms.
- Host integration kinds: `extension` (Omp only, in-process plugin `src/omp/plugin.ts`, boot driver factory is `null` for it) vs `mcp-config` (all other 21 hosts share `DRIVER_FACTORY` from `resolveBoot`) (`src/host/types.ts:40`, `src/host/boot-driver.ts:590-597`).
- Installer receipts: 5 recipe kinds (`json-merge`, `text-block`, `toml-table`, `yaml-map`, `bundle-copy`), pure planner `src/host/recipe.ts` + apply in `src/host/install.ts`; Realm changes only what a receipt entry owns, refuses foreign/drifted/symlink/unparseable content, resume is `done | apply | conflict` by hash comparison of the owned part. Status reports per-entry `ok | drifted | missing | unreadable`, extension shim target `present | missing | unreadable`, and launch resolution `on-path | not-on-path` (`src/host/adapter.ts:90-100`).
- Omp extension shim: install-time token `@realm:extension-url@` replaced with a strict JSON string literal `import("file:///...")`; backslash/encoded-separator paths are refused `unsupported-path` instead of writing an unloadable shim (`src/host/adapter.ts:113-131`). Omp plugin composes, never constructs: daemon owns sandbox/policy/session; plugin registers 5 tools + retry command + widget paint, or 0/0/0 when the persisted toggle is off, and fails closed on hook errors/timeouts (`src/omp/plugin.ts:1-21`).
- GSD-Core hook contract (upstream, per N1 §4): installer writes skills/agents/commands + lifecycle hooks per runtime — `SessionStart` (update-check + session orientation), `PreToolUse`/`PostToolUse`/`Stop`/`PreCompact`/`SubagentStart|Stop`, global-vs-local shadowing advisory (W028), runtime restart required after install.
- Probes (N1 §5–6): `podman 4.9.3` on PATH (below the 5.x OpenShell/live tier), `podman 5.7.1` at `/usr/local/bin/podman`, `openshell 0.1.5`, AgentOS CLI absent (`@rivet-dev/agentos-core 0.4.7` in `node_modules`, in-sandbox runner/probe compiled from source), no `localhost/realm-agentos` image, 150+ registered worktrees, `realm` absent from PATH (`dist/` built, no `npm link`).

Compositions scored (definitions fixed for this node):

- **A — single container/project:** one container/sandbox per project (workspace root), shared by all its sessions and worktrees.
- **B — AgentOS controller + per-worktree containers:** daemon-led controller (today's `SessionExecution` + per-session `AgentOsSupervisor` over OpenShell) with one container/sandbox per worktree (each git worktree pinned to its own container).
- **C — host-only disposal:** no central daemon/sandbox; each host process owns and disposes its own execution directly on the host (PATH-resolved binaries, host FS).

Plugin mechanisms scored:

- **P1 — native GSD-Core hooks:** per-runtime lifecycle hooks installed by the GSD-Core installer (`SessionStart`, `PreToolUse`/`PostToolUse`/`Stop`, worktree guards).
- **P2 — per-agent configs:** Realm `realm host install` recipes + receipt-owned config blocks/blobs (incl. Omp extension `bundle-copy` + shim token) with `resolveBoot`/boot-driver attach.
- **P3 — PATH shim:** bare executable resolution on `PATH` (`mcp-config` launch command, `launch: on-path` check, `podman 5.7.1` off-PATH precedent).

## 1. Composition scoring

Scale 5 = best, 1 = worst, on each criterion, with evidence. Score order is INFERENCE from the FACT rows.

Failure-mode stress test (INFERENCE from probes + taxonomy):

- **Leader missing** (no daemon socket): B and A both retry through `ensureDaemon` (spawn at most once, poll to the up bound) and settle `failed/REALM_NOT_ACTIVE` with exit 1 at stdin end, 0 otherwise — sandbox untouched, next host start recreates. C has no leader concept; absence of a host binary surfaces as shell 127 with no diagnostics table.
- **Component missing** (no AgentOS driver, no `realm-agentos` image, AgentOS CLI absent): today's daemon refuses `up` with `AGENTOS_NOT_CONFIGURED` before any libpod call (`daemon.ts:10`, `seams.ts:179`) — B preserves this refusal. A inherits it too but pins it to one container for the whole project. C treats it as a version problem to shim around (e.g. `podman 4.9.3` vs `5.7.1` ambiguity, N1 §5) rather than a refusal.
- **Unhealthy sandbox after active:** B holds the supervisor, moves the session to error with the classified code, never auto-restarts; explicit `start()` reuses the stored container, stale recovery only under `OPENSHELL_START_FAILED`. A would need a new ownership protocol before it can even say whose error it is. C has no probe — "unhealthy" is indistinguishable from "working".
- **Gateway/compute-driver down vs runner dead:** B classifies via `gatewayAnswers` / `driverAnswers` probes (`agentos.ts:14-21`): gateway silent → `OPENSHELL_GATEWAY_LOST`; gateway answers + driver answers or unconfigured → `AGENTOS_CRASH_LOOP`. A and C have no equivalent two-leg probe in the composed system.

**Chosen ordering (compositions): B > A > C.** B is the only composition that already exists in code without relocation of ownership: daemon as leader, per-session `realm-<sessionId>` sandbox, per-worktree materialisation of the same mechanism. A is a viable future consolidation for single-worktree projects only. C is rejected as a default because it fails the core value on every criterion except brevity.

**Chosen ordering (plugins): P2 > P1 > P3.** P2 is the default attach path for all 21 `mcp-config` hosts and, via the extension bundle-copy shim, for Omp. P1 is kept for the 18 GSD-flagged runtimes as the hook *vocabulary* (SessionStart orientation, `PreToolUse`/`PostToolUse` guards) that P2's boot bounds already mirror — adopt the semantics, install through P2's receipted recipes, do not depend on upstream hook installation for correctness. P3 is a launch-resolution *fallback only* (how `realm host status` proves `launch: on-path`), never a mechanism.

Note on Omp: Omp is `extension`, not `mcp-config` (`bootHookOf` returns `null`, `boot-driver.ts:593-597`). Its plugin composes the daemon client and holds no lifecycle/policy/runtime (`plugin.ts:3-5`); the shim (`import("file:///...")`) is P2's bundle-copy form, and its interactive value (tool_call guard + AUI widget) is precisely what P1's hooks and P3's PATH cannot provide. So Omp is the strongest evidence for P2, not the exception that needs P1.

## 3. Chosen pairing and division of labour

- **B + P2** is the target composition: daemon leader → `SessionExecution` (label-idempotent OpenShell create, inspect-verify, per-session AgentOS supervisor) → one `realm-<sessionId>` container pinned to its worktree's `workspaceRoot`; hosts attach via `resolveBoot`/`createBootDriver` (mcp-config) or the Omp extension (`session_start`/`tool_call`/widget), install via receipted recipes, and never send `down` on exit.
- Division: `src/runtime` (openshell/agentos/session-execution/driver) owns containers and liveness codes; `src/host` (`boot`, `boot-driver`, `attach`, `recipe`, `adapter`) owns attach/retry/exit; `src/lifecycle` owns the S-02 binding. P1 hooks are referenced in docs as the upstream vocabulary, not implemented or shipped.
- Until the per-worktree keying lands, B runs today keyed by session id; the per-worktree step is exactly the `pinnedRoot`/`workspaceRoot` record binding already enforced in `controller.ts`.

## 4. Reversal condition

This ordering reverses, in a stated order, only on evidence:

1. **B → A (per-worktree keying)** if per-worktree containers cannot fit the gateway/material constraints on a real tree: name length 19 (`realm-` + sessionId) must compress worktree identity without colliding with the 150+ registered worktrees; ambiguous label match (`OPENSHELL_LABEL_AMBIGUOUS`) or repeated 30 s name-release waits show up in lifecycle telemetry for a single checkout; **and** canonical worktree count for the delivery checkout is 1 (no second worktree bound to a container). Single-checkout projects may then consolidate to one container per project, keeping S-02's principle (a container never serves a root it was not created for) as one container per project.
2. **P2 → P1** if a GSD-flagged runtime cannot consume `mcp-config` at all (no MCP client) and its hook contract is the only attach surface; then ship P1-shaped receipts for that runtime only, still behind `resolveBoot` bounds — never upstream's unreceipted installer.
3. **Any → C** is never a default. Host-only disposal becomes admissible **only** as an explicit per-workspace policy mode a user opts into with visible `realm status` disclosure ("disconnected / host-only, no sandbox"), with the same catalogue codes and fail-closed guard (`backstopVerdict`), and with PATH resolution pinned to an absolute binary (`launch: on-path` checked at attach). Unlabelled host execution without those constraints is a P0 regression against the core value, not a degradation.

Explicit non-goals carried from N1: `realm` PATH absence (A4) and podman store equivalence (A2) are out of scope for this comparison; neither changes the ordering, because B already treats missing components as `AGENTOS_NOT_CONFIGURED`/`REALM_NOT_ACTIVE` refusals rather than assumptions.
