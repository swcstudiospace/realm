# Plan 15-15: live checkpoint L-C (ONB-01, ONB-02)

## Objective

Record the live evidence for `realm init` and `realm doctor --fix` on the realm account. This is a human-needed checkpoint (L-C in `15-RESEARCH.md` section 6). The executor pauses here and does not run it.

Starting state. L-C starts from the host state that the owner's written decision on L-B names. Plan 15-10 step 9 restores the saved driver unit, the previous `app` directory and the backed-up `config.json` (P15-O4). If the owner has not decided in writing that the new build and its edited unit stay installed after L-B, the realm account runs the old driver on the old config and L-C has no valid start state. In that case the checkpoint stops and reports `blocked: owner decision pending`, and no step runs.

Gate, checked before step 1 of the action:
- The owner's written decision exists, names the new build installed at the realm account's `app` directory, names the edited driver unit (three `REALM_DRIVER_*_ROOT` variables dropped, config home added) as still in place, and names the account's `config.json` as the one whose `image` is the driver's digest.
- L-A and L-B passed (plan 15-10), with the driver of the new build running from that edited unit.
- If any item is missing, report `blocked: owner decision pending` and stop.

Preconditions the human confirms once the gate passes:
- The lock is held by the operator. The lock script is outside this repository.
- `openshell` is on `PATH`, Podman 5.x is installed, and the built CLI comes from the same checkout as the driver.
- The account's state directory and its `secrets` and `sandboxes` roots exist at mode 0700, and the pinned workspace is an existing account-owned directory outside the state directory.

Decisions this checkpoint serves: D-1507 (init and fix behaviour on a real host), P15-O1 (the image is the driver's digest, passed explicitly), P15-O2 (the host already has the stack; init provisions none of it), P15-O3 (the doctor exit codes on the live path), P15-O4 (L-C adds no host change; any restore after L-B is governed by the owner's decision, not by this plan).

This plan adds no restore step. L-C does not install, edit or restart the driver, and it does not restore anything. Its only host changes are the aside move of the two templates in step 1 and the init in step 2; step 4 puts the templates back.

## Artifacts this phase produces

- A redacted transcript returned by the human to the orchestrator. Plan 15-16 uses its init, up, status and down output for the README quickstart transcript, and its `doctor --fix` output as ONB-02 evidence. No file in the repository is written by this plan.

<threat_model>
- The live realm account is left without its config and policy while the procedure runs. Mitigation: the originals are moved aside, never deleted, and step 4 restores them whatever the result of steps 2 and 3.
- L-C runs from a host state the owner did not approve, such as the old driver after L-B's restore. Mitigation: the gate above; without the written decision the checkpoint reports blocked and runs no step.
- The throwaway run touches the realm account's state. Mitigation: step 5 uses only scratch `HOME`, `XDG_CONFIG_HOME`, workspace and state paths, and the realm account's files are not named in it.
- Host-local absolute paths or secrets reach the committed docs. Mitigation: the transcript is redacted before it is handed back (step 7), and the automated check rejects any transcript with a host-local absolute path. No secret is expected: `config.json` and `policy.json` hold no secret.
- The executor runs live commands. Mitigation: this plan is `autonomous: false`; the executor stops at the checkpoint.
</threat_model>

The human runs these steps. The executor does not.

Gate (check first; if any item fails, report `blocked: owner decision pending` and stop without running a step):
- The owner's written decision keeps the new build at the realm account's `app` directory, the edited driver unit in place, and the account's `config.json` with the driver's image after L-B. Its text is quoted in the returned transcript.
- L-A and L-B passed under the lock, and the driver of the new build was running from the edited unit at that point.

On the realm account:
1. Locate the account's files: `config.json` at `$XDG_CONFIG_HOME/realm/config.json` and `policy.json` at `<stateDir>/policy.json`. Move both aside with `mv` to a new aside directory. Do not delete them. Record the state directory mode and the modes of `secrets` and `sandboxes` (expect 0700 each). Do not restart the driver; the running driver already holds its config.
2. Run `realm init --image <driver image digest> --workspace <pinned workspace> --state-dir <existing state directory>` as the realm account, with the account's `HOME` and `XDG_CONFIG_HOME`. Expected: exit 0, one JSON line with `"mode":"fail-closed"`, and both files created at 0600. The existing state directory and both roots already exist at 0700, so init accepts them. If init refuses, go to step 4 at once and report the refusal code and reason.
3. Run `realm up` (no file is edited by hand). Expected: the daemon reaches active. Then run `realm status` (expect `mode` `fail-closed` in its output) and `realm down` (expect the daemon to stop).
4. Restore the templates: move the init-written `config.json` and `policy.json` aside (keep them for the record), then move the step 1 originals back to their paths. Confirm the originals' modes and bytes match what was recorded in step 1.

On a throwaway host (scratch paths only, never the realm account's):
5. Create `<scratch>/workspace`. Run `realm init --image <driver image digest> --workspace <scratch>/workspace --state-dir <scratch>/state` with `HOME=<scratch>/home` and `XDG_CONFIG_HOME=<scratch>/config` in a clean environment (`env -i` with `PATH`, `HOME`, `XDG_CONFIG_HOME` and `XDG_RUNTIME_DIR` only). The state directory is absent, so init creates it at 0700. Then run `chmod 755 <scratch>/state`. Then run `realm doctor --fix --dry-run`: expect `"dryRun":true` and a `set-mode` fix for `<scratch>/state` from 755 to 700, and the state mode still 755. Then run `realm doctor --fix`: expect exit 0, the state mode 700, and the same fix listed. Then run `realm doctor --fix` again: expect exit 0 and `"fixes":[]`.
6. Delete `<scratch>` after recording its outputs.

Recording (step 7):
- Record the exit code and stdout and stderr of every command above.
- Replace the realm account's home directory, the pinned workspace, the scratch directory and any other host-local absolute path with `<account-home>`, `<pinned-workspace>` and `<scratch>`.
- Save the redacted transcript in a file, and give its path to the orchestrator as the value of `REALM_LC_TRANSCRIPT`.
- Report any refusal, any non-zero exit, or any difference from the expected results; do not summarise a failure as a pass.
