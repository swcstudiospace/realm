# Plan 15-10: live checkpoints L-A and L-B for the roots, the environment and the doctor (ONB-03, ONB-04, ONB-07)

## Objective

Prove on the realm stack what the hermetic tests cannot: the live suite passes with its roots read from the config file, a driver of the new build starts on an edited unit, and the doctor reports the three new items as passing. This plan has one automated gate before the live steps and two checkpoints. The executor does not run any live step. Each checkpoint pauses the executor, a human runs the procedure under the realm account's lock, and returns evidence. Each automated verify then checks that evidence without touching the host.

Evidence location: the human sets `REALM_EVIDENCE_DIR` to an absolute scratch directory outside the repository, created with mode 0700, before checkpoint L-A. Every verify command that reads evidence starts with `test -n "$REALM_EVIDENCE_DIR"`, so it fails closed when the variable is unset. This is the same rule plan 15-16 uses.

### Live state (unverified research claims; re-check at L-A before relying on them)

- Unverified research claim: the realm account runs the 0.2.1 driver from its `app` directory, and its unit sets the three root variables plus the socket, gateway and supervisor variables (`15-RESEARCH.md:62`).
- Unverified research claim: the account's `config.json` carries `stateDir` and `workspaceRoot`, names no `secretRoot` or `sandboxStateRoot`, and its `image` differs from the driver unit's `REALM_DRIVER_SANDBOX_IMAGE` (`15-RESEARCH.md:62-64`).
- Unverified research claim: the derived defaults `<stateDir>/secrets` and `<stateDir>/sandboxes` equal the old driver's root variables, so the running driver and the new daemon agree without a host edit (`15-RESEARCH.md:62`, `:123`).
- Unverified research claim: a driver of the new build reads `config.json` through `XDG_CONFIG_HOME` or `HOME/.config`, and on the unmodified unit it refuses with `SCHEMA_INVALID` (`15-RESEARCH.md:63`).
- Recorded decision, not a claim: P15-O4 (`15-CONTEXT.md:13`) authorises the host change for L-B, once, under the live lock, with the saved unit restored afterwards.
- Dated repository record, not a current measurement: the most recent live result is ten scenarios and 33 of 33 assertions (2026-10-30, `docs/integration/openshell.md:557`). The research's "nine scenarios, 31 of 31" is stale; the suite has ten scenarios at HEAD (`test/integration/production-driver.test.ts:248-870`, verified by reading the file).

<threat_model>

- Trust boundary: the live stack belongs to the realm account. The live suite and the host edit act on real sandboxes, on the account's `config.json`, on its systemd user unit, and on its driver process.
- Destructive effect: the driver's startup sweep removes every realm container and every sandbox secret entry of the account (`src/runtime/driver/main.ts:211-218`). A driver restart is therefore account-wide. The checkpoints require that no sandbox the operator needs is running before any restart.
- Secrets: the live procedure requires the image digest and the socket path, which are not secrets. The procedure forbids printing the environment, the unit file's contents other than the `Environment=` names, and any key or token. Evidence is redacted before return.
- Rollback: the saved unit and the previous `app` directory are the rollback. Restoring them is part of the procedure (P15-O4), not optional.
- Lock: the lock script is outside the repository; the human acquires it before the first live step and releases it after the restore.

</threat_model>
