### 3.2 ONB-03: roots in `config.json`, daemon and driver read one source

`src/runtime/config.ts`:
- `RuntimeConfig` gains optional `secretRoot?: string` and `sandboxStateRoot?: string`; `ACCEPTED_KEYS` gains the same two names (the names `SessionExecution`/`startDaemon` already use). Explicit values must be absolute (existing `requireAbsolutePath`) and, lexically, `secretRoot` must not equal or lie inside `sandboxStateRoot`, and neither may equal, contain or lie inside `workspaceRoot` (the driver enforces the same on realpaths; the lexical check moves the refusal to config load). No fs access in the loader.
- `export interface RuntimeRoots { readonly secretRoot: string; readonly sandboxStateRoot: string; readonly workspaceRoot: string }` and `export function runtimeRootsOf(config: RuntimeConfig): RuntimeRoots`: explicit value, else `join(stateDir, "secrets")` and `join(stateDir, "sandboxes")`; `workspaceRoot` is `config.workspaceRoot`. Constants `DEFAULT_SECRET_ROOT_NAME = "secrets"`, `DEFAULT_SANDBOX_STATE_ROOT_NAME = "sandboxes"` exported for init and doctor. These defaults equal the installed layout (2.2).
- `export function describeRuntimeConfigProblems(input: unknown): readonly string[]`: one fixed phrase per failing key, naming the key, never the value (for init messages and the doctor's no-config path). `loadRuntimeConfig` stays the validator; this reuses its predicates.
- Phase 18 reworks the workspace pin; keep `RuntimeRoots` the only seam so it has one place to change.

Daemon: `src/daemon/main.ts` drops the three constants and the three `deps.env[...]` reads; it computes `const roots = runtimeRootsOf(loadRuntimeConfig(runtimeInput))` (the config was already read at `:77`) and passes the three values unconditionally, plus `doctorOptions: { runtimeRoots: roots, driverSocketPath }` (3.4). `src/daemon/daemon.ts` and `session-execution.ts` keep their optional fields: embedding callers and tests that omit them still fail closed with `SCHEMA_INVALID`. No edit in `daemon.ts` is needed, which avoids the Phase 14 W2 hunks there.

Driver: `src/runtime/driver/main.ts`: remove `stateRoot`, `secretRoot`, `workspaceRoot` from `DRIVER_ENV`; `loadDriverProcessConfig(env, version, roots: RuntimeRoots)` keeps all other validation; `main()` obtains `roots` with `readHostRuntime(env)` then `runtimeRootsOf(loadRuntimeConfig(...))`, using the same `resolveConfigPath` the daemon uses (`XDG_CONFIG_HOME` absolute, else `HOME/.config`). The driver already depends on `XDG_RUNTIME_DIR`, so adding the config-home lookup keeps it at the three-name environment. A stale `REALM_DRIVER_{STATE,SECRET,WORKSPACE}_ROOT` in a unit is ignored (daemon and driver both use config, so they cannot diverge); rejected: refusing to start on a stale variable (extra failure mode, no safety gain) and keeping the variables as an override (D5 and the roadmap say no shim).

Host cutover (TD-02 coordination, to be written into `docs/integration/openshell.md`): install the new build, edit the driver unit (remove the three `Environment=` lines, add `Environment=XDG_CONFIG_HOME=<config home>` or rely on `HOME`), `daemon-reload`, restart. Until then the 0.2.1 driver keeps working with the new daemon on this host because the derived defaults equal its env values (INFERENCE: shown by live run L-A). ### 3.5 ONB-01 and ONB-02: `realm init` and `realm doctor --fix`

`src/cli/init.ts` (new): `parseInitArgs(words)` and `runInit(args, deps): CliResult`, called from `runCli` before the config resolution (`init` needs no config, no daemon, no Podman). Surface:

`realm init --image <name@sha256:64hex> [--workspace <abs>] [--state-dir <abs>]`

- `--image` required; checked with `loadRuntimeConfig` on the assembled object (the same validator `up` uses), so init cannot write a config the daemon would refuse; a failure prints the key names from `describeRuntimeConfigProblems`. No default digest, no lookup (decision 1).
- `--workspace` default `deps.cwd ?? process.cwd()` (as `up` does); must be absolute, an existing directory, not a symlink, owned by the current uid (the driver demands it), not `/`.
- `--state-dir` default `$XDG_STATE_HOME/realm` when absolute, else `$HOME/.local/state/realm`. This is only the value written into the config; the daemon still reads the state dir from the config (the tests that ignore `XDG_STATE_HOME` stay valid).
- Config path: `resolveConfigPath(env)`.

Preflight, all before any write; every refusal is exit 2, one stderr line `realm init: <reason>`, nothing written: image missing or malformed; paths not absolute; workspace problems above; state dir inside the workspace or the workspace inside the state dir; the config file inside the workspace; `controlSocketPath(stateDir)` or the channel socket path derived from `runtimeRootsOf` longer than 107 bytes (message suggests `--state-dir`); `config.json` or `<stateDir>/policy.json` already exists in any form (`lstat`, so a dangling symlink counts); state dir exists but is not a real directory owned by the uid with mode 0700 (init never chmods what it did not create; the message names `realm doctor --fix`).

Writes, in order: state dir (missing ancestors default mode, leaf `mkdir` 0700 then `chmod` 0700 against umask), `<stateDir>/sandboxes` and `<stateDir>/secrets` (names from `runtimeRootsOf`, 0700), config dir `realm/` (0700), then `policy.json` and finally `config.json`, each as a temp file created `wx` at 0600, fsynced, then published with `linkSync` (fails with EEXIST if a racing writer created the target: atomic no-clobber) and the temp unlinked. If the second publish fails, the first file created by this run is removed and reported. Failure after preflight is exit 1 with `SCHEMA_INVALID` as the existing `refusalOf` maps unknown errors. Output: stdout one JSON line `{"config":"...","policy":"...","stateDir":"...","mode":"fail-closed"}`, stderr "realm init: wrote ...; next: realm up". Templates:

```json
{ "image": "<ref>", "stateDir": "<abs>", "workspaceRoot": "<abs>" }
{ "mode": "fail-closed", "workspaceRoots": ["<abs workspace>"] }
```
`mode` is written explicitly (D4). No `secretRoot`/`sandboxStateRoot`: the defaults apply, so there is one derivation. No `--dry-run` for init (not in ONB-01; add only if the owner wants it). Rejected: writing a placeholder digest (forbidden), creating the workspace (the driver never creates it, and a wrong path should be an error), overwriting with `--force` (not asked), prompting (non-interactive CLI).

`realm doctor [--fix [--dry-run]]`: `parseArgv` accepts `--fix` and `--dry-run` only for `doctor`; `--dry-run` without `--fix` is usage (exit 2). `--fix` always runs locally, never through the daemon (it edits the host and must not depend on the daemon's environment). New `src/doctor/fix.ts`:
```ts
export interface FixTarget { readonly path: string; readonly createIfAbsent: boolean }
export interface FixResult { readonly path: string; readonly action: "create"|"chmod"; readonly from: string; readonly to: "700";
  readonly outcome: "applied"|"would-apply"|"refused"|"failed"; readonly reason?: "symlink"|"not-a-directory"|"foreign-owner"|"unsafe-target"|"error" }
export function fixDirectories(targets: readonly FixTarget[], options: { dryRun: boolean; uid: number; workspaceRoot: string; home: string|undefined }): readonly FixResult[];
```
Targets built by the CLI from the config: `stateDir` (create if absent), `<stateDir>/run` and `<stateDir>/sessions` (chmod only; the daemon creates them), `secretRoot` and `sandboxStateRoot` (create if absent). Per target: `lstat`; absent and creatable: `mkdir` 0700 (ancestors default mode, as `withDaemonLog` does) then verify; present: symlink, non-directory, or another owner are `refused` with a reason and nothing touched; mode other than 0700 on a real directory: open with `O_DIRECTORY|O_NOFOLLOW`, `fstat` (uid check), `fchmod(0700)` through the descriptor (no check-then-use race); mode already 0700: no result entry. `unsafe-target` refuses a target that is `/`, `home`, or equals or contains the workspace root (an explicit root misconfigured onto the user's tree must not be chmodded). Nothing else is touched: no files, no `policy.json` or `config.json`, no workspace, no sockets. Dry-run computes the same results with `would-apply` and writes nothing (test: `stat` before and after). Output: stdout JSON `{"dryRun":bool,"fixes":[...],"checks":[...]}` where `checks` is a fresh local report (after the fixes, or the current state for dry-run); stderr one line per fix. Exit 0 when nothing is refused or failed (also when nothing needed fixing), 1 when any fix was `refused` or `failed`, 2 for usage or an unresolvable config (message gains "run `realm init`"). The existing fix prose of `state-dir`, `control-channel` and the new roots check gains "or run `realm doctor --fix`".

Tests: `test/cli/init.test.ts` (templates exactly as above and loadable by `loadRuntimeConfig` and `loadPolicyFile` with `mode` `fail-closed` explicit; modes 0700/0600 asserted with `stat`; every preflight refusal writes nothing; second run refuses and leaves the first bytes; dangling symlink target refused; socket path too long; workspace containing the config; simulated failure on the second publish removes the first; real umask 022 and 077), `test/doctor/fix.test.ts` (the 0755 to 0700 case from ONB-02, a second run returns no fixes, dry-run changes nothing, symlinked directory refused with the target untouched, file in place of directory refused, absent creatable dirs created at 0700, unsafe target refused, only the listed directories touched), CLI wiring tests for the exit codes and `--dry-run` usage. `test/cli/cli.test.ts:395-400` usage test: add `init` to `CLI_COMMANDS` and the usage string.
