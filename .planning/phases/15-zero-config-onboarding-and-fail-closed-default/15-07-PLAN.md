# Plan 15-07: doctor and spawn wiring at the entry edges (ONB-03, ONB-04, ONB-07; D-1504, D-1505, D-1506)

## Objective

Wire the pieces built by plans 15-04 to 15-06 into the two entry edges, `src/daemon/main.ts` and `src/cli/main.ts`, and prove the wiring in `test/cli/cli.test.ts`.

### Verified at HEAD (reconciled)

- Spawn environment (ONB-07): `src/cli/main.ts:342-347` `spawnDetachedDaemon` and `:351-369` `launchFilteredDaemon` already pass `env: daemonSpawnEnv(source)` (`:366`). `:373-375` `startDetachedDaemon` passes `process.env`. This is done and is not changed here; the test proves it.
- Daemon roots (ONB-03): `src/daemon/main.ts:78-79` and `:92-94` pass the three roots from `runtimeRootsOf`. Shipped and tested.
- Daemon doctor (ONB-04): `src/daemon/daemon.ts:155` types `doctorOptions` as `Omit<DoctorOptions, "stateDir" | "env">`. `:258-266` `runDoctor` spreads `options.doctorOptions` and then sets `runtimeConfig: config` (`:265`), so the daemon's doctor already receives the loaded config. What is missing is `configPath` and `driverSocketPath`: `src/daemon/main.ts:84-99` passes no `doctorOptions`.
- Plain doctor (D-1506): `src/cli/main.ts:683-707` reads the config in a `try`. In the catch, for `doctor` only, it runs `runtimeChecks({ env: deps.env })` with no problems, so an invalid file gets the detail `runtime config is absent`. That is wrong for a present file, and the stderr says `config is absent`.
- `src/cli/main.ts:494-504` `localDoctorOptions` passes no `configPath` and no `driverSocketPath`.
- Exit code (P15-O3): `src/cli/main.ts:487-491` returns `exitCode: 0`; pinned at `test/cli/cli.test.ts` (the no-daemon run, and the no-config run at `:918-935`, both assert 0).
- Test seam: `test/cli/cli.test.ts:60-73` `makeSpawn` records `file`, `args`, `detached` and `stdio` only, so no test observes the spawn environment.

### Gaps this plan closes

1. The daemon's doctor does not receive `configPath` (for the config-location check) or `driverSocketPath` (for the driver-socket item).
2. Plain doctor cannot distinguish an absent config from an invalid one and does not name the bad keys.
3. The CLI spawn environment is not asserted by any test.

## Artifacts this phase produces

- `src/daemon/main.ts`: `doctorOptions` passed to `startDaemon`; `resolveConfigPath` imported from `../runtime/host-paths.js`.
- `src/cli/main.ts`: one config read kept as a raw value; a doctor-only one-item path using `describeRuntimeConfigProblems`; `localDoctorOptions` with `configPath` and `driverSocketPath`; stderr for the one-item path says `config is absent or invalid`.
- `test/cli/cli.test.ts`: `SpawnCall` gains `env`; new tests named `ONB-07:` and `ONB-04:`; one updated assertion (the no-config detail) if it pins the old wording.

## Decision coverage

- D-1504: the daemon and the doctor read the roots from the same config (the daemon via `runtimeRootsOf`, the doctor via `runtimeConfig`).
- D-1505: the spawn environment is observed on the CLI call.
- D-1506: the one-item config report names the problem keys and `realm init`.
- P15-O3: the plain doctor exit stays 0 on every path, pinned by the tests this plan keeps.

<threat_model>

- Trust boundary: the CLI and the daemon both receive the environment at the entry edge. The doctor receives values from that edge and never reads `process.env` itself.
- Information disclosure: the one-item report names keys only (plan 15-04's `describeRuntimeConfigProblems`); no value and no path appears in stdout or stderr. The stderr line is fixed text.
- Tampering: the doctor only reads config and sockets; the daemon's start is unchanged. A stale `REALM_DRIVER_*_ROOT` in the CLI environment is not read by any path here.
- Exit code: a doctor failure never makes the process exit non-zero (P15-O3). Exit 1 belongs only to `doctor --fix` refusals (plans 15-12 and 15-13).

</threat_model>
