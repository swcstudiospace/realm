## Locked decisions
- **D-1201 two tiers of gating.** `REALM_LIVE_OMP=1` opts in to any test that starts a real Omp process; it is hermetic (no Podman, no image, no openshell) and is never set by a test. `REALM_OMP_BIN` optionally names the Omp executable (default `omp` on `PATH`). `REALM_OMP_NET_TRACE=1` opts in to the strace-based network assertion. The optional production-stack case C4 additionally needs `REALM_LIVE_PRODUCTION=1` and its four existing variables (`productionSkipReason`, unchanged). `ompSkipReason` returns the first missing prerequisite, in the order: opt-in variable, Linux, Omp executable present, `omp --version` parses and is at least 18.12.6, built extension present, then for the trace `strace` present and able to trace. Helpers that already exist in `test/support/production-live.ts` (`isDirectory`, `onPath`, `runCommand`, `pollUntil`) are reused, not copied.
- **D-1202 the three cases run against an in-process real daemon with fakes.** `startDaemon` runs in the test process over `FakeExecutionService`, `FakeBridge`, a scripted probe and `sweep: async () => 0`, as `test/daemon/e2e.test.ts` does; Omp is a child process that dials the control socket. `down` over the control channel removes the socket, which is what the live `realm down` does. Cases: C1 advisory with the realm down (the notice `realm status unavailable (REALM_NOT_ACTIVE); the write proceeds under advisory policy` and the file exists), C2 fail-closed with the realm down (the call is blocked with `REALM_NOT_ACTIVE`, the file is absent, the provider's next request carries the error), C3 the realm active (the call proceeds on the host; the offered tool list is recorded as the baseline that Phase 16 changes). C4 (optional, doubly gated) reproduces the live attach and the blocked write on the production stack once. Each case has its own temp profile, daemon and Omp process. The policy mode is always written explicitly, because Phase 15 flips the default.
- **D-1203 event-driven waits only.** No wall-clock sleeps except bounded failure timers; waits resolve from the frame handler. The daemon is created before Omp is spawned so `ensureDaemon` never spawns a detached real daemon. No `spawnSync` in a test process that hosts the in-process daemon. Socket paths stay under 107 bytes (short `mkdtemp` prefix `rlv-`). Bounds: Omp ready 180 s, per prompt 60 s, scenario 300 s.
- **D-1204 the spike uses a test extension, not the Realm plugin.** `test/support/omp-spike-extension.ts` (compiled, loaded with `-e`) logs `tool_call`, `tool_result`, `getActiveTools()` and `getAllTools()` to a JSONL file; the scripted provider emits exactly one tool call per prompt. The questions are S1 to S14 of the research (section 4): registration and shadowing, `setActiveTools` enforcement per built-in, the transports that survive removal (`write xd://...`, `local://`), `ast_edit`, `lsp`, `debug`, `eval`, `task` and subagents, `registerFileWriteFallback`, `tool_call` blocking, session lifecycle, and the network levers. The same cases run against the Realm plugin in Phase 16. The spike's table is version-stamped and is a permanent gated regression test.
- **D-1205 the network assertion.** The research found that a fresh Omp profile makes dozens of outbound TCP 443 connections at startup (model catalog refresh) and that a warm profile makes none beyond loopback probes of ports 11434, 8080 and 1234 and the stub. The harness observes with `strace -f -e trace=connect,...` and classifies connects (AF_UNIX allowed, loopback allowed with the three discovery ports and the stub port on an explicit allowlist, loopback port 53 reported as DNS, anything else external and a failure). The spike tries the levers in this order: an Omp setting or environment variable that disables the catalog refresh and provider discovery; a registry configuration exposing only the stub; a warm profile seeded by an untraced warm-up run; an empty network namespace. HARN-03's text says "no network call outside loopback": the harness asserts that over the measured run once a lever works. If no lever works, the honest claim is "after the `ready` frame and across all scripted turns Omp made no non-loopback connection", with startup traffic named out of scope and recorded with the Omp version; that wording change is made in `.planning/REQUIREMENTS.md` HARN-03 and the roadmap criterion in the same pull request, with the evidence.
- **D-1206 version handling.** The harness records `omp --version` in its output and hard-fails below 18.12.6; newer versions run and are recorded. Frame names, the device-only `write` behaviour and `registerTool` replacement are 18.12.6 behaviour.
- **D-1207 file ownership.** `docs/integration/omp.md` is owned by the spike unit (WU4); the guard-suite unit (WU5) adds its text after WU4 or in a second commit. `AGENTS.md` (Commands and Layout), `docs/integration/omp.md` and `docs/integration/omp-lifecycle-runbook.md` are updated in this phase's pull requests.

## Risks and stop conditions
- Omp ready takes 10 to 60 s on a loaded host; three cases need at least three starts. Generous bounds, no speed assertions.
- Enforcement is partial by default: removing `write`, `edit` and `bash` leaves `ast_edit`, `lsp`, `debug`, `eval`, `task` and `local://` writes reachable. The spike records the full list; Phase 16 removes by an allowlist or a computed denylist, and the product claim follows what is proven.
- `strace` may be absent or blocked on a host; the assertion skips with a reason. Parallel test files share the CPU but no ports.
- Stop and report instead of widening scope if the spike shows that the extension API cannot block a built-in at all; that changes D3's outcome and Phase 16's claim.
