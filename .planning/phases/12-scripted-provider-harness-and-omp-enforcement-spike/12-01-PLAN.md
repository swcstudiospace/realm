## Sequence
1. Wave 1 units edit in parallel and run no gate. The orchestrator builds in the lane worktree, runs typecheck, the new always-running helper tests and lint on the changed files, fixes through corrective units, then one commit per unit.
2. Wave 2: the spike agent builds, runs the spike live on the realm host's Omp installation (the harness is hermetic, so the lock is not needed; it never touches Podman), records the table, and commits nothing (the orchestrator commits). The orchestrator reviews the table against the raw JSONL before anything depends on it.
3. Wave 3: WU5 writes the guard suite using the lever WU4 found. The orchestrator runs the gated suite live, then the full unit suite and lint once, and records the run.
4. Pull requests: A (wave 1 and 2: the harness core, the fixture, the observer, the spike and its docs) and B (wave 3: the guard suite, the runbook, AGENTS.md, and the OMP-05 and HARN-03 requirement changes with the live evidence), reviewed to 5 of 5 and merged through the ship flow.
5. Records: summary, verification, requirements and roadmap statuses from evidence only.

## Acceptance
The five items of `12-CONTEXT.md`, plus: typecheck, lint, `check:docs`, `check:gates`, `test:scripts` and `npm test` pass with no test deleted or skipped to get there (the new gated tests skip with a stated reason when their opt-in variable is unset, as the production suite does) and no suppression directive; the helper tests always run in CI without Omp.

## Risks and stop conditions
See `12-CONTEXT.md`. Additionally: if `strace` cannot trace Omp on this host, the network assertion is built and unit-tested but its live run is reported as not run, and HARN-03 stays partial rather than complete.
