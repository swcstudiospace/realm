## Phase Boundary

The owner's decision D-v6-5 (2026-11-18): reproduce `daemon.stopped code=REALM_STOPPING failedTeardowns=1` after about 30 s in a stop with a sandbox container, find the cause, fix or bound it, and prove it with a hermetic test and a live run.

This phase has two plans. Plan 41-01 is the hermetic half: it makes the stop path testable without waiting (an injectable teardown bound and a leaf module that holds the stage bounds), records the reproduction as tests that fail on the current code, and fixes the bound. Plan 41-02 is the live half: a gated test that stops a real daemon with a real sandbox container several times, an owner-supervised window that runs it, and the record of the result.

Decisions fixed elsewhere and not reopened here: the single teardown bound is a ruled design (D-28, Q-1 in `src/lifecycle/bounds.ts`; the catalogue has no teardown-timeout code and none is added); the `daemon.stopped` event carries `failedTeardowns` always and `code` when a teardown failed (owner ruling 5, 2026-11-07, `docs/integration/runtime-decision.md`); `controller.stop` keeps the session record so the next start's reap clears a container the stop left (`closeEverything` in `src/daemon/daemon.ts`); the owner authorization of 2026-11-18 that live windows are authorized when a phase needs them, under the same rules as before (shared live lock, `realmlive` account, residue checks, evidence outside the repository, a person runs every production-stack step).

Out of scope, stated so no task drifts into it:

- A new error code, a new event name, a change of the field names or order of `daemon.stopped`, or a policy key. The error catalogue stays at 29 codes.
- The startup reap, the compute driver's own stop grace (`STOP_GRACE_MS` in `src/runtime/driver/lifecycle.ts`) and its supervisor bounds, the OpenShell CLI or gateway, and the AgentOS runner stop (`src/runtime/agentos-driver.ts`). They are read as evidence; a finding about them is recorded, not patched here.
- Stopping the sessions of one daemon in parallel (see Deferred Ideas), and any change to how a `down` sequences its two teardown calls (OQ-41-05).
- The Phase 38 to 40 and 42 to 43 topics. The phases are independent; only the shared live lock couples them.

## Implementation Decisions

### Evidence (each fact: source, read or observed date 2026-11-18, tier)

Tiers: **O** observed by reading a repository file, **R** a recorded run or owner statement, **M** measured on this host in this planning pass, **I** inference (also marked [INFERENCE]).

- **E-41-01 (R). The report.** During the Phase 34 live window one run showed a daemon teardown that failed: `daemon.stopped` with code `REALM_STOPPING` and one failed teardown, after about 30 seconds; the restarted daemon reaped the sandbox container; it did not recur and was not investigated (34-03-SUMMARY run history; 34-VERIFICATION limitation 5). The step in question is step 5 of Task 5b in `34-03-PLAN.md`: stop the daemon after a scratch session, with the expectation that the sandbox container is removed within about thirty seconds. What is not recorded: how the window stopped the daemon (a signal or a control request), whether a client request was in flight, the host load at the moment, and the timestamps of the stages. See OQ-41-02.
- **E-41-02 (O). What the stop does.** `closeEverything` (`src/daemon/daemon.ts`) logs `daemon.stopping`, sets `downRequested` and `draining`, waits at most `SOCKET_TIMEOUT_MS` (5 s) for other in-flight requests (`drainOthers`), then walks the registry in order. For each session it disposes the health loop and awaits `withTimeout(controller.stop(), TEARDOWN_TIMEOUT_MS, "REALM_STOPPING")`. A rejection counts one failed teardown and keeps the first code. It then logs `daemon.stopped` with `{ code?, failedTeardowns }`, closes the server and removes the socket file; the process exits when the event loop drains (`awaitStop` in `src/daemon/main.ts`). The sessions are stopped one after the other, and no bound covers the loop as a whole.
- **E-41-03 (O). What `REALM_STOPPING` means here.** The only sources of that code on the stop path are an expiry of a teardown bound (the daemon's outer `withTimeout` above, and `teardownCall` in `src/lifecycle/controller.ts`, both `TEARDOWN_TIMEOUT_MS`) or a port failure that is not a `RealmError`. A `RealmError` thrown by the execution port keeps its own code (`teardownCall` rethrows it), so a stage that fails with a code shows that code, for example `AGENTOS_STOP_FAILED`. `code=REALM_STOPPING` on `daemon.stopped` therefore says that a bound ran out, not that a step failed. This fits the report: the failure appeared after about 30 s, and `TEARDOWN_TIMEOUT_MS` is 30 000 ms.
- **E-41-04 (O). The bound and its stated derivation.** `src/lifecycle/bounds.ts` defines `TEARDOWN_TIMEOUT_MS = 30_000` and says it is the sum of three bounds that teardown stages honour in turn: the AgentOS stop backstop (15 s), the container stop grace (10 s) and one libpod request bound (5 s), and that "teardown gives up only after an inner stage has had its own bound". The constant and its derivation date from Phases 2 and 3 (commits `26ab145` and `53fc919`, 2026-10-21; moved to `bounds.ts` on 2026-11-04).
- **E-41-05 (O). The stages the stop actually runs.** `SessionExecution.stop` and `destroy` share `endSession` (`src/runtime/session-execution.ts`). It runs, one after the other and each attempted even when an earlier one failed: (S1) `settleCreatesFor`, only when a create of the sandbox is in flight, bounded by `stopDeadlineMs` (15 s); (S2) `stopAgentOs`, `withTimeout` at `stopDeadlineMs` (15 s); (S3) `containerStep`, an `inspectContainer` and then, in stop mode, `stopContainer(id, CONTAINER_STOP_GRACE_MS)` or, in remove mode, `removeContainer(id, { force: true })`; (S4) `deleteSessionSandbox`, the `openshell sandbox delete` CLI under `SANDBOX_DELETE_DEADLINE_MS` (15 s, killed at that bound), skipped only when this instance already deleted the name. The libpod client bounds each request at `DEFAULT_REQUEST_TIMEOUT_MS` (5 s) and extends a stop by its grace, so S3 is at most 5 + (5 + 10) = 20 s in stop mode (5 + (5 + 2) = 12 s in remove mode, `FORCE_REMOVE_STOP_GRACE_SECONDS`). The worst case of one `exec.stop` is therefore 15 + 20 + 15 = 50 s without a pending create and 65 s with one, against a bound of 30 s.
- **E-41-06 (O). The derivation is stale.** The S4 step (`SANDBOX_DELETE_DEADLINE_MS`, 15 s) was added on 2026-10-26 (commit `e01dabd`, "delete session sandboxes on stop"), five days after the 30 s bound was derived without it. Nothing revisited the bound, and no test runs the stages against it: the stop tests either inject a small `teardownTimeoutMs` into the controller (`test/lifecycle/controller.test.ts`, the test of line 315, "destroy with a scripted stop delay beyond the teardown bound", 50 ms) or use the fake execution service, whose stop takes no stage time at all. No test pins `failedTeardowns` or the shape of `daemon.stopped` either.
- **E-41-07 (O, with [INFERENCE] on the host). The container stop is dead time.** `src/runtime/driver/lifecycle.ts` says of the sandbox runtime that it "ignores SIGTERM" (the comment on `ADOPTION_RESTART_GRACE_MS`); the Phase 19 summary records libpod's `StopSignal SIGTERM failed to stop container ... resorting to SIGKILL`; `src/runtime/libpod-client.ts` and the 2026-10-28 STATE entry record the same dead wait for the force removal, which was cut to a 2 s grace in commit `40684e0` (a first `realm up` after a crash failed with `REALM_STOPPING` because the sweep's force removal waited the 10 s default and outlived its bound). The stop path in `containerStep` still asks for a 10 s grace, so every ordinary stop of a sandbox container spends the full 10 s before the kill [INFERENCE: not measured on this host; the live run measures it]. The AgentOS runner has been stopped before the container step, so nothing in the container is waiting to exit gracefully.
- **E-41-08 (O). What the sandbox delete costs.** The `openshell sandbox delete` CLI asks the gateway, which asks the compute driver: `deleteSandbox` stops the host supervisor (SIGTERM, 5 s grace, then SIGKILL and up to 5 s more), reads the container, and the lifecycle `delete` lists the sandbox's containers, calls `stopContainer` with a 10 s grace (a no-op on an exited container) and `removeContainer`, discards the scratch volume, and removes the state directory and secret entries. The CLI is killed at 15 s while that chain can take longer; a CLI that is killed leaves the gateway to finish or not. [INFERENCE: on a quiet host this step is a few seconds; on a loaded host it is the step most likely to stretch.]
- **E-41-09 (O). What the flake cost.** An expiry leaves the session `stopping` with its record and container recorded. The process then exits (nothing else keeps it), so the stop's remaining work is cut off, and the container, already killed or still running, is reaped by the next start's reap: exactly what the report describes. The harm is a misleading failed-teardown report and a container that lives until the next daemon start.
- **E-41-10 (O). The timeline that fits the report [INFERENCE].** A normal stop of a finished session is: runner terminate (up to 2 s SIGTERM grace and 2 s after SIGKILL), inspect (about 0), podman stop (the full 10 s, because the runtime ignores SIGTERM), sandbox delete (a few seconds quiet, many seconds loaded). That is about 13 to 20 s on a quiet host, so a host that is twice as slow, or one slow gateway delete, crosses 30 s. The outer bound and the controller's own bound expire at the same instant, so no stage code surfaces and the step in progress is abandoned. This is a hypothesis from code and from the recorded constants. The hermetic reproduction in Plan 41-01 proves the mechanism (a stop whose stages each stay inside their own bound still returns `REALM_STOPPING` at 30 s); which stage was slow in the Phase 34 window cannot be known, and the live run in Plan 41-02 attributes stages for the fixed build.
- **E-41-11 (O). A stop concurrent with a bring-up.** The registry entry is set before `controller.create` runs (`admitUp`), a client that leaves mid-up does not cancel the daemon's up (Phase 33, `test/daemon/up-disconnect.test.ts`), and, apart from a failed listening server, nothing but a signal or the `down` that empties the registry stops the daemon (a host leaving never sends `down`; only `realm down` does). So a signal during an `up` reaches `controller.stop()` with a create or a start in flight. The controller then reclaims them in parallel with `exec.stop` (`teardownContainer`): `reclaimPendingCreate` waits for the create under one bound and then `destroyUnrecorded` runs under another, `reclaimPendingStart` waits for the start and then `stopStarted` runs, and `SessionExecution.settleCreatesFor` waits up to 15 s for the create. These are sequential inside the controller, so the chain can reach two bounds while the daemon's outer bound is one. The create itself runs up to `OPENSHELL_CREATE_DEADLINE_MS` (60 s). A stop that arrives mid-up and finds the create still running cannot finish in 30 s whatever the stage bounds are. This is bounded by the outer bound and reported as `REALM_STOPPING` by design; it is a second, different way to the same log line. Step 5 of the Phase 34 window follows steps whose status calls returned `active`, so by the plan text this is the less likely explanation of the report [INFERENCE] (OQ-41-02), but it is the one the Phase 33 change made reachable, so the plan characterises it too.
- **E-41-12 (O). `down` has the same arithmetic.** `controller.destroy` runs a stop phase through `exec.stop` and then `exec.destroy`, each under its own `teardownCall`. The CLI's bound for `down`, `CONTROL_TIMEOUT_MS.down = 45_000` in `src/daemon/channel.ts`, was derived as 30 s of teardown + 2 x 5 s reply allowance (the waiter check in `releaseSession`) + 5 s of queue wait, and `test/daemon/main.test.ts` (the test "the CLI down bound outlasts the daemon teardown bound") and `test/daemon/channel.test.ts` (the `down` row of the RT-06 test) pin it. A change of `TEARDOWN_TIMEOUT_MS` moves `down` with it. The documented derivation in `docs/integration/runtime-decision.md` (the C11 paragraph, "10 000 ms of lock wait") no longer matches `downLockWaitMs` (the client bound less the reply allowance, 40 s with the defaults); the phase rewrites that paragraph from the code.
- **E-41-13 (O). Gates that bind this phase.** `src/lifecycle/controller.ts` is 1069 lines and pinned at exactly that in `scripts/check/module-size-allowlist.json`; it may not grow, so this phase does not edit it. `src/daemon/daemon.ts` is 986 lines against the 1000-line limit, so new logic goes in a new module. The gate closure (`scripts/check/gate-closure.mjs`) forbids `src/runtime/session-execution.ts` from the closure of the four gate entries; `src/lifecycle/bounds.ts` and the new leaf module import nothing that reaches `node:child_process`. `src/daemon/channel.ts` keeps a five-import allowlist (P6-D10), so it mirrors constants rather than importing them, with a test that pins equality. The export-usage gate fails a test-only export without an allowlist entry and a stale entry.

### D-41-01. The cause, stated as the phase will record it (TEAR-01)

The teardown bound is the budget of the whole stop of one session, but the stages inside it are sequential and their bounds sum to more than the budget (E-41-05), and one stage, the container stop, always consumes its full grace (E-41-07). A stop of a finished session therefore sits at about half to two thirds of the bound on a quiet host and crosses it when the host or the gateway is slow. Expiry is reported as `REALM_STOPPING` by two timers that fire together (E-41-03), the step in progress is abandoned, and the container waits for the next reap.

What the record must show: the reproduction (a hermetic run of the real `SessionExecution` and the real controller, with scripted stage durations that each stay inside their own bound and a mock clock, ends `REALM_STOPPING` at 30 s on the unchanged code), the arithmetic (the table of E-41-05), and, from Plan 41-02, the measured stage timeline of the fixed build. What it must not claim: that the Phase 34 run was this exact timeline. It is "the cause the code shows, reproduced; the slow stage of that one run is not recoverable".

### D-41-02. One source for the stage bounds, and the teardown bound derived from them (TEAR-02)

A new leaf module `src/runtime/teardown-stages.ts` holds the stage constants that `src/runtime/session-execution.ts` now declares privately (`AGENTOS_STOP_DEADLINE_MS`, `CONTAINER_STOP_GRACE_MS`, `SANDBOX_DELETE_DEADLINE_MS`), the libpod request bound it reads from `src/runtime/libpod-client.ts` (`DEFAULT_REQUEST_TIMEOUT_MS`, `FORCE_REMOVE_STOP_GRACE_SECONDS`), and the derived bounds:

- `SESSION_END_STAGE_BOUNDS_MS`, a frozen object: `createWait` (the S1 wait, 15 s), `agentosStop` (15 s), `containerStep` (inspect 5 s + stop request 5 s + the stop grace; the larger of the stop and remove variants), `sandboxDelete` (15 s).
- `SESSION_END_WORST_CASE_MS`, their sum.

`src/lifecycle/bounds.ts` then defines `TEARDOWN_TIMEOUT_MS = SESSION_END_WORST_CASE_MS + TEARDOWN_MARGIN_MS` with `TEARDOWN_MARGIN_MS = 3_000` (the controller's own synchronous record writes and the timer slack), and its header comment states the real derivation. `src/daemon/daemon.ts` reads the gateway delete deadline of the startup reap from the same module instead of its private `gatewaySandboxDeadlineMs = 15_000`. With the stop grace of D-41-03 the numbers are: 15 + 15 + 12 + 15 = 57 s, plus 3 s = **60 s**. The invariant the original header stated (a stage that has not exhausted its own bound is never cut off by the teardown bound) holds again and is pinned by a test that runs every stage to just inside its bound.

Why derive rather than raise to a round number: the next stage added to the stop would repeat the 2026-10-26 mistake, and a derived constant plus the test that runs the stages to their bounds makes that fail in CI instead of in a live window. Why the margin is 3 s and not a percentage: the margin covers fixed synchronous work, not stage time.

Rejected alternatives: (a) one shared deadline passed down so the stages together cannot exceed 30 s and the container stop is skipped under pressure (the sandbox delete removes the container anyway). It keeps the user-visible bound, but it adds a budget parameter to the execution port or its constructor, cuts stages short on a loaded host (a stop that is slow because the host is slow would be cut earlier, not completed), and cannot be proved by the arithmetic alone. Recorded as a Deferred Idea. (b) Shortening the stage bounds to fit 30 s: the 15 s stage bounds are the reason a slow gateway still gets to finish; with no measurement of a quiet host there is no evidence to tune them down.

### D-41-03. The stop path's container grace: 10 s to 2 s

`CONTAINER_STOP_GRACE_MS` (the libpod stop timeout of `containerStep` in stop mode) becomes 2 000 ms. Reason: the runtime ignores SIGTERM (E-41-07), so the grace buys nothing and costs 8 s of every stop; the force removal of `down` already uses 2 s for the same reason (commit `40684e0`); the AgentOS runner is stopped first. The effect on the arithmetic: S3 falls from 20 s to 12 s, `TEARDOWN_TIMEOUT_MS` from 68 s to 60 s, and the typical stop from about 13 to 20 s to about 5 to 12 s [INFERENCE]. The container is still removed by the sandbox delete that follows.

This is the one behavioural change of the phase that is a tuning decision rather than a correction, so it is a separate, reviewable edit, its own assertion (the stop request carries the grace the constant names) and a single constant: if the owner objects (OQ-41-01), the constant returns to 10 000, `TEARDOWN_TIMEOUT_MS` derives to 68 s, the two literal mirrors in `src/daemon/channel.ts` follow (68 s and 83 s), and every test derives from the constants. It does not change the driver's own 10 s `STOP_GRACE_MS`, which acts on a container that is already exited on this path (Deferred Ideas).

### D-41-04. The outer bound and the inner bounds: who reports what

The daemon's outer `withTimeout` and the controller's `teardownCall` stay equal to `TEARDOWN_TIMEOUT_MS` (a stop is one session's whole budget at both layers). What changes is the order of events for the ordinary slow stop: a stage that runs out of its own bound now reports its own code first. For example a hung sandbox delete rejects `exec.stop` with `AGENTOS_STOP_FAILED` at its 15 s bound (inside the budget), the controller keeps the session `stopping` as it always did, and `daemon.stopped` carries `code=AGENTOS_STOP_FAILED`, which names the family of the failed stage instead of the generic expiry. `REALM_STOPPING` on `daemon.stopped` then means what the controller header says: a real hang that outlived every stage bound, or the mid-up chain of E-41-11. The `daemon.stopped` contract is unchanged: same event name, the `failedTeardowns` count always present, the first failure's catalogue code under `code`, no other field. The value domain of `code` was already "any catalogue code" (E-41-03). The docs name the change.

### D-41-05. The client bound for `down` follows the teardown bound

`CONTROL_TIMEOUT_MS.down` becomes `TEARDOWN_TIMEOUT_MS + 2 x DAEMON_REPLY_ALLOWANCE_MS + 5 000` = 75 000 ms. `src/daemon/channel.ts` mirrors the teardown bound as a private constant with the comment that it is mirrored and not imported (the P6-D10 allowlist), and a test pins `CONTROL_TIMEOUT_MS.down` to the formula over the real constants, so the two cannot drift again. The waiter check in `releaseSession` is unchanged in form (`remaining` against `TEARDOWN_TIMEOUT_MS + replyAllowanceMs`) and keeps its meaning: a `down` that waited more than 5 s behind another request replies `TOOL_TIMEOUT` before it destroys. `downLockWaitMs` becomes 70 s with the defaults and its comment in `src/daemon/sessions.ts` says so. The docs change from 45 s to 75 s in the same places (the "Control request limits" paragraph and the C11 paragraph of `docs/integration/runtime-decision.md`).

### D-41-06. Test seams: an injectable teardown bound, no environment variable

`teardownTimeoutMs` is added to `BuildDaemonHandleOptions` (`src/daemon/seams.ts`; `StartDaemonOptions` extends it), to `CreateRealmHandleOptions` (`src/realm/compose.ts`, passed to the `LifecycleController` deps field that already exists) and read by the daemon's stop path, default `TEARDOWN_TIMEOUT_MS`. It is a constructor option, like `stopDeadlineMs` and the controller's own `teardownTimeoutMs`: production never sets it, tests set a few tens of milliseconds, and no process environment is read. `src/lifecycle/controller.ts` is not edited (E-41-13). The teardown loop of `closeEverything` moves to a new `src/daemon/teardown.ts` as `stopSessions`, which keeps the sequential order, the per-session bound, the health-loop disposal and the counting exactly as they are and returns `{ failure, failedTeardowns }`; this gives `daemon.ts` room (it shrinks) and gives the tests one function to call.

### D-41-07. The tests (the stage chain run to its bounds is the centre)

Hermetic, no network, no real clock wait, runnable as a regular non-root user. Detail is in Plan 41-01; the shape is:

1. **Stage arithmetic against the bound (red on the current code).** The real `SessionExecution` over scripted libpod, runner and supervisor stubs, composed with the fake execution service's `create`, `start` and `probe` so the real `LifecycleController` reaches `active`; `t.mock.timers` for `setTimeout` only; each stage is a held promise the test releases after ticking its scripted cost. Cases: every stage costs its own bound minus 1 ms (the controller must finish and the session reach `unbound`); a typical slow host (agentos 8 s, inspect 3 s, the stop grace, delete 14 s); a hung supervisor stop and a hung delete around a slow container stop (the controller rejects with `AGENTOS_STOP_FAILED` at the sum of the two hung stage bounds plus the slow stage, before `TEARDOWN_TIMEOUT_MS`, and the session stays `stopping`); the relation `TEARDOWN_TIMEOUT_MS` not below `SESSION_END_WORST_CASE_MS`.
2. **The daemon's report (the contract of criterion 4, green before and after).** A real daemon on a real socket with the fake execution service and a small injected bound: a stop inside the bound logs `daemon.stopped` with exactly the keys `event`, `failedTeardowns`, `level`, `ts` and `failedTeardowns` 0; a stop past the bound ends `daemon.stop()` rejecting `REALM_STOPPING` with `failedTeardowns` 1 and `code` `REALM_STOPPING`; a stage failure carries its own code; with two sessions, the first failing, the second is still stopped and the count is 1 with the first code kept.
3. **The mid-up characterisation (green before and after; it pins what exists).** An `up` held at its create and abandoned by its client, then a daemon stop: within the injected bound the stop resolves with the session `unbound` and no container; past the bound it rejects `REALM_STOPPING`, and once the held create is released the late container is destroyed by the controller's orphan path (nothing is left in the fake's resources).
4. **The grace.** The stop request reaches libpod with the grace the constant names (2 000 ms), in stop mode only; the force removal keeps its own 2 s.
5. **The relations.** `CONTROL_TIMEOUT_MS.down` equals the formula over `TEARDOWN_TIMEOUT_MS` and `DAEMON_REPLY_ALLOWANCE_MS`; the channel mirror equals `TEARDOWN_TIMEOUT_MS`.

Red-first: Plan 41-01 Task 2 lands cases 1 (and the relation of case 5 that the old numbers fail) before the fix and records their failure output in the summary as the TEAR-01 reproduction; Task 3 makes them pass.

### D-41-08. The live run (TEAR-02), repeated, with variants

Plan 41-02 adds a gated test that uses the production stack the way `test/integration/production-driver.test.ts` does (the `REALM_LIVE_PRODUCTION` gate and its inputs, `createScenarioEnvironment`, `realmCli`, `findDaemonPids`) and stops the daemon with SIGTERM, which is the path that logs `daemon.stopped` with a registry that still holds the session. A `realm down` empties the registry before the daemon stops, so it reports `failedTeardowns=0` whatever the stages do and proves nothing here (the report's `failedTeardowns=1` can only come from the signal path or from a session left in the registry). Variants, each repeated: (A) stop after a scratch session that ran one exec (N = 5, the acceptance variant); (B) the same under CPU load, N = 3, to recreate a slow host, which the original run may have had (OQ-41-02), with the load readings recorded; (C) a stop in the middle of an `up`, N = 3, an observation that records the outcome and asserts only that the daemon exits inside the teardown bound plus a margin and that the next start reaps what is left. Acceptance for A and B: in every iteration `daemon.stopped` reports `failedTeardowns` 0 with no `code`, the session's container is gone by the time the daemon has exited, the gateway no longer lists the sandbox name, and the residue after the iteration is zero. A per-iteration timeline (daemon signal time, `daemon.stopping` and `daemon.stopped` times from `daemon.log`, container state changes sampled every 250 ms, exit time) goes to the evidence directory; it attributes the stages and is the data for the next bound decision. The same test and its support file import nothing that Plan 41-01 adds, so an optional baseline run on the commit before the fix (E-41-10 reproduced live, or recorded as not reproduced in N runs) uses the same files.

A failing iteration is a result, not a retry: record the first failing assertion, its code and the timeline, run `realm down` for the scratch project, and report it as a finding. No product code is patched inside the window.

### D-41-10. Hygiene constraints for every plan

The rules of `AGENTS.md` and the v6.0 constraints apply: strict TypeScript, `RealmError` with catalogue codes (no new code), a timeout on every async boundary, no silent catch, no suppression comments, `process.env` read only at the three entry edges, no new dependency, no host-local absolute path in a committed file. ### Threat model (summary; each plan carries its STRIDE rows)

- A longer worst-case teardown holds an admission slot as unproven and a `down` caller waiting longer. Bounded and derived; the client bound follows.
- A shorter container grace could cut a process that would have exited cleanly. The runtime ignores SIGTERM, the runner is stopped first, and `down` already removes with a 2 s grace.
- A changed `code` on `daemon.stopped` could break an operator's filter on `REALM_STOPPING`. Documented; the field is unchanged.
- The live window kills a daemon on a shared stack. The pid is found by exact argv match for the compiled daemon entry and the current uid only; one live run at a time under the shared lock; residue snapshots before and after.
- The live evidence could leak paths, identities or environment values. Counts, durations, codes and versions only, kept outside the repository.

### Verification posture

Plan 41-01 is verified by the hermetic suites it adds and the existing daemon, lifecycle and runtime suites, plus the gates. The red-first run is evidence and is recorded. Plan 41-02 is verified by the person's window evidence; no worker or parent runs a production-stack step.

## Existing Code Insights

- The stop of one session is three layers deep and each layer has its own timer: the daemon's `withTimeout` around `controller.stop()`, the controller's `teardownCall` around `exec.stop(...)`, and the stage timers inside `SessionExecution.endSession`. Only the inner ones know the stage; only the outer ones know the session. The fix keeps all three and orders them (inner sum below the two equal outer ones).
- `FakeExecutionService` models create, start, probe, stop and destroy with a delay, a hold gate, a one-shot failure and a hook per operation; its stop has no stage structure, which is why no existing test could see the arithmetic. The real `SessionExecution` needs only stub collaborators for stop (`SessionContainers`: `inspectContainer`, `stopContainer`, `removeContainer`, `info`, `listContainersByLabel`; an `OpenShellRunner`; a `SupervisorFor`), as the F5 and N5 tests of `test/runtime/session-execution.test.ts` show. A composite port (fake create, start, probe; real stop and destroy) lets the real controller reach `active` without the heavy create path.

## Open Questions (none blocks Plan 41-01; OQ-41-02 informs the record)

- **OQ-41-01. The grace change.** Is a 2 s container stop grace acceptable? Default taken: yes (D-41-03). If not, one constant returns to 10 000 and two literals and the docs follow; nothing else changes.
- **OQ-41-02. How the Phase 34 window stopped the daemon.** A signal or a `down`, whether a client request was in flight, the host load and any timestamps. - **OQ-41-03. A per-session stop timing line.** An additive info event with the session's stop duration and code would attribute the next flake from the log alone. Default taken: no (the contract of `daemon.stopped` is the criterion, and the live timeline gives the data for this phase). Revisit if the window finds a slow stage the timeline cannot name.
- **OQ-41-04. Parallel session stops.** With N sessions the stop takes up to N bounds, one after the other. Default taken: leave sequential (behaviour unchanged, no evidence it mattered). See Deferred Ideas.
- **OQ-41-05. `down` runs two teardown calls.** `destroy` is a stop phase and then a destroy phase, each bounded by the teardown bound, so a `down` in the worst case outlasts its 75 s client bound. This phase fixes the single-stop arithmetic only; the `down` worst case keeps the `TOOL_TIMEOUT`-then-resume behaviour the design already has.
