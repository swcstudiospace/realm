# Phase 16 plan 04 (unit O4): bounded re-attach of the Omp plugin to the daemon

Source of the requirement: the planner spec section SANDBOX_OMP_PLUGIN_CONNECTION (planner session 01a194ef), the design-register defaults, and the behaviour-change rule. Context: `16-CONTEXT.md`, section "Decisions added 2026-11-01".

## What "dropped connection" means in this code

The daemon client has no persistent socket. Each request dials, exchanges one line and closes (`src/daemon/client.ts`, `src/daemon/channel.ts`). A dropped connection is therefore observed as a failed request with one of two catalogue codes:
- `REALM_NOT_ACTIVE`: the control socket is absent or refused (channel failure).
- `TOOL_TIMEOUT`: a status read exceeded `GUARD_STATUS_BUDGET_MS`. This is the liveness timeout that stands in for a half-open link.

Every other code is a daemon answer, not a loss of link. A daemon that answers with a refusal is not dropped.

Liveness is the existing repaint poll (`STATUS_POLL_MS`, 2 s), which reads status with a 5 s bound. The poll detects loss within about 2 s.

## Design (defaults from the design register; reversible under C3)

Retry cap 8. Equal jitter. Base delay 1 s. Delay cap 60 s. Attach budget per attempt: the existing `STARTUP_BUDGET_MS`.

Equal jitter, for attempt k from 1 to 8: `ceiling = min(60000, 1000 * 2^(k-1))`, and `delay = ceiling/2 + random() * ceiling/2`. `random()` is injected and must return a value in [0, 1]. The delays therefore lie in [ceiling/2, ceiling]. Full jitter is not used, because it can yield near-zero delays.

Re-attach is behind a configuration key. The key is the environment variable `REALM_OMP_REATTACH`. The Omp extension edge (`src/omp/extension.ts`) is the only module that reads the environment, so the plugin receives the setting as an option.
- Unset or `0`: disabled. Behaviour is exactly today's: no wait timer, no re-attach, and the poll paints `REALM_NOT_ACTIVE` as before.
- `1`: enabled.
- Any other value: the extension fails at load with `SCHEMA_INVALID`, the same way an invalid config fails.

The default is disabled until the owner records the live validation (see "Owner validation" below).

## Status mapping (existing names, not a parallel set)

The repository's connection state type is the six-name `State` in `src/core/states.ts`. The spec's eight names are mapped onto it, and no name is added to the frozen table (D-11).

| Spec name | Existing name used | How it reads on the status item | Notes |
|---|---|---|---|
| UNCONFIGURED | `unbound` | `realm disconnected · no workspace` | The session always has a cwd, so this is not reached by re-attach |
| CONNECTING | `connecting` | `realm disconnected · connecting` | Attach in progress |
| HANDSHAKING | (within `connecting`) | none | No separate handshake exists in the control protocol; see open questions |
| CONNECTED | `active` | `realm active` | Set after a successful re-attach |
| DEGRADED | `degraded` | `realm active [degraded]` | Daemon-reported; re-attach does not create it |
| RECONNECTING | `connecting`, with a host-side sub-state `reconnecting` | `realm disconnected · connecting`, plus a notify with the attempt number and next attempt time | The frozen table has no wait state, so the wait is host-side and paints as connecting |
| FAILED | `error` | `realm disconnected · <catalogue code>`, plus a notify with the action `/realm-retry` | Terminal until the user acts |
| DISABLED | (no state) | flag off means today's behaviour | |

The host-side sub-states are plugin-internal: `off` (flag disabled, no states tracked), `linked`, `reconnecting`, `attaching`, `failed`. Legal transitions are checked by a pure function, `reattachTransitionAllowed(from, to)`:
- `linked` to `reconnecting`, `attaching`
- `reconnecting` to `attaching`
- `attaching` to `linked`, `reconnecting`, `failed`
- `failed` to `attaching`

Every other transition is rejected, and the rejection is reported through `ctx.ui.notify` with the two names. Nothing is applied.

## Retryable and non-retryable outcomes

Retryable attach codes: `REALM_NOT_ACTIVE`, `TOOL_TIMEOUT`, `STARTUP_BUDGET_EXCEEDED`, `DAEMON_START_TIMEOUT`.

Not retryable, so FAILED at once with no wait: any refusal the daemon answered (for example `PODMAN_MISSING`), `SCHEMA_INVALID` (a malformed or incompatible peer), and `POLICY_DENIED` (the host tool set refused the mode). These are reported with their own codes.

### T3. Loss detection and the wait
- Files: `src/omp/plugin.ts`
- Action: when enabled, a poll status read that fails with a code in `LINK_LOST_CODES` triggers `onLinkLost`. So does a guarded status read that fails the same way, and so does a Realm `read`, `list`, `exec` or `write` call that fails the same way. `onLinkLost`: (a) does nothing if the sub-state is already `reconnecting` or `attaching`, so repeated signals never arm a second timer; (b) otherwise sets the client to null and closes it, transitions `linked` to `reconnecting`, paints the connecting label, and arms one wait with `armTimer`. The wait's delay is `equalJitterDelayMs(attempt+1, ...)`. The wait's end action settles without attaching, so shutdown cancels it through the existing `endSession` path. Notify once per scheduled attempt with the attempt number, the cap and the next attempt time.
- Done when: tests cover one drop producing one wait, and repeated signals during the wait producing none.

### T4. Attempts, FAILED, and user retry
- Files: `src/omp/plugin.ts`
- Action: when a wait expires, check that the session is still current, the sub-state is still `reconnecting` and the counter still matches. Then transition to `attaching` and call the existing `attach(session)`. Outcomes: `attached` transitions to `linked` and resets the counter to 0. `superseded` does nothing further. `failed` with a retryable code transitions to `reconnecting` and arms the next wait while the counter is below the cap, and transitions to `failed` with a notify naming the code and the action `/realm-retry` once the counter reaches the cap. `failed` with a non-retryable code transitions to `failed` at once. The existing `realm-retry` command cancels a pending wait (`disarmTimer`), resets the counter, transitions to `attaching` (from `linked`, `reconnecting` or `failed`) and runs the same outcome handling. With the flag off, the retry command is unchanged.
- Done when: the retry-exhaustion and non-retryable tests in T6 pass.

### T5. In-flight Realm writes after a loss
- Files: `src/omp/plugin.ts`
- Action: when enabled, a Realm call whose `tool` is `write` or `exec` (mutating) and whose daemon call fails with a code in `LINK_LOST_CODES` rejects with `AUDIT_OUTCOME_UNKNOWN` (the existing catalogue code "whether the call took effect is unknown", not retryable). It is never dispatched again by the plugin. Read-only calls keep their current code. With the flag off, nothing changes.
- Done when: the test in T6 passes.

### T6. Tests in `test/omp/plugin.test.ts`
- Action: add these deterministic tests. They use the existing manual `FakeCtx` timers, the `FakeDaemon` double, and a seeded PRNG (mulberry32 with a fixed seed) passed as `random`. No wall clock is read. Add a `failStatus` switch to `FakeDaemon` so it can throw a chosen code.
  - R1 "a dropped link is detected on the poll, paints connecting, and re-attaches after one jittered wait to active": one wait armed within [500, 1000] ms for attempt 1; firing it calls `attachDaemon` a second time and paints active.
  - R2 "delays grow with equal jitter and cap at 60 s": with `random` always 1, the eight waits are 1000, 2000, 4000, 8000, 16000, 32000, 60000, 60000; with `random` always 0 they are half of each; with the seeded source every wait lies within its bounds.
  - R3 "retry exhaustion reaches FAILED with the catalogue code, notifies the action, and leaves no pending timer": `attachDaemon` always rejects with `REALM_NOT_ACTIVE`; the total attach calls are 1 plus 8; the label is disconnected with reason `REALM_NOT_ACTIVE`; a notify names `/realm-retry`; every armed timer is fired or cleared, and none is pending.
  - R4 "a non-retryable refusal reaches FAILED at once with no wait": `attachDaemon` returns a refusal with `PODMAN_MISSING`, or rejects with `SCHEMA_INVALID`; no wait is armed.
  - R5 "shutdown during a backoff clears the wait and starts no attach": after the drop, `session_shutdown`; the wait's handle is in `ctx.cleared`; no further attach call occurs.
  - R6 "a second loss signal during a wait arms no second timer; realm-retry cancels the wait and attaches once; the counter resets": assert one pending wait throughout, the cancelled handle recorded, and one attach from the retry.
  - R7 "with the option absent, a drop behaves exactly as today": no wait is armed, `attachDaemon` is called once, and the poll paints `REALM_NOT_ACTIVE`.
  - R8 "an in-flight write that loses the link reports AUDIT_OUTCOME_UNKNOWN and is not dispatched again": the daemon rejects one `write` with `REALM_NOT_ACTIVE`; the outcome code is `AUDIT_OUTCOME_UNKNOWN`; the dispatch count is 1.
  - R9 "a hung status read is bounded by GUARD_STATUS_BUDGET_MS and counts as a loss; every wait stays at or below 60 s": `hangStatus` is set, the timer armed has `GUARD_STATUS_BUDGET_MS`, and it fires to a `TOOL_TIMEOUT` loss.
  - R10 "re-up is idempotent": a re-attach adds no tool registration and no second poll interval (`ctx.intervals.length` stays 1), and `up` is called again only by the attach path.
  - R11 "transitions outside the table are rejected and reported": `reattachTransitionAllowed("failed", "reconnecting")` is false, and the plugin reports the rejection through `ui.notify`.

Steps for the owner: with `REALM_OMP_REATTACH=1` set in the Omp host environment, stop the daemon while Omp is attached; the status item must read `realm disconnected · connecting` and then re-attach to `realm active` within the first wait. ## Open questions this unit does not close
- The spec's handshake, protocol-version and credential requirements have no counterpart in the repository's control protocol (`src/daemon/channel.ts` has no version field and no handshake). The socket is protected by its directory and file modes. O4 does not add a handshake. Under the spec's rule this is a BLOCKER for the handshake portion, and it needs the owner's decision.
- In-flight control requests are bounded by `CONTROL_TIMEOUT_MS` and cannot be aborted on shutdown, because `sendRequest` takes no abort signal. Adding one would change `src/daemon/channel.ts`, which this unit does not own.
- The message-level validation rules (malformed threshold to DEGRADED, flood limits, request IDs for replay) are not implemented here.
