<objective>
Give the daemon a way to hear how every host's boot went, record it with the baseline mechanisms Realm already has (metrics, the structured logger, the hash-chained audit), and bound what a hostile host process can do through it.

Purpose: Phase 23 asks for correlation ids, metrics counters over the control socket and audit events for boot. The daemon is the one process every host talks to and the one single-writer audit appender (the audit writer has no cross-process lock: `src/audit/log.ts:139-151`), so the receiving side lives there. The sending side (the host observer) is 23-03; this plan proves the receiver with raw control requests.
Output: `src/host/boot-report.ts`, the `host-boot` control method, `src/daemon/host-boot.ts`, `recordHostBoot` and the optional snapshot keys, one `case` in `daemon.ts`, tests.
Non-goals: no host-side sender, no presence write, no CLI change (`realm metrics` prints the new keys as it prints any snapshot), no change to the `up` wire, `DaemonClient` or any fake of it, no change to `src/runtime/**` (the sandbox's bind set is untouched), no docs (23-03).
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Risk |
| --- | --- |
| Host process (same user) → control socket (`host-boot`) | Flood, malformed or oversized frames, lies about host, phase or code |
| Report fields → log, metrics, audit | Injection, secret leakage, cardinality growth, audit chain growth or fork |
| Daemon → audit file | A second writer forks the hash chain; a failed append hides the line |
| Sandbox workload → control socket | Forge reports or exhaust the bucket |
| New method → old clients | A strict snapshot validator rejects the new keys |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
| --- | --- | --- | --- | --- | --- |
| T-23-08 | Denial of service | `host-boot` handler | high | mitigate | Task 3: the token bucket is taken before the parse (60, one per second); the existing 1 MiB line cap and per-socket read timeout bound the read (`MAX_CONTROL_LINE_BYTES`, `readControlLine`); the handler does O(1) work and one synchronous audit append for at most three phases; the flood test asserts `status` still answers within 5000 ms and the audit file has at most 60 lines. |
| T-23-09 | Spoofing | report content | medium | accept and bound | Reports are self-reported and advisory: nothing authorizes on them (the daemon gates read `Policy` and the selection, not a host id); every doc and the audit `path` triple say so; the vocabulary is closed, so a lie can only select a label, never inject text. Same-user code that can dial the 0600 socket can already call `tool` and `down`; this adds no power. |
| T-23-10 | Tampering | boot audit chain | high | mitigate | Task 3: the daemon is the only writer (one process, synchronous `appendAudit`), so `seq` and `prev` cannot fork; the reserved id `host-boot` is separate from `host-plugins`, written by the CLI; a failed append is `AUDIT_WRITE_FAILED` and logged, never silent; `realm audit verify` passes on the file in tests. |
| T-23-11 | Information disclosure | log, audit, metrics | medium | mitigate | Tasks 1 and 3: only closed-vocabulary strings, integers and a boot id cross; no path, session id, daemon reason or notice; the logger and `appendAudit` redact as for every other line; a token-shaped boot id is hashed in the audit and redacted in the log (tested); `capabilitiesDenied` lists capability names and catalogue codes only. |
| T-23-12 | Denial of service | metrics cardinality and snapshot size | medium | mitigate | Task 2: closed key sets (20 hosts, 3 transports, 6 phases, the catalogue codes) and a hard cap of 256 rows; excess keys are ignored. |
| T-23-13 | Spoofing / Tampering | malicious workload | high | mitigate | The workload cannot reach the control socket or the state directory (not mounted; the Phase 19 bind set is unchanged and no file of this plan touches `src/runtime/**`), so it cannot send a report, fill the bucket or write the chain. Workload-controlled text (directory names, tool output) is not a field of any report. |
| T-23-14 | Denial of service | mixed-version snapshots | low | accept | A pre-upgrade `realm metrics` binary reading an upgraded daemon sees the unknown key and fails `SCHEMA_INVALID` (the old validator is strict). Same package, same release: `realm down` then any command restarts the daemon on the new build. The new validator accepts both shapes, so the reverse direction works. Written in the docs by 23-03. |

Accepted residuals: self-reported labels (T-23-09); a boot that never reached a daemon leaves no daemon-side record (OQ-23-02).
