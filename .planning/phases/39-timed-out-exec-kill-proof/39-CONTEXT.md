## Phase Boundary

Decisions fixed elsewhere and not reopened here: D-v6-3 (a live closeout test where a sleeper outlives the timeout window must show the sleeper dead, not merely finished, within a bound, with a proof independent of the sleeper's own run time; if the sleeper survives, the kill path is fixed), the owner authorization of 2026-11-18 that live windows are authorized when a phase needs them under the same rules as before (shared live lock, `realmlive` account, residue checks before and after, evidence outside the repository, a person runs every production-stack step), the pinned OpenShell exec form (D-92, D-93: `openshell sandbox exec --name realm-SESSION --workdir /workspace --no-tty --no-login-shell -- WORKLOAD`), the per-call bound (`TOOL_CALL_TIMEOUT_MS` 30 s, runner deadline 28 s; D-91, D-101), and the error catalogue (29 codes, no new code).

This phase answers one question, "what does `TOOL_TIMEOUT` do to the process the exec started?", from the code and from a live run, and then makes the answer true. The code answer is already in hand (E-39-02): `TOOL_TIMEOUT` kills the local `openshell sandbox exec` client and its process group, and nothing else. It never signals a process inside the sandbox. The upstream evidence (E-39-04, E-39-05) says the OpenShell gateway and supervisor of the pinned revision do not signal it either. So the phase plans the fix as well as the proof: an in-sandbox watchdog around every dispatcher exec (D-39-02), a hermetic test of the kill semantics, a live proof that does not depend on the sleeper's own run time (D-39-08), and one live window that runs the proof twice, once on a build without the fix (the evidence that the sleeper survives) and once with it.

Plan 39-01 builds the live proof (a process-state probe that runs inside the sandbox, scenario C rewritten, scenario C2 recording the limit, scenario D checking that egress still works through the wrapper). Plan 39-02 adds the watchdog and its hermetic tests. Plan 39-03 is the blocking-human live window and the record (docs, the F-3 closure statement, the summary).

Out of scope: any change to the `TOOL_TIMEOUT` reply, its `retryable` flag, the 28 s and 30 s bounds, the audit line or the catalogue; a per-call timeout parameter (D-101 keeps it a constant); a cgroup per exec or any change inside OpenShell (upstream, not ours); the AgentOS runner child and the probe, which are long-lived execs and stay unwrapped; a doctor check for the watchdog binary (the doctor cannot exec into the sandbox); Phase 41's teardown work; any edit of the archived v5.0 ledger (history; Phase 27 set that rule), so finding F-3 is closed by the record this phase writes (D-39-10), not by editing the old file.

### Evidence (each fact: source, read or observed date 2026-11-18, tier)

Tiers: **O** observed by reading a repository file, **R** a recorded owner statement or verification record, **M** measured on this host in this planning pass, **W** read from the web (upstream source of record), **I** inference (also marked [INFERENCE]).

- **E-39-01 (O, I).** Finding F-3 (live closeout C, window run 3, main at 04ca807, 2026-11-18): the exec of `sleep 47` answered `TOOL_TIMEOUT` after 28083 ms; the sleeper was visible 409 ms after the call started; after the reply it was listed on 13 consecutive polls (1 s interval) and absent on the next. The record itself says the test cannot tell a kill from the sleeper ending by itself and calls it an evidence limit, not a defect. [INFERENCE] The arithmetic favours the sleeper ending by itself: it started about half a second into the call, so it had about 47 - 28.1 = 18.9 s of life left at the reply; 13 polls at a 1 s interval plus the cost of each probe (a node exec in the sandbox, several hundred milliseconds) is about 18 to 19 s. If the timeout had killed it, the first poll after the reply would have found nothing. This is a reading of the numbers, not a measurement of the survival; the baseline run of Plan 39-03 measures it.
- **E-39-02 (O).** What `TOOL_TIMEOUT` does. `ToolDispatcher.#exec` (`src/tools/dispatch.ts`, lines 236 to 262) calls `runSandboxExec(runOpenShell, sessionId, workload, TOOL_CALL_TIMEOUT_MS - EXEC_RUNNER_MARGIN_MS)`, that is a 28000 ms runner deadline, inside a `withTimeout` of 30000 ms that is only a backstop. `runSandboxExec` (`src/runtime/session-execution.ts`, line 749) builds the argv with `buildExecArgv` and runs it through the injected runner. The production runner is `spawnOpenShellRunner` (line 683): it spawns the `openshell` binary with `detached: true` (its own process group), arms a timer at `timeoutMs`, and on expiry `killProcessTree(child)` (line 634) sends SIGKILL to the group and to the child, then rejects with an `OpenShellRunnerError` of kind `timed-out`, which `runSandboxExec` maps to `TOOL_TIMEOUT`. The child is the OpenShell CLI, a gRPC client. The workload runs elsewhere, inside the sandbox, under the gateway and the supervisor, so the kill reaches the client and its group and nothing else. No code path signals a process inside the sandbox. The comment above `runSandboxExec` ("a timed-out call keeps nothing running") is true only of the local client.
- **E-39-03 (O, M).** The realm never passes `--timeout` to `sandbox exec`: the pinned argv of `buildExecArgv` (`src/runtime/openshell.ts`, line 259) has `--name`, `--workdir`, `--no-tty`, `--no-login-shell` and no other flag, and `docs/integration/runtime-decision.md` (Exec verb pin, D-93) lists `--timeout` as an unused flag of the CLI. Measured: `openshell sandbox exec --help` on the installed 0.1.5 shows `--timeout` ("Timeout in seconds (0 = no timeout)", default 0). The flag is enforced by the gateway; see E-39-04 for what that does.
- **E-39-04 (W).** Upstream issue NVIDIA/OpenShell 5042, "ExecSandbox processes keep running after execution_timeout and after the client disconnects" (open, labelled triage-needed, opened 2026-10-29). It is reported against OpenShell v0.1.5 at revision bdb956f, which is the revision the realm pins (`sandbox/expected-digests.json`, `openshellRevision` bdb956f2cd65). Reproduction: an exec of `sleep 600` with a 5 s execution timeout; the client stream ends after 5 s and the `sleep 600` is still running in the workload afterwards (seen 8 s later). Its acceptance criteria (the process tree is terminated on timeout, and on client cancel or disconnect) are unchecked. The report used the Docker compute driver; the realm uses its own Podman driver. [INFERENCE] The exec path (gateway to supervisor over SSH) is the same code, so the same behaviour is expected here; the baseline run decides.
- **E-39-05 (W).** Upstream issue NVIDIA/OpenShell 3159 (closed 2026-10-01), "let the caller terminate a sandbox exec command and everything it spawned". Its analysis at the revision it names (v0.0.116): there is no pid, exec id, signal or kill call in the exec request or event; the supervisor starts the command with `/bin/bash -c` and no process group or cgroup of its own; closing the channel or the input drops the senders and aborts the output tasks without signalling the child; the gateway's timeout sends exit code 124 to the client and returns without telling the supervisor. The maintainers' answer in that issue: callers should not expect the processes of an exec to exit when the caller does (the same as `podman exec` and `kubectl exec`), and should supervise inside the sandbox themselves. So in-sandbox supervision is the supported pattern, not a stopgap.
- **E-39-06 (W).** Upstream issue NVIDIA/OpenShell 4946 (open, opened 2026-10-26, against 0.1.5): when an SSH connection to a sandbox ends without closing its channels, the processes started for those channels keep running, and after enough orphans (62 in the report) every new exec or shell request fails with "failed to start boundary exec". It also states that closing a channel normally does terminate the channel's process, which differs from the reading in E-39-05. The two upstream accounts disagree, so the live baseline is required (OQ-39-04). The impact is the reason this is a defect, not only an evidence gap: repeated timed-out execs that leave processes behind can make the sandbox refuse new execs.
- **E-39-07 (M).** GNU coreutils `timeout` 9.4 on this host (a regular process tree, 2026-11-18): `timeout --kill-after=1 -- 1.5 sh -c 'sleep 311 & sleep 312; wait' MARKER` exited 124 and left no `sleep 311` or `sleep 312` (the background job and the foreground job both died, so the signal reaches the whole group `timeout` makes); a child that ignores SIGTERM (`trap "" TERM; sleep 313`) was killed after the grace and `timeout` exited 137; a child that started its own session (`setsid sleep 314 &`) survived (the limit, D-39-05); a command that exits 124 or 137 by itself is indistinguishable by exit code from a timeout; a missing command gives exit 127 with a message from `timeout`. Option order matters: `--` must come before the duration (`timeout --kill-after=1 -- 1.5 CMD`); with `--` after the duration, `timeout` tries to run a command named `--`. The image's coreutils is Debian bookworm's (9.1); the semantics used here are older than both versions, so the same behaviour is expected; the window verifies it in the image (OQ-39-01).

### Decisions

- **D-39-01. The kill path is client-side only, so the fix is planned unconditionally, and the baseline run is still the first live step.** The code (E-39-02) and the upstream record (E-39-04, E-39-05) say a timed-out exec leaves its process tree running in the sandbox. The roadmap's condition ("if the sleeper survives in a first run, fix the kill path") is met by running the new proof on a build without the fix first (D-39-09). If that baseline run shows the tree dead (OQ-39-04), the plan stops at Plan 39-03 Task 3 and the owner decides whether the watchdog stays as defence in depth (it still bounds orphans after a client loss, D-39-05) or is dropped; the proof and the F-3 closure then rest on the baseline result.
- **D-39-02. The fix is an in-sandbox watchdog: GNU `timeout`, by absolute path, in front of every dispatcher exec workload, argv form and shell form.** New pure module `src/runtime/exec-watchdog.ts` with one export, `watchdogWorkload(workload, runnerDeadlineMs)`, returning `["/usr/bin/timeout", "--kill-after=1.5", "--", "28.5", ...workload]` for a 28000 ms deadline (the numbers come from D-39-03; `--` comes before the duration, E-39-07). `runSandboxExec` calls it and passes the result to `buildExecArgv`, so the pinned form, its forbidden-flag pins and the runner child and probe argvs stay as they are (E-39-11, E-39-13). The user's argv follows the duration verbatim and is never reparsed as options. Why `timeout`: it already does what is needed (its own process group, SIGTERM then SIGKILL with a grace, the group signalled as a whole, exit 124 or 137), it needs no change to the digest-pinned image, and it is the pattern the OpenShell maintainers name (E-39-05). Rejected: (a) the OpenShell `--timeout` flag: enforced at the gateway only and reported not to stop the process (E-39-04); (b) a second cleanup exec after the timeout that sweeps `/proc`: it needs an identity for the tree (the process list of the sandbox also holds the AgentOS runner and any concurrent exec), the upstream issue calls that sweep racy by construction, and it does nothing when the daemon dies first; (c) a node supervisor script through `node -e`: no coreutils dependency, but more code to get right (signals, group, exit status), and the parent of the user's command would be node, the one binary the egress policy names; (d) a realm supervisor binary baked into the image: a rebuild of the digest-pinned image, new digests and a supply-chain review, out of proportion for a process group kill.
- **D-39-03. Timing.** The reply stays the client-side kill at 28000 ms (E-39-02, unchanged). The watchdog sends SIGTERM at the runner deadline plus 500 ms (`28.5`, a constant `WATCHDOG_MARGIN_MS` of 500), measured on the sandbox clock, and SIGKILL 1500 ms later (`WATCHDOG_KILL_GRACE_MS` of 1500) for a process that ignores TERM. Why later than the client: the sandbox clock starts after the client spawned (the in-sandbox start latency L was about 0.4 s in F-3), so the watchdog cannot fire before the client's timer except through a stall of the daemon's event loop longer than the margin plus L; and a watchdog that fired first would end the exec with exit 124 or 137 before the client gave up, which a caller could not tell from the command's own status. Worst case with an ordinary L: the tree is dead 0.5 s plus L after the reply when it handles TERM, and 2.0 s plus L after the reply when it ignores TERM. The stated bound of this phase: a timed-out exec's process group is dead within 15 s of the `TOOL_TIMEOUT` reply (the tested bound, covering a loaded host) and normally within 3 s. After a loss of the client (the daemon crashed or was killed mid-exec) the group still ends 30 s plus L after the exec started, which the old path never did.
- **D-39-04. A stall fallback keeps the reply unchanged.** `runSandboxExec` measures the time the run took on an injectable monotonic clock (default `performance.now`); a run that resolves with an elapsed time at or above the runner deadline is `TOOL_TIMEOUT`, whatever its exit code. It can only happen when the client timer was late (a stalled event loop) and the watchdog's exit 124 or 137 arrived first; a call that resolves earlier is a normal result and keeps its exit code, so a command that exits 124 by itself at 5 s is still `exitCode: 124`. No new catalogue code.
- **D-39-05. What the guarantee covers, and what it does not.** `timeout` runs its command in a new process group and signals the group: the command, a shell and its background jobs and helpers die; a process that changes its own group or session (`setsid`, a daemonizing double fork) is not covered (E-39-07). That limit is documented, not fixed (a cgroup per exec would need OpenShell, Deferred Ideas). Scenario C2 records the limit live so the docs state a measurement. The AgentOS runner is outside the group (it is another exec chain) and must survive a timeout: scenario C asserts the session stays usable.
- **D-39-06. The contract for callers is unchanged, and the observable differences are named.** The `TOOL_TIMEOUT` reply (retryable, no cause code), the 28 s runner deadline, the 30 s backstop, the audit lines (E-39-12) and the catalogue (29 codes) do not change. Exit codes pass through `timeout` unchanged, except: a command that cannot be started now reports exit 127 with `timeout`'s message ("failed to run command") on stderr, and 126 for a command that cannot be executed; a command killed by a signal reports 128 plus the signal, the way a shell does. Scenario C records the exit and stderr of a nonexistent command on both builds so the docs state the before and after (Plan 39-03 Task 4).
- **D-39-07. Image requirement.** The sandbox image must provide `/usr/bin/timeout` (coreutils). The realm's own image (Debian bookworm slim) has it, [INFERENCE] until scenario C shows it. A custom image without it makes every exec fail with exit 127 instead of running unsupervised, which is the fail-closed direction. It is documented in the image section of `docs/integration/openshell.md`. There is no doctor check (the doctor cannot exec into the sandbox). If the pinned image turns out not to have `timeout`, the plan falls back to design (c) of D-39-02 with the same constants; that is a stop for the owner, recorded in Plan 39-03 Task 3.
- **D-39-08. The live proof (EXEC-01), independent of the sleeper's own run time.** Scenario C becomes: the sleeper is `sleep 300` (and a background `sleep 301` in the same shell), far longer than the observation window, so it cannot end by itself during the test (the window is at most 40 s for the reply plus 15 s for the death, 55 s of a 300 s run). The process state is read inside the sandbox through a `/proc` probe (a node script run by an argv exec) that lists every process of the tree by three independent rules: a unique marker in its argv, the exact sleeper argvs, and membership of a process group seen in flight, plus all descendants by parent id; identity is the pid and the start time (field 22 of the stat file), so pid reuse cannot pass or fail the check; the probe excludes itself and its ancestors; a zombie is dead but reported. Before the exec: none (negative control). In flight: at least three members sharing a group, including both sleepers (positive control). After the `TOOL_TIMEOUT` reply (asserted retryable, between 25 and 40 s): poll every 500 ms for at most 15 s until no member is running, record the time of death after the reply, then re-check once more 3 s later, then a following `exec` of `echo ok` exits 0, and `realm mcp` exits 0 when its stdin closes. The test also asserts the independence explicitly: the death was observed with at least 200 s of the sleeper's natural life left. The failure messages carry the surviving members with their states.
- **D-39-09. Baseline first, one window, two trees.** Plan 39-01 lands before Plan 39-02, in its own commits. The window builds two trees: BASELINE (the last commit of Plan 39-01, which has the proof and not the watchdog; `src/runtime/exec-watchdog.ts` must not exist in it) and FIXED (the head with both plans). Step A runs scenario C on BASELINE and expects it to fail at the death assertion with the sleepers still running at the bound (that is the survival evidence); Steps B to F run on FIXED. The baseline failure is the expected result, recorded as such; it is not a defect of the test.
- **D-39-10. Where finding F-3 is closed.** The archived ledger (`36-DISPOSITIONS.md`) is history and is not edited. Plan 39-03 writes the closure into `docs/integration/openshell.md` (a dated Phase 39 paragraph after the Re-verification window paragraph, and the scenario 7 and scenario C descriptions), `docs/integration/runtime-decision.md` (an addendum to D-91 and D-93), `docs/policy-reference.md` (the constants), and `39-03-SUMMARY.md`; the verifier's `39-VERIFICATION.md` states what the proof shows and its limits; the orchestrator updates REQUIREMENTS, ROADMAP and the audit pointers. The statement says what is proved (the process group of the exec, on the pinned image, on one stack, one run per scenario) and what is not (processes that left the group, other images, other OpenShell revisions, other hosts).
- **D-39-11. Conventions.** The new module imports nothing from `node:child_process` and nothing from `src/core/policy.ts`, `src/core/states.ts`, `src/core/errors.ts` or `src/contract/validate.ts` beyond `makeRealmError` from `src/core/errors.js` (allowed: the closure rule forbids the reverse); it has one export, used by `session-execution.ts`, so the export-usage gate needs no allowlist entry (tests pin the numbers as literals, not through exported constants). The edit of `src/runtime/session-execution.ts` is `runSandboxExec` and its comment only. No `!` marker: the contract is unchanged and the shipped image has the binary; a custom image without it is OQ-39-03. Commit type `fix(runtime)` for the fix, `test(integration)` for Plan 39-01, `docs(integration)` for the record. The test taxonomy test forbids test file basenames that contain mcp or acp; the new files are `test/runtime/exec-watchdog.test.ts`, `test/integration/exec-kill-proof-helpers.test.ts` and `test/support/process-tree-probe.ts`.
- **D-39-12. The hermetic proof uses the real `timeout`.** The behaviour that matters (group kill, escalation, exit 124 and 137, the option order) lives in coreutils, so `test/runtime/exec-watchdog.test.ts` runs the exact argv from `watchdogWorkload` against a real local process tree (the host's `/usr/bin/timeout`, a shell with a background helper, a TERM-ignoring child, an unrelated sibling that must survive). A fake cannot show the kill. The test fails without the fix in the sense that matters: with the old argv (no wrapper) the same tree is not signalled by anything but the test's own cleanup, which the test shows as a control. Tests run as a regular non-root user (no root-only call) and every fixed wait goes through `scaledMs` (`test/support/timing.ts`).
