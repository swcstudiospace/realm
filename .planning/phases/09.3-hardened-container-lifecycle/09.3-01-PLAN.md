## Constraints

- The verifier `src/runtime/hardening.ts` is reused unchanged. Its 14 properties and profile values are not edited in this phase. A change to them is a re-plan.
- Kernel capability evidence is read on the host, from `/proc/<State.Pid>/status`, after start. The read is fail-closed.
- The container's entry point is `/opt/realm/bin/realm-helper idle`, the only process before `StartAgent` (phase 9.5).
- Only the libpod REST API is used. No `podman` CLI call (PD-11).
- Libpod REST paths are versioned (`/v5.7.1/libpod/...`), as the spike used. Routes are confirmed against 5.7.1; the version probe (`src/runtime/podman-version.ts`) refuses other versions.

## Tasks and waves

### Wave 0 (blocking check, read only)

- T0, digest confirmation. The records show two digests for the node 24 alpine base: one in the spike's G2 inspect (the digest of the container image the spike ran) and one in the decision D-016 (the base digest for the derived image). Resolve which value is the image index and which is the platform manifest, with `podman image inspect` and the registry's manifest, and record the value to pin in the SUMMARY. Check: one pinned reference is recorded, and the libpod inspect of a container from it reports the same digest. Blocks T4.

### Wave 1 (parallel: disjoint files)

- T1, libpod create and start. Extend `src/runtime/libpod-client.ts` with `createContainer(spec)` and `startContainer(id)`, and their routes in `src/runtime/libpod-routes.ts`. The spec sets: no `privileged`; `cap_drop` as requested (the Podman record of "ALL" expands, so the check reads kernel evidence and not this field); `cap_add` empty; `security_opt` `no-new-privileges`; `read_only` true; tmpfs `/tmp` and `/run`; `pids_limit` 512; memory 1 GiB; `nano_cpus` 2 CPU; network `none`; mounts `/workspace` read-write and `/realm-state` read-only, both binds from the bound paths only; the entry point above; labels `openshell.managed=true`, `openshell.ai/sandbox-name`, `openshell.ai/isolation-role=sandbox`. No socket is mounted. Check: unit tests against a fake HTTP server (see T6).
- T2, lifecycle. Add `src/runtime/driver/lifecycle.ts` with three functions:
  - `create(spec)`: `createContainer`, `startContainer`, inspect, read kernel capability sets for `State.Pid` (T3), `verifyInspect(inspect, binding)`. On any failure: `removeContainer(id, {force: true})`, then throw `HardeningFailedError` (existing class, `session-execution.ts`) naming the failed property. A `State.Pid` of 0 fails `cap-drop`.
  - `delete(sandboxName)`: stop, force-remove the container, delete the launch and active files for that sandbox in the secret directory.
  - `startupSweep()`: `removeAllRealmContainers` (existing, `sweep.ts`) before the driver accepts any request.
- T3, shared kernel-capability reader. Move `readHostProcStatus` and `attachKernelCaps` from `src/runtime/session-execution.ts` into a new `src/runtime/kernel-caps.ts`, and import them from both files. This removes a would-be import cycle (the driver must not import `session-execution.ts`). Check: `session-execution.test.ts` passes unchanged (behaviour is the same).
- T4, derived image (HC-08, PD-16). After T0 and owner approval, build the derived image from `sandbox/Dockerfile` (phase 9.2) in the realm account's rootless store. Disk guard: 8 GiB free before the build. Record the image digest, its size, and the helper SHA-256 in the realm runtime configuration, not in repository documentation. Rollback: `podman rmi` the image.
- T5, labels. Check that a container created by T2 is found by `listContainersByLabel(OPENSHELL_MANAGED_LABEL_KEY, "true")` and by the sandbox-name label. This keeps `SessionExecution`'s existing lookups working.

### Wave 2 (after wave 1)

- T6, tests.
  - `test/runtime/libpod-create.test.ts`: request bodies for create and start match the spec; route versions are pinned.
  - `test/runtime/driver-lifecycle.test.ts`: fourteen cases, one per property. For each case, a recorded good inspect is mutated in exactly one field, and `create` must fail naming that property and must call `removeContainer` with `force`. One more case: `State.Pid` 0 after start fails `cap-drop`. Plus: `delete` removes launch and active files; `startupSweep` removes labelled orphans before it resolves.
  - `test/runtime/kernel-caps.test.ts`: parses the five sets from a sample status text; a missing set fails closed.
  - Check: all of the above run under `npm test` with no host dependency (the libpod fake is an in-process HTTP server).

## Acceptance

1. Given the pinned image and a valid spec, When `create` runs on the host, Then one container exists whose PID 1 is `realm-helper idle`, whose five kernel capability sets are zero, and for which `verifyInspect` returns no failures (PRD-CTR-01).
2. Given any single one of the 14 properties mutated in the inspect (test seam), When `create` runs, Then the container is force-removed, the error names that property, and no workload has been started (PRD-CTR-01).
3. Given `State.Pid` is 0 after start, When `create` runs, Then it fails closed on `cap-drop` and removes the container (PR-06).
4. Given a created sandbox, When `delete` runs, Then no container named for the sandbox remains and its launch and active files are gone (PRD-CTR-02, spike G5).
5. Given a realm-labelled orphan, When `startupSweep` runs, Then the orphan is removed before the call resolves (PRD-CTR-03).
6. Given the created container, Then its labels are found by the existing label lookup (PRD-CTR-04).
7. Given the image record, Then the digest matches the libpod inspect value and the container has no mount whose source is a socket path (PRD-CTR-05, `socket-path` property).
