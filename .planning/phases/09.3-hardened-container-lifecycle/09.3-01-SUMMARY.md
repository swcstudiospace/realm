# Phase 9.3 summary: hardened container lifecycle (plan 09.3-01)

Status: built and verified on the final tree, with open items. The lifecycle creates, verifies, deletes and sweeps sandbox containers through the libpod REST API, and a derived image was built and checked live. Two checks are partial or unit-level only (see Not verified here). The 9.5 launch path and the 9.6 live suites remain open.

## Delivered and verified

### L1: libpod create and start

- `createContainer(spec)` and `startContainer(id)` were added to the libpod client and routes, pinned to `/v5.7.1/libpod/...`.
- Podman 5.7.1 silently ignores several field names in the plan (`read_only`, tmpfs map, `pids_limit`, `memory`, `nano_cpus`, `network`, `security_opt`). A real create and inspect showed this. The body now uses `read_only_filesystem`, `mounts` (tmpfs `/tmp` and `/run` with `nosuid,nodev`), `resource_limits` (pids 512, memory 1 GiB, CPU quota 200000 with period 100000 for 2 CPUs; `NanoCpus` 2000000000 confirmed live), `netns` with nsmode `none`, and `no_new_privileges`.
- Podman 5.7.1 answers DELETE with 200, not 204. The client accepts both.
- Podman inspect reports the bare container name, without the leading slash. The delete scope compares the bare name and tolerates the slash form. Before this fix, delete missed its own container. It was fixed and re-run on the rebuilt tree.

### L2: kernel capability reader

- `readHostProcStatus` and `attachKernelCaps` moved from `session-execution.ts` into `src/runtime/kernel-caps.ts`. Both files import from the new module, so the driver does not import `session-execution.ts`.
- Inbound kernel capability values from the engine are stripped. Only the host `/proc` read attaches them. A missing set fails closed.

### L3: derived image

- The image is built from `sandbox/Dockerfile` (phase 9.2). The builder is the gcc 13.3.0 bookworm image pinned by digest (<gcc-base-digest>). The runtime stage is the node 24 bookworm-slim index digest (<node-base-digest>, D-020).
- Final reference: `localhost/realm-agentos:phase9-locked`, digest <image-digest>, size <image-size> bytes, helper SHA-256 <helper-sha256>, source digest <source-sha256>.
- The helper SHA-256 and source digest are in the image labels. The realm runtime configuration key set is closed, so the helper SHA is not in the config. The image key in the config was changed. The previous value is kept in <evidence-dir>.
- The runner library install uses `npm ci --omit=dev --ignore-scripts` from the repo-root `package.json` and `package-lock.json` (security M5). This installs the repo's whole production set (15 packages, including ajv, zod, croner and @xterm), not only the runner's closure. A sandbox-only lock is a follow-up.
- The build context has no `.dockerignore`, so `node_modules` and `.git` are sent to the daemon. This is a performance residual.
- Rollback: remove the derived image with `podman rmi`.

### L4: lifecycle

- `src/runtime/driver/lifecycle.ts` provides `create`, `delete`, and `startupSweep`.
- `create`: creates and starts the container, inspects it, reads the five kernel capability sets for `State.Pid`, and runs `verifyInspect`. Post-create checks also verify the `/workspace` mount options and `Config.Tty`. On any failure it force-removes the container and throws. The 14 properties in `src/runtime/hardening.ts` are unchanged. The post-create checks raise `HardeningRefusal` (extends `RealmError`) because the 14-property type cannot name them without editing `hardening.ts`.
- `create` refuses a sandbox name that is already in use, inspected by name whether labelled or not. A 409 from the engine maps to the new catalogue code `SANDBOX_NAME_IN_USE`. The lifecycle never removes a container on that code, because the container may belong to another sandbox.
- The create path requires the dedicated state directory `<sandbox-state-root>/<sandbox-name>`. No symlink is allowed on the path. A symlinked ancestor is refused. A state directory that contains a socket file is refused. A secret-named file with group or world bits is refused. The state directory must not overlap the workspace (inside it, or equal to it, is refused).
- `delete` removes every container of the sandbox: those with the managed label, the sandbox-name label, or the bare name equal. The role requirement was dropped deliberately so that teardown leaves no sandbox container, including a supervisor role. It then removes the sandbox state directory. A failed state directory removal reports the existing code `CLEANUP_FAILED`. Its reason text is loose for this case; no new code was added. A second delete is a no-op.
- `startupSweep` removes all realm-labelled containers and resolves only after removal.

### L5: image build and live acceptance

- Live acceptance ran against the realm socket, Podman 5.7.1, rootless, with a sandbox created by the lifecycle. The final run used the rebuilt image. Results are in 09.3-VERIFICATION.md.

## Decisions beyond the plan

1. The Podman 5.7.1 body names differ from the plan's names (see L1). Podman silently ignores the plan's names, so the observed names were used.
2. DELETE on Podman 5.7.1 answers 200. Accepted with 204.
3. Podman inspect reports the bare name. The delete scope compares the bare name, tolerating a leading slash.
4. New catalogue code `SANDBOX_NAME_IN_USE` for a create 409. The lifecycle never removes a container on that code.
5. Delete removes every container of the sandbox, including a supervisor role. See L4.
6. Post-create mount-option and tty checks live in the lifecycle, not in `hardening.ts`. Their refusal is `HardeningRefusal`.
7. A failed state directory removal reports `CLEANUP_FAILED` (see L4).
8. The runner dependency set is the repo's production set (see L3).
9. The lifecycle lives in `src/runtime/driver/lifecycle.ts`. The kernel-set reader moved to `src/runtime/kernel-caps.ts`.
10. The state directory check requires the dedicated sandbox directory (see L4).
11. The create path refuses a sandbox name already in use (see L4).
12. Launch and active files (needs operator confirmation). Plan 09.3-01 T2 says delete removes the launch and active files for the sandbox in the secret directory. The phase brief defers launch and active files to phase 9.5 and makes 9.3 acceptance container-level. The 9.3 delete therefore removes the sandbox's containers and its state directory only. The operator should amend 09.3-01-PLAN.md T2 and acceptance 4 to match. The plan file was not edited here.
13. The realm-prefix rule is enforced in `validateContainerSpec` before any request, in addition to the lifecycle check.

- A create that races another create for the same name, between the pre-check and the failed create, can remove the other container on a non-409 failure. The window is narrow. The fix would be a per-name lock in DriverLifecycle; that is not in 9.3.

- `libpod-client.ts` imports the label constants from `openshell.ts`. Move them to a leaf module in a later refactor.
- A symlinked or non-directory sandbox state directory makes delete throw before containers are stopped. This fails closed; it is not a clean teardown.
- DriverLifecycle has no production caller in 9.3. Wiring belongs to phase 9.5.
