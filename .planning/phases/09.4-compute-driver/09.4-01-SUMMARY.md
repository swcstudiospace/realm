## T5: service implementation

`src/runtime/driver/compute-driver.ts` implements the twelve RPCs. The create checks run before any libpod call. A
refusal is `SCHEMA_INVALID`, and the lifecycle spy records zero creates in every refusal test.

Create refuses:
- an image that is not the configured digest exactly, including a tag-only reference;
- a CPU or memory request or limit that differs from the realm profile (2 CPUs, 1 GiB). Other spellings of the same value
  are accepted, for example `2000m` or `1024Mi`;
- a GPU request;
- a non-empty `platform_config` or `driver_config`;
- a user-namespace request;
- an isolation backend selection;
- a non-empty environment;
- an empty argv;
- a sandbox name without the realm prefix, a workspace id outside the safe form, or no spec.

`GetCapabilities` returns the pinned acknowledgement on every call. It declares `openshell.compute.contract` only, with no
isolation backend, and `gateway_manages_lifecycle: false`.

`StopSandbox` and `StartSandbox` return `FAILED_PRECONDITION` through the catalogue code `REALM_INVALID_TRANSITION`,
and they read and change no state (PD-08 default).

`WatchSandboxes` sends every sandbox on connect, then each change, then deleted events. It polls the labelled containers
and stops on client cancel. Stop and cancel are tested through a real gRPC client.

## T6: socket server

`src/runtime/driver/server.ts`:
- the parent directory is created at 0700, or an existing one is set to 0700. It must be a real directory, not a symbolic
  link, and owned by the process account;
- the socket is bound under umask 0177 and verified at 0600 afterwards;
- a regular file, a directory, a symbolic link, or a socket of another owner at the path is refused and left in place;
- a stale socket (no listener) is removed; a live socket is refused with `LOCK_CONFLICT`;
- `close` removes the socket only if it is still a socket.

Tests cover the modes, each refusal, stale removal, and live refusal.

## T9: entry and gateway (code part)

`src/runtime/driver/main.ts` reads its configuration from these variables, and it is the only file that reads
`process.env` for the driver:
- `REALM_DRIVER_NAME`: the driver name in the gateway's `[openshell.drivers.<name>]` table;
- `REALM_DRIVER_SOCKET`: absolute socket path;
- `REALM_DRIVER_SANDBOX_IMAGE`: the digest-pinned image;
- `REALM_DRIVER_STATE_ROOT`, `REALM_DRIVER_SECRET_ROOT`, `REALM_DRIVER_WORKSPACE_ROOT`: absolute roots;
- `XDG_RUNTIME_DIR`: the libpod socket is `$XDG_RUNTIME_DIR/podman/podman.sock`.

It runs `startupSweep`, then binds the socket, then logs the driver name and the socket path. A missing or invalid value
exits 1 with a catalogue code and no value. I ran it with a missing environment (`SCHEMA_INVALID`) and with an unreachable
libpod (`PODMAN_MACHINE_DOWN`): neither created a socket or a directory.

`eslint.config.js` adds `src/runtime/driver/main.ts` to the `process.env` allowlist.

The user unit (HC-04) must set the variables above. That unit and the gateway unit (HC-05) are the lead's steps.

## Decisions and deviations from the plan

These need the owner or lead to confirm or reverse:

1. `AuthenticateSandbox` is not implemented. It returns `UNIMPLEMENTED`, and the driver does not advertise sandbox
   authentication. The lifecycle names `launch.json` and `active` in the secret root, but no code writes them, so there is
   no credential store to authenticate against. Implementing it needs that store.
2. The proto has no network, mount, or capability fields on the sandbox. Those are fixed by the realm profile, and the
   only channels that could carry them (`platform_config` and `driver_config`) are refused when non-empty.
3. Environment is refused when non-empty, because the create body carries no environment. `log_level` is accepted and not
   forwarded. `command` is validated as non-empty and not forwarded: the container runs the idle init, and the argv is for
   the supervisor in phase 9.5.
4. A sandbox name must be realm-prefixed, because the lifecycle requires it. T2 must confirm that the gateway names
   sandboxes that way. If it does not, acceptance 1 fails and this is the first place to look.
5. The driver keeps a registry from sandbox name to gateway sandbox id, filled by create and cleared by delete. The startup
   sweep removes every realm container, so no sandbox survives a restart without an entry. The "realm session records"
   named in the plan are not used, because nothing writes such records for the driver.
6. `gateway_manages_lifecycle` is false, so the gateway should not call `StopSandbox` on shutdown. T2 must confirm.
7. `DeleteWorkspace` removes only an empty workspace. A workspace that still holds files is left, because it may be the
   user's data, and the refusal is `FAILED_PRECONDITION`.
8. A filesystem failure in `EnsureWorkspace` or `DeleteWorkspace` maps to `SCHEMA_INVALID` or `CLEANUP_FAILED`. No catalogue
   code describes a failed workspace mkdir.
9. Capability negotiation: a gateway that requires an unknown capability is refused with `SCHEMA_INVALID`.
