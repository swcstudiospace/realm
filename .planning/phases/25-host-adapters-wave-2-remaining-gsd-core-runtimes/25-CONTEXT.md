**CodeBuddy Code** (`codebuddy`)

### D-25-04. Engine: the `yaml-map` kind (WAVE2-01, plan 25-02)

A new `InstallRecipe` variant `{ kind: "yaml-map"; file: string; path: readonly [string, string]; value: YamlEntry; homeRole?: ... }`, where the path is exactly a parent key and a child key (both `isSafeKeySegment`, no dots) and `YamlEntry` is a flat mapping whose values are strings or arrays of strings (`command`, `args`; nothing else, so the recipe can always be written in plain scalars; a table-time check rejects a string that is not safe as a YAML plain scalar, that starts with a YAML indicator, or that resolves to a boolean, null or number). Ownership is by **key identity and parsed value**, not by text and not by a comment: the host rewrites the file with a comment-preserving round trip that re-quotes and re-flows the entry (E-HM1), so the owned hash is `sha256` of the canonical JSON of the entry **parsed** from the file, as `json-merge` does. Two new modules: `src/host/yaml-scan.ts` (a conservative line scanner; never a parser, never a claim to parse a file) and `src/host/yaml-owned.ts` (`planYamlMapInstall`, `planYamlMapUninstall`, `ownedYamlMapPart`), wired into `planRecipe` and `ownedPart` by the dispatch lines only, `RECIPE_KINDS` in `receipt.ts`, `entryState` in `adapter.ts`.

The scanner contract (every doubt is a refusal, `unparseable` for a file it cannot read, `foreign-content` for a file it can read that already defines the target differently):
- **Unreadable (`unparseable`):** over 1 MiB, a NUL, a BOM, a tab used for indentation, a flow-style root (`{` or `[` as the first non-comment character), a document marker (`---` or `...`) or a `%` directive line, an anchor (`&x`), alias (`*x`) or tag (`!x`) token anywhere outside a comment, a merge key (`<<:`), a complex key (`? `), and any line it cannot classify as blank, comment, `key:`, `key: value` or a continuation of one. A scan never claims more than "the `mcp_servers` mapping is (or is not) here in block style".
- **The parent key.** At column 0, exactly `mcp_servers:` (unquoted, `"mcp_servers":` and `'mcp_servers':` count as the same key), optional trailing comment. Two parent keys: `foreign-content` (a duplicate key). Parent absent: install appends the block at the end of the file. Parent present with a block mapping: the child `realm` is looked for at the child indent (the indent of the first content line below the parent; spaces only; 1 to 8). Parent value is a flow mapping other than exactly `{}`, a scalar, `null` or `~`: `foreign-content` (`{}` alone on the parent line is replaced by the block header). Parent present with no content lines below (null by emptiness): the child is inserted directly below it.
- **The child.** `realm:` (same three key spellings) at the child indent. Two: `foreign-content`. Present: its lines run to the next line at an indent less than or equal to the child indent; the entry is parsed by a tiny reader that accepts exactly `key: scalar`, `key:` followed by a block sequence of scalars, and `key: [scalar, ...]`, with plain, single-quoted and double-quoted scalars (a `\` escape other than `\"` and `\\` is unreadable); any other construct is "not readable" and the entry counts as not equal to the recipe. Equal to the recipe value: no-op if owned by the receipt, otherwise (an identical entry that Realm did not write, for instance one the user added by hand or with `hermes mcp add`) a no-op that Realm does not claim, as `json-merge` does. Different: `foreign-content`. The recipe's own previous value (the receipt hash) is replaced in place.
- **Write.** Realm writes block style with plain scalars, the child indent detected from the file (default 2), the body one indent step deeper (`command: realm`, `args:` then `- mcp`, `- --host`, `- hermes`), in the file's own line ending (LF or CRLF, detected; a file with mixed endings is `unparseable`), after ensuring the file ends in a line ending (recorded as `separatorAdded`). Everything outside the owned lines stays byte for byte: comments, blank lines, other children, quoting, anchors-free by construction. Created parent: recorded in `createdParents` so uninstall removes an `mcp_servers:` header Realm added when it becomes empty.
- **Status and uninstall.** Absent: `missing`. Parses to the receipt's hash: `ok`. Anything else: `drifted`; a file the scanner cannot read: `unreadable`. Uninstall removes exactly the child's lines (and the header and separator Realm created) only when the parsed value hashes to the receipt's; a gone entry (the host's own remover) is a clean no-op that deletes the receipt; a changed one is `drifted` and writes nothing.
- No new `RealmError` code and no new `HostRefusalReason`: refusals use `unparseable`, `foreign-content`, `symlink`, `concurrent-change`. Atomic write, receipt, audit and logging are the engine's (Phase 21), unchanged.

`hermes`' recipe: `{ kind: "yaml-map", file: "config.yaml", path: ["mcp_servers", "realm"], value: { command: "realm", args: ["mcp", "--host", "hermes"] } }`. The owner may delete the kind and the `hermes` row without touching anything else (OQ-25-05); the existing Agent Plugins bundle `adapters/hermes-agent` stays the other route.

### D-25-06. The `shadows` guard (WAVE2-02, plan 25-02)

### Threat model: malicious workload, hostile config content, confinement (summary; each plan carries its STRIDE rows)

The workload is code inside the sandbox plus whatever it writes into the workspace: file content, symlinks, tool-call arguments. It cannot reach the user's host config directories (none is mounted; the workspace, state and channel binds are Phase 19's exact set and are not changed). What this phase adds on the host side, and how each is held:

| Asset | Attack | Hold |
| --- | --- | --- |
