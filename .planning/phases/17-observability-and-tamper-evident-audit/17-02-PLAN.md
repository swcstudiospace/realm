# Phase 17 plan 02 (unit U4a-rest): daemon log events and the crash path

Context: `17-CONTEXT.md` (D-1704, P17-O2, P17-O3, P17-O4 bind this plan) and `17-RESEARCH.md` sections 3.2 (the closed event list and the entry behaviour) and 3.1 (`audit.head`).

## Reconciliation against the code (read-only, 2026-11-02)

Done (on `origin/main`):
- The failure line is the JSON event `daemon.failed` with `ts`, `level`, `event`, `code`. `src/daemon/ensure.ts` parses it (`FAILURE_EVENT`, `failedCode`); LOCK_CONFLICT is still ignored. Commit f27e70e.
- The startup record is `daemon.startup` with the same prefix, written by the entry through the logger (`emitStartup` in `src/daemon/main.ts`). Commits 50fe21f and 2e48073.
- Early and entry failures go through `emitFailure` (`src/daemon/main.ts`): the state directory is unknown at that point, so the sink is stderr, with the same JSON shape.
- `REALM_LOG_LEVEL` is read only in `src/daemon/main.ts`; an invalid value falls back to `info` with one `daemon.log-level` warning (P17-O4).
- The logger, file sink, correlation ids and metrics library are in `src/observe/` (commit 82e3928), with tests in `test/observe/`. The logger never throws; `droppedLines` is counted (QUAL-01 exception (i) is recorded in `.planning/REQUIREMENTS.md`). The daemon now imports the logger, the file sink and the metrics registry (`src/daemon/daemon.ts`, `src/daemon/main.ts`).
- Correlation ids: one per `up` and one per `tool` control request, passed into `ToolDispatcher.call` (`src/daemon/daemon.ts`), with `up.begin`, `up.end`, `tool.result` and `health.probe_failed` logged.
- `onHealthProbeFailure` is called from the health loop (`src/daemon/daemon.ts`), next to `health.probe_failed`.
- Tests migrated to the JSON failure line: `test/daemon/main.test.ts`, `test/cli/cli.test.ts`, `test/daemon/start-failure.test.ts`.

Deviation, recorded, not yet ratified: request and lifecycle lines go to `<stateDir>/requests.log` (`requestLogPath` in `src/daemon/ensure.ts`, rotated at 4 MiB by the file sink), not to `<stateDir>/daemon.log` as D-1704 names. `docs/integration/runtime-decision.md` records the reason: rotating `daemon.log` would strand a later `daemon.failed` line on an unlinked inode. This plan keeps that layout. The owner must ratify it, or direct a change, before this plan merges (open question 1).

Missing (no call site or no file, by grep of `src`):
- `lifecycle.transition` (info). The research's closed list requires it; the transition subscription in `startDaemon` only records a metric.
- `control.refused` (warn, with `code` and `method`) and `control.request` (debug, with `method`).
- `daemon.starting`, `daemon.listening`, `daemon.stopping`, `daemon.stopped` (info).
- `audit.head` (info) at startup and at shutdown, in `daemon.log`. The string appears nowhere in `src`.
- An uncaught-exception and unhandled-rejection path in the daemon entry that logs `daemon.failed` and exits 1 (research section 3.2). The only such handlers are in `src/runtime/agentos-runner.ts`, which is a different process.

Not planned: a rotation fix in `daemonStartFailureSince`. It matters only if `daemon.log` rotates, and under the recorded layout it does not.

## Layout rule for every new line (state it in a code comment where the line is written)
- Lines that belong to a control request or to the daemon's own lifecycle go through the logger the caller passes in `StartDaemonOptions.logger`. In production that is `requests.log`.
- Entry records go through `entryLogger(writeStderr)` in `src/daemon/main.ts`, which is `daemon.log` in production: `daemon.startup`, `daemon.failed`, `audit.head`, and the uncaught-failure record.
- Changing this split is open question 1. Do not change it in this plan.

## Tasks

### T1. `lifecycle.transition` on every state change
- Files: `src/daemon/daemon.ts`
- Action: in the existing `handle.controller.events.subscribe` callback in `startDaemon` (next to `metrics.recordTransition`), call `logger.info("lifecycle.transition", { from, to, ... })`. Add `upId` when the id is set. The bus event's `reason` is free text (`StateTransitionEvent` in `src/core/events.ts`), so log `code` only when `reason` is a catalogue code (use the existing `catalogueCode` helper). Never log the raw reason string.
- Done when: a test whose name contains "lifecycle.transition" drives one transition through the controller and finds one `lifecycle.transition` line with `from`, `to`, and no free-text reason.
- Verify: `npm run build && node --test --test-name-pattern "lifecycle.transition" dist/test/daemon/daemon.test.js`

### T2. `control.request` and `control.refused`
- Files: `src/daemon/daemon.ts`
- Action: where the daemon records control metrics (`metrics.recordControl(request.method, reply?.error !== undefined)`), call `logger.debug("control.request", { method })` for every request. When the reply carries an error, call `logger.warn("control.refused", { method, code })` with the reply's `code` (already an `ErrorCode`; `causeCode` is not logged). Do not log request params, ids, or any other field.
- Done when: tests whose names contain "control.refused" and "control.request" find one `control.refused` warn for a refused `tool` call with its code, one `control.request` debug per request, and no param or payload field in either line.
- Verify: `npm run build && node --test --test-name-pattern "control.refused|control.request" dist/test/daemon/daemon.test.js`

### T3. Daemon lifecycle lines
- Files: `src/daemon/daemon.ts`
- Action: log `daemon.starting` (info) before the startup maintenance runs; `daemon.listening` (info) in the `server.listen` callback, with no fields (the socket path is a host path and is not logged); `daemon.stopping` (info) when `stop()` begins; `daemon.stopped` (info) after teardown completes. Each line is written once per process lifetime. All four go through the logger passed in `options.logger`.
- Done when: a test whose name contains "daemon.starting" and "daemon.listening" starts and stops one daemon with fakes and finds each event exactly once, in order, and `daemon.listening` has no path or socket field.
- Verify: `npm run build && node --test --test-name-pattern "daemon.starting|daemon.listening" dist/test/daemon/daemon.test.js`

### T4. `audit.head` at startup and at shutdown
- Files: `src/daemon/main.ts`
- Action: add `emitAuditHead(stateDir, writeStderr)`. It calls `checkAuditFile(join(stateDir, "audit", "daemon.jsonl"))` from `src/audit/chain.ts`. When the result's `head` is defined it logs `entryLogger(writeStderr).info("audit.head", { seq, line, lineSha256 })`, where `lineSha256` is `head.hash`. When `head` is undefined (missing or unreadable file, or no chained line) it logs nothing. `checkAuditFile` never throws (it returns an exit-2 result), so do not add a catch. Call it in `runDaemon` right after `started` is assigned (startup, after the gate has opened, so `up` is not delayed) and once more after `awaitStop` resolves, before `requests.close()`.
- Done when: a test whose name contains "audit.head" seeds a file with three chained lines, runs `runDaemon` with a fake start, and finds one `audit.head` line in the stderr sink whose `seq` and `lineSha256` equal the `verifyAuditFile` head of that file. A test with no file finds no `audit.head` line.
- Verify: `npm run build && node --test --test-name-pattern "audit.head" dist/test/daemon/main.test.js`
- Stop condition: if `audit.head` must be emitted before the gate opens for any reason, stop and report; do not delay `up`.

### T5. Uncaught exception and unhandled rejection in the entry
- Files: `src/daemon/main.ts`, `test/daemon/main.test.ts`
- Action: add `installFailureHandlers(register, writeStderr)` and call it once from `main()`, not at module import. The handler for each event writes `entryLogger(writeStderr).error(FAILURE_EVENT, { code: codeOf(error) })`, sets `process.exitCode = 1`, and calls `process.exit(1)`. The `register` argument is `(event, listener) => void` and defaults to `process.on`, so the test passes a fake and never installs real process handlers. `codeOf` already maps a non-`RealmError` to `SCHEMA_INVALID`; keep that fallback and name it in the code comment (open question 3). Replace the header comment's "never calls process.exit" with the exact exception: "only the uncaught-failure handler calls process.exit, after logging `daemon.failed`."
- Done when: a test whose name contains "uncaught" calls the registered listener with a `RealmError` and with a plain `Error`; each run writes exactly one `daemon.failed` line with the expected code, sets the exit code to 1, and calls the fake exit once with 1.
- Verify: `npm run build && node --test --test-name-pattern "uncaught" dist/test/daemon/main.test.js`
