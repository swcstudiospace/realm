  <name>Task 1: The Anthropic-format scripted loopback provider</name>
  <files>test/support/scripted-anthropic-provider.ts, test/support/scripted-anthropic-provider.test.ts</files>
  <behavior>
    - A class or factory starts an HTTP server on 127.0.0.1 with a port the operating system picks and exposes the base URL, the placeholder key it requires, the recorded requests and the failures, and a stop that closes the listener and every open socket and is idempotent. It binds loopback only and never makes an outgoing connection.
    - Routes. A POST to the Messages route (the path v1 messages, with or without a query string such as the beta flag) with a JSON body: the request must carry the placeholder key in the x-api-key header or as a bearer value; any other value is answered 401 with an Anthropic-shaped error body and recorded as a rejected request. The body is parsed with a size bound (413 above 1 MiB, 400 for bad JSON). The reply depends on a turn function that defaults to this script: when the request offers a tool whose name equals the configured tool name (default mcp__realm__status) and no message of the request carries a tool_result block, reply with one tool_use block for that tool with a generated id (toolu_ followed by a counter) and the input given by the script (default an empty object) and stop reason tool_use; otherwise reply with a text block containing the configured final text (default done) and stop reason end_turn. A POST to the token count route (v1 messages count_tokens) answers an object with input_tokens 1. A GET of the models route answers an empty data list object. A CONNECT request or an absolute-URL proxy request is answered 403 and recorded as a proxy refusal, never forwarded. Every other path is 404 with an Anthropic-shaped error body and is recorded.
    - Streaming. When the body has stream true the reply is a server-sent event stream with these events in order: message_start (a message object with id, type message, role assistant, model, an empty content list, null stop_reason and a usage object), content_block_start for index 0 (a tool_use block with id, name and an empty input object, or a text block with empty text), content_block_delta (an input_json_delta with the partial_json string for a tool call, or a text_delta with the text), content_block_stop, message_delta (the stop_reason and a usage object), message_stop. Each event has an event line and a data line and a blank line. Without stream the reply is the single message object with the content blocks, the stop_reason and the usage.
    - Recording. Each request is recorded as: the route, whether the key was accepted, the model name string, the names of the tools offered (names only), whether it carried a tool_result block and how many messages it held, and whether it was streamed. The recorder never keeps message text, tool schemas, headers other than a boolean for the key, or the key itself. getters: requests, rejected, proxyRefusals, failures.
    - The turn function is injectable so a test can script other replies; the default script is the one above. Pure encoders (the streamed event list for a tool call and for a text, the non-streamed message) are exported from the module for the tests and are used by the server.
    - Hermetic tests: the encoders produce the event order and the fields above for both block kinds; a real socket test (the test client is the Node http client against the started server) checks the tool-call reply, the text reply after a tool_result, the 401 for a wrong key, the 403 for a proxy-form request, the 404 for an unknown path, the 413 and 400 cases, the count route and the models route; a recorded request holds no message text, no schema text and no key; stop is idempotent and leaves no listener.
  </behavior>
