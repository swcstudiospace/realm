## Phase Boundary

Phase 32 built per-session, per-host capability tokens and shipped them with the default `off`. Its verification record (`32-VERIFICATION.md`) lists what was not shown. Three of those items are this phase:

- **Items 5 and R4.** Every local run of the capability tests was as root, where file-mode and owner guards rest on an injected uid. The regular-user result rests on CI. EVID-01 is the run as a non-root user on a host with Yama `ptrace_scope` 1.
- **Item 1.** The claim that a process which is not a descendant of the token holder cannot read the token from its memory under Yama `ptrace_scope` 1 is marked `[INFERENCE]` in `docs/integration/mcp.md` (Q10, "Evidence limits"). An informational probe exists in `test/daemon/capability-e2e.test.ts`, but it skips as root, has never been run as a regular user, and its design cannot settle the claim (see D-35-03). EVID-02 is a probe that can: a non-root, non-descendant, same-uid process, with positive controls, with the result recorded either way.
- **Item 2.** Enforce mode was never run on the production stack with a real host attached. EVID-03 is that run: claude through the daemon, enforce on, the audit lines checked for host and kid, and no token in any log.

The phase measures and records. It changes no product behaviour: no file under `src/` changes, no error code, no schema key, no default. The default flip is Phase 34. A defect that a measurement exposes is reported with its catalogue code and the owning phase and is never patched here (the Phase 31 rule).

### What this phase must not claim (read this before the rest)

1. **No defence against a same-uid reader of the key file.** `keys.json` is a 0600 file of the same uid. A same-uid process can read it and mint any token, or run the same `capability-attach` request a host runs. A memory-read result, whichever way it falls, does not change that. The evidence page says so next to the memory result, in the same table row.
2. **A negative memory result is a result about one kernel configuration.** It is about this kernel, Yama at the recorded `ptrace_scope`, this Node version and this process layout. It is not a statement about other kernels, about `ptrace_scope` 0, about root, about a descendant of the holder, or about `process_vm_readv` (not exercised; the same access check on Linux, `[INFERENCE]` from the kernel documentation, not measured).
3. **A scripted loopback model turn is not a real model turn.** If the host-driven proof of EVID-03 uses a scripted provider, the page says "claude issued the call against a scripted provider", never "claude used Realm with a model".
4. **No claim from a skipped test.** A test that skips (not Linux, root, `ptrace_scope` below the stated bound, gate closed) is `not-run`, never a pass.

### Out of scope

Changing a default, the token format, the gate, the client or the audit schema (Phases 32 and 34); the cold-attach behaviour (Phase 33; EVID-03 observes its interaction with enforce once, in one step, and proves nothing about cold attach itself); an enrollment secret or any authentication of the attach (deferred in Phase 32); other hosts than claude for the live proof (codex and opencode run in Phase 33 and 36); Node versions other than the one on this machine (the CI matrix covers 22.x and 24.x; this phase records the one version it ran); other kernels.

### D-35-03. EVID-02: the probe (plan 35-02)

**The question.** Can a process that is the same uid as the token holder, is not root, and is not an ancestor of the holder (so Yama's descendant rule does not apply to it), read the capability token or the signing key out of the holder's memory, and what does it learn from `/proc/PID/environ`? The kernel's rule, from its Yama documentation `[INFERENCE]` until measured: opening `/proc/PID/mem` and `PTRACE_ATTACH` need the ptrace attach check, which at `ptrace_scope` 1 admits only a tracer that is an ancestor of the target (or has `CAP_SYS_PTRACE`, or the target allowed it); reading `/proc/PID/environ` needs the weaker read check, which Yama does not restrict. The probe measures both and does not rely on this reading.

**Arms and controls.** One result is only readable with its controls:

| Arm | Probe process | Target | Purpose |
| --- | --- | --- | --- |
| N (subject) | non-root, same uid, not an ancestor of the target, started detached so it is reparented | the token holder, a real `DaemonClient` with a real token from a real daemon in enforce mode (the rig; plan 35-03 adds the live `realm mcp --host claude` and the live daemon) | the measurement |
| D (descendant control) | non-root, same uid; it is the ancestor: it spawns the holder itself | a synthetic holder that holds a freshly minted token-shaped string and an environment marker | shows the scanner finds a token in a Node heap when the kernel allows the read; a negative in N means nothing without it |
| R (root control) | root | the same target as N | shows the scanner finds the real token in the real holder when no kernel rule applies; separates "the probe cannot find it" from "the kernel refused it" |

Arms N and D run when the test runs as a non-root user; arm R runs when it runs as root. The test chooses by uid, so one file serves both runs and no gate variable exists. The recorded result of the phase is the triple (N, D, R) from the same kernel on the same day.

**What the probe does.** It reads `/proc/sys/kernel/yama/ptrace_scope`, the target's `/proc/PID/status` (`Uid`, `TracerPid`), then `/proc/PID/environ` (open, read, and whether a planted marker name and the token shape occur), then `/proc/PID/maps` and, for the memory read, opens `/proc/PID/mem` and reads **every** readable private writable region (`rw-p`) in chunks of 1 MiB with an overlap of 512 bytes (the channel bound on a token is 512 characters), with no region count cap and no per-region size cap, bounded only by a total of 2 GiB read and 60 seconds, and reports coverage: regions listed, regions read, regions failed by errno, bytes read. It searches each chunk, as Latin-1 and as UTF-16LE, for the prefix `rcap1.` and for each named needle it was given on standard input (the exact token and the signing key text in the rig, nothing in the live arm). For each token-shaped candidate it reports the encoding, the length, the first 8 hex characters of the SHA-256 and the public claims decoded from the payload (`host`, `kid`, the first 8 hex characters of the SHA-256 of `sid`, `exp`), and never the text. A needle hit is reported by name and count. The report is JSON; the test asserts that its serialisation contains neither the token nor the key (the redaction rule of Phase 32 applied to the evidence itself). It also records, for arm N only, whether the keyring file is readable by the probe (it is the same uid; recorded so the memory result is never read alone).

**The decision rule (frozen here, before any run).** With controls D and R both `found` and coverage in N complete (every listed region read or failed with an errno that is itself recorded):
- N `denied` at open of `/proc/PID/mem`, or N read all regions with zero hits: the memory-read claim is **settled for this kernel and this `ptrace_scope`**: "a same-uid non-descendant non-root process did not obtain the token or the key from the holder's memory". The page states the limits of item 2 of "What this phase must not claim" in the same row.
- N `found`: the claim is **refuted for this configuration**; the page says a same-uid non-descendant reader obtained the token (or key) from memory, and the docs text that asserted otherwise is replaced.
- A control not `found`, or coverage incomplete without a recorded cause: **inconclusive**; the claim stays `[INFERENCE]`, the page says why, and the run is repeated after the cause is fixed (a test-side cause) or the item is carried with the named reason.
The environment read is recorded separately and never changes this rule: `readable` with the marker found means a same-uid reader sees the holder's environment (so nothing secret may ever be put there, which the product does not do); `denied:CODE` is recorded as such.

**Code shape.** A test-support module `test/support/memory-probe.ts` (pure parsing, chunk scanning and report building, the probe's reads, the detached starter) and its entry `test/support/memory-probe-run.ts` (reads its specification from standard input, writes the report to a file named on its command line), compiled by the existing `tsc` build and run from `dist` by `process.execPath`. A test `test/daemon/capability-memory-probe.test.ts` (basename free of `mcp` and `acp`) drives the arms against the rig. The informational test in `capability-e2e.test.ts` is removed in the same change (clean cutover; nothing keeps two probes). Hermetic unit tests of the pure parts (a token split across a chunk boundary is found; a UTF-16LE token is found; a report never contains a needle; a refused open is recorded as `denied:CODE` with zero regions; a region list parse) run for every contributor and in CI.

### D-35-04. EVID-03: the live enforce proof (plan 35-03)

**What "claude through the daemon with the host attached under enforce" requires.** A tool call (E-35-04). Two drives, each with its own evidence tier, both run in the window:

- **Launcher-driven (always run).** A scripted MCP client starts the exact command claude's recipe registers, `realm mcp --host claude`, on the production stack, under the default (enforce) policy, makes `status` and `list` calls (and `read` of a file the test plants under the pinned workspace), and records the audit lines. It starts **cold** (no prior `realm up`) once and polls `status` until the realm is active (Phase 33's contract: not-active status and refusals until ready), so the interplay of enforce and serve-early is observed once. Tier: "the registered host command, driven by a script". It does not show that claude issued the call.
- **Host-driven (run when feasible).** The real claude CLI (2.1.322 or the version on the machine, recorded) runs `claude -p` in an isolated `CLAUDE_CONFIG_DIR` with the recipe installed and the wire recorder in front of `realm mcp --host claude`, against a loopback scripted provider that speaks the Anthropic Messages format and answers the first request with a tool call to the Realm `status` tool and the next with a text. No credential (a placeholder API key value the provider checks), no real model, no traffic leaves the machine. The wire recorder shows `tools/call` from claude. Tier: "claude issued the call, against a scripted provider". Feasibility is an open technical question (whether claude 2.1.322 completes a turn against such a provider), so plan 35-03 answers it first in a hermetic task on the validator-tier rig; if it cannot, the named reason is recorded and EVID-03 is `partial` with the launcher-driven tier only (OQ-35-02, OQ-35-03).

**EVID-03 recorded means:** the effective mode was `enforce` with no policy edit (`realm host token status`, the doctor item `capability-tokens`); at least one attach line exists for the session with `host` `claude` and a `kid` equal to the active kid reported by `realm host token status`; every admission and result line of every tokened call carries `host` `claude` and that `kid`; the attach line precedes the first call line; `realm audit verify --session ID` passes on the live audit file, and editing `host` or `kid` of a line in a copy makes the verification fail (the chain covers the fields; Phase 32 tested this in a rig, here it is shown on the live file's copy); and no token and no key text appears in any sink (D-35-05). The record names the tier. With the host-driven tier it is `recorded`; with the launcher-driven tier only it is `partial`, stating "the registered host command was driven by a script; claude itself did not issue a tool call".

**Live probe.** While the launcher-driven session is open, the non-descendant same-uid probe of plan 35-02 (same module, no new code) is aimed at the live `realm mcp --host claude` process (the token holder) and at the live daemon (the key holder), with no needle text (the real key is never passed to a probe), and the report is recorded as an N-arm observation of the live stack. The rig result of plan 35-02 is the settling one; the live result corroborates it or contradicts it.

### D-35-08. Windows

Each plan has its own window; each is a blocking-human checkpoint: the person runs it as `realmlive`, under the shared live lock, serially, with a before and after snapshot (containers, sandboxes, `hosts` entries in the state root, workspace entries, the account's node processes, and the hashes of the real `.claude.json`, `.codex/config.toml` and the state `policy.json`), a stop rule (a failed step is reported with its catalogue code and the owning plan, never retried silently), and no push, pull request or merge from the window. The windows of plans 35-01 and 35-02 touch no production stack (they run in-process fake-runtime tests); the lock is held anyway because they run as the account that owns the stack and the startup reap is account-wide. The window of plan 35-03 uses the production stack: rootless Podman 5.7.1, the OpenShell gateway, the digest-pinned image, the driver config and socket. If the owner does not open a window, execution stops at that plan's first checkpoint and reports BLOCKED with the unmet precondition; the hermetic work of that plan (code, tests, page skeleton) is still complete and stands.

### D-35-09. Hygiene constraints for every plan

- `AGENTS.md` applies: strict TypeScript, `RealmError` with catalogue codes where product code is involved (none here), a timeout on every async boundary, no silent catch, no suppression comments, `process.env` read only at the three entry edges (test files read it where the live files already do, at the top of the file, through an injected `env` parameter below that), no new dependency.
- Lint traps for the new test code: no unnecessary conditions after an assertion narrows, `restrict-template-expressions` (convert numbers with `String(...)`), `no-base-to-string`, `prefer-const`, `void test(...)` for test registration, no unused imports after a test is moved.
- Tests must pass as a regular non-root user (the point of EVID-01), no host-local absolute paths in committed files, no source-text tests, test file basenames must not contain `mcp` or `acp` (the taxonomy test), and the `[INFERENCE]`, `Observed`, `From code` labels are used as in the Phase 32 documents.
- Gates the parent runs after each plan lands: `npm run typecheck`, `npx eslint .`, `npm run build`, `npm test`, `npm run test:scripts`, `npm run check:docs`, `npm run check:gates`, and `node scripts/check/host-paths.mjs`. The default-mode docs guard (`scripts/check/default-mode.mjs`) reads the prose of every new page: no sentence may say advisory is the default.
- The JSON-RPC and MCP era rules of `docs/integration/mcp.md` apply to every test that speaks MCP: a legacy-era client sends `initialize`, a modern-era client (claude 2.1.322, observed 2026-11-18) sends `server/discover` and no `initialize`; JSON-RPC ids are echoed, notifications get no reply, and a tool refusal is a tool result with `isError`, not a JSON-RPC error.
