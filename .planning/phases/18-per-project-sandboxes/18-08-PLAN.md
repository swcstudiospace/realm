# Phase 18 plan 08 (unit C1): CLI behaviour on the selection, and its tests

## Reconciliation against the code (read-only, 2026-11-02)

- Plan 05 already moved the call sites: `runUp`, `runDown`, `runMetrics`, `runStatus`, `runMcp`, `runAcp` and `ensureSharedDaemon` carry the selection of their workspace through `selectionOf` (`src/daemon/client.ts`), and `daemonAnswers` takes it. This plan does not repeat that work.
- `runDoctor` (`src/cli/main.ts`) still sends `doctor` with no params. C4 makes the selection optional for `doctor`: without one the daemon reports the agent-OS reading as unbound. This plan decides when the CLI sends one.
- `test/cli/cli.test.ts` and `test/cli/mcp-attach.test.ts` already carry the expectations updated in plan 05. This plan adds the cases that assert the new behaviour.

## Scope and ownership

Owns the three files listed. The daemon side is plan 06. The Omp surface is plan 10. Contract item C4 of `docs/integration/runtime-decision.md` binds every task.

Owner rules: no live step, no build or test run inside the replan, no git command, no commit. The CLI reads `process.env` only where it already does (the entry edge).

Behavioural consequence to report to the parent, recorded in plan 12: `realm status`, `realm metrics` and `realm down` run outside every policy root report `POLICY_DENIED`, and so does the `tool` call that `realm mcp` and `realm acp` make on their attached client. C4 names these four methods (`status`, `down`, `tool` and `metrics`). Each previously reported the daemon's state. A `realm down` outside the roots therefore no longer answers the unbound snapshot; inside the roots it still does.

## Tasks

### T1. The doctor selection and the command tests
- Files: `src/cli/main.ts`, `test/cli/cli.test.ts`
- Action: in `runDoctor`, when a workspace is given with `--workspace`, send `{ id: 1, method: "doctor", params: { selection: selectionOf(workspace) } }`; without `--workspace` send the request with no params, as today. No other source change is made in this plan.
- Done when: `test/cli/cli.test.ts` gains cases asserting what the fake send receives: (a) `realm status --workspace D` sends a selection whose `sessionId` is `sessionIdOfWorkspace(realpath(D))`; (b) `realm down --workspace D` sends that selection and no other method; (c) `realm up --workspace D` sends `params` equal to `{ workspaceRoot }` with no selection; (d) `realm metrics --workspace D` sends a selection; (e) `realm doctor` with no `--workspace` sends no params, and `realm doctor --workspace D` sends the selection; (f) a `--workspace` path that does not exist exits 1 with `POLICY_DENIED` and the fake send records no call; (g) a `POLICY_DENIED` reply from the daemon for `status`, `metrics` or `down` (each for a directory outside every policy root) is printed with exit 1 and that code, unchanged, and the command sends no further request.
- Verify: `npm run build && node --test dist/test/cli/cli.test.js`

### T2. realm mcp and realm acp attach by selection
- Files: `test/cli/mcp-attach.test.ts`
- Action: add cases to the existing file, using its injected `connect` fake, which records its arguments. (a) `realm mcp --workspace D` calls `connect` with the socket path and the selection of D, and calls `up` with no argument; (b) `realm acp --workspace D` does the same; (c) a `status` reply inside `up` whose `sessionId` differs from the selection is refused by the client, and the command exits 1 with `SCHEMA_INVALID` on stderr with no frames written. The `connect` fake may return a client that rejects `up` with `SCHEMA_INVALID`, the code the real client throws.
- Done when: the three cases pass with the existing ones unchanged, and each case asserts the recorded arguments or the exit code and stderr.
- Verify: `npm run build && node --test dist/test/cli/mcp-attach.test.js`
