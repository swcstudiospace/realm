# Phase 18 plan 11 (unit T2): surface tests for the selection

## Reconciliation against the code (read-only, 2026-11-02)

- `test/support/realm-daemon-fixture.ts` `startRealmDaemon(options)` starts the real daemon in the test process with `startDaemon` over the existing fakes, for one configured root (`options.workspace`). Plan 06 removed its literal session id. Its `status`, `up` and `down` helpers are the surface that tests call.
- `test/surfaces/daemon-equivalence.test.ts` checks that the surfaces give equal replies through one daemon. It uses one workspace.
- `test/mcp/server.test.ts` and `test/acp/agent.test.ts` drive the MCP and ACP servers through a dispatcher. They do not attach to a daemon.
- Callers of `startRealmDaemon`: `test/daemon/realm-daemon-fixture.test.ts` and `test/integration/omp-guard.test.ts`, the only integration importer. `test/integration/omp-ompx05.test.ts` uses the production-live helpers and is in plan 13's scope, not this plan's.
- `attachDaemon` in `src/omp/extension.ts` is a closure inside the default export `realmExtension`. It is not importable. The Omp leg of the equivalence test therefore reproduces its calls (`selectionOf`, `connectDaemon`, `up()`), and the closure's own behaviour is covered by plan 10's extension tests.

## Scope and ownership

Owns the four files listed. The fixture's option shape does not change: a test's projects are directories under the one configured `workspace`, so no existing caller changes. The integration tests stay in plan 13's live scope; this plan adds no live step.

Owner rules: no live step, no build or test run inside the replan, no git command, no commit. The tests assert observable replies and audit lines, not source text.

## Tasks

### T1. The fixture serves two projects on one daemon
- Files: `test/support/realm-daemon-fixture.ts`
- Action: keep `startRealmDaemon(options)` and its options (`stateDir`, `workspace`, `mode`) exactly as plan 06 left them. The configured `workspace` is the root that contains every project a test uses. Add to the returned fixture `selectionFor(project: string): ControlSelection`, which is `selectionOf(project)` from `src/daemon/client.ts`, and `connectFor(project: string): DaemonClient`, which is `connectDaemon(socketPath, selectionFor(project))`. The fixture's `status`, `up` and `down` helpers take the project they address and send that project's selection; a project outside the root is refused by the daemon, not by the fixture.
- Done when: `test/daemon/realm-daemon-fixture.test.ts` passes with its call sites unchanged, and `test/integration/omp-guard.test.ts` (its call sites unchanged, run by the parent at the wave gate) type-checks; the two-project case in `test/surfaces/daemon-equivalence.test.ts` (T2) exercises `selectionFor` and `connectFor` with two projects.
- Verify: `npm run build && node --test dist/test/daemon/realm-daemon-fixture.test.js`

### T2. Surface tests: CLI, MCP, ACP and Omp on two projects
- Files: `test/surfaces/daemon-equivalence.test.ts`, `test/mcp/server.test.ts`, `test/acp/agent.test.ts`
- Action: in `daemon-equivalence.test.ts`, add: with two projects A and B under the fixture's root on one daemon, the `status`, `up` and `down` replies for A are equal whether sent by the CLI send path (the `sendRequest` request the CLI issues, with `selectionOf(A)` in params), by the MCP client path (`connectFor(A)`), or by the Omp client calls (`selectionOf(A)`, `connectDaemon(socketPath, selection)`, `up()`, as `attachDaemon` in `src/omp/extension.ts` makes them); the same holds for B. The replies for A and B differ only by `sessionId` and `boundRoot`. In `test/mcp/server.test.ts`, add: a server whose dispatcher is the client of A answers a `tool` call and writes its audit line to A's audit file; the server whose dispatcher is B's client writes to B's file; neither file contains the other's line. In `test/acp/agent.test.ts`, add the same two-project case for the ACP agent. Use the fixture from T1 and temporary project directories under one root. Each assertion checks a reply value or an audit line.
- Done when: the three files pass with `node --test dist/test/surfaces/daemon-equivalence.test.js dist/test/mcp/server.test.js dist/test/acp/agent.test.js`; the cases for each surface assert their own session's audit file and reply, and no existing case expectation is changed except where it asserted a selection-free request.
- Verify: `npm run build && node --test dist/test/surfaces/daemon-equivalence.test.js dist/test/mcp/server.test.js dist/test/acp/agent.test.js`
