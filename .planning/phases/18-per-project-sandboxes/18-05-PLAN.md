## Tasks

### T1. The selection envelope and its validator
- Files: `src/daemon/channel.ts`, `test/daemon/channel.test.ts`
- Action: in `channel.ts`, add `export interface ControlSelection { readonly workspaceRoot: string; readonly sessionId: string }` and `export function parseControlSelection(method: ControlMethod, params: unknown): { readonly selection: ControlSelection | null }`. Rules per method. `up`: `params` must be an object with exactly one own key, `workspaceRoot`, a string of 1 to 4096 characters starting with `/`; `sessionId` present is refused. `status`, `tool`, `down`, `metrics`: `params.selection` must be an object with exactly the keys `workspaceRoot` (as above) and `sessionId` (a string that passes `isSessionId`); any other key or any missing key is refused. `doctor`: `params` may be absent, in which case the result is `{ selection: null }`; if present it must carry a valid selection as above. Any refusal throws `makeRealmError("SCHEMA_INVALID")`. The validator does not canonicalize paths and does not compare the id with the path: that check needs the daemon's pinned identity and belongs to plan 06 (it calls `sessionIdOfWorkspace` on the pinned realpath). Add a `selectionParams(selection: ControlSelection): { readonly selection: ControlSelection }` helper for the client's use. Keep `CONTROL_METHODS`, the timeouts and the wire format unchanged.
- Done when: `test/daemon/channel.test.ts` gains cases asserting the thrown code or the returned value: `up` with `{workspaceRoot: "/x"}` is accepted; `up` with `sessionId` is `SCHEMA_INVALID`; `status` without `selection` is `SCHEMA_INVALID`; `status` with `selection` missing `sessionId` is `SCHEMA_INVALID`; a `sessionId` containing `/` or `..` is `SCHEMA_INVALID`; a relative `workspaceRoot` is `SCHEMA_INVALID`; an extra key inside `selection` is `SCHEMA_INVALID`; `doctor` with no params returns `{ selection: null }`; `doctor` with a malformed selection is `SCHEMA_INVALID`; a 4097-character path is `SCHEMA_INVALID`. The existing cases pass unchanged.
- Verify: `npm run build && node --test dist/test/daemon/channel.test.js`

### T2. The client holds one selection, sends it on every request, and detaches on close
- Files: `src/daemon/client.ts`, `src/daemon/ensure.ts`, `test/daemon/client.test.ts`, `test/daemon/ensure.test.ts`
- Action: in `client.ts`, add `export function selectionOf(workspaceRoot: string): ControlSelection`. It calls `realpathSync` on the path (a failure throws `POLICY_DENIED`, matching `bindRoot`) and returns `{ workspaceRoot: real, sessionId: sessionIdOfWorkspace(real) }`. This is the only derivation of a selection in `src/`. Change `connectDaemon` to `connectDaemon(socketPath: string, selection: ControlSelection): DaemonClient`. The selection is fixed at construction and never inferred. `status()`, `call(tool)` and `metrics()` send `selectionParams(selection)` as params (`call` sends `{ tool, ...selectionParams }`; keep the existing `tool` key). `up()` takes no argument and sends `{ workspaceRoot: selection.workspaceRoot }`; the client refuses with `SCHEMA_INVALID` a reply whose `sessionId` differs from `selection.sessionId`. Add `sessionId: string` to `DaemonStatus` and require it in `isDaemonStatus`; keep `boundRoot`. `close()` marks this client closed and affects no other client and no session; document this in the header comment. Validate `selection` at construction with `parseControlSelection` for the method it will send (`up` shape, then `status` shape): an invalid selection throws `SCHEMA_INVALID` synchronously from `connectDaemon`. In `ensure.ts`, change `daemonAnswers(connect)` to `daemonAnswers(connect, selection)`: it calls `connect(socketPath, selection)`; its `status()` call is unchanged.
- Done when: `test/daemon/client.test.ts` passes these cases against a real `net` server bound to a temporary socket, which answers each request line with a reply it builds: (a) two clients for projects A and B on one socket each send their own `workspaceRoot` and `sessionId` on `status`, `call` and `metrics`, verified by the request lines the server received; (b) interleaved calls from both clients all resolve with their own reply; (c) `close()` on client A makes A's later requests refuse with `REALM_NOT_ACTIVE` and leaves B's next request answered; (d) `up()` returning a `sessionId` other than the constructed one is refused with `SCHEMA_INVALID`; (e) `connectDaemon` with an invalid selection throws `SCHEMA_INVALID` before any socket is opened; (f) a reconnect (a new client for the same selection) after close succeeds, showing that no session state lives in the client; (g) `selectionOf` of a path that does not exist throws `POLICY_DENIED`. The client test's replies carry `sessionId`. The real-daemon cases that used to end this file move to plan 06 and are not part of this file any more. `test/daemon/ensure.test.ts` passes its selection to every `daemonAnswers` call and asserts that the probe calls `connect` with the given socket path and selection; the absent, starting and answering classifications and the refusal propagation stay as they are.
- Verify: `npm run build && node --test dist/test/daemon/client.test.js dist/test/daemon/ensure.test.js`
