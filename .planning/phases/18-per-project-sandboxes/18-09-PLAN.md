# Phase 18 plan 09 (unit M1): startup maintenance attribution and registry cleanup

## Reconciliation against the code (read-only, 2026-11-02)

- `src/daemon/daemon.ts` `runStartupMaintenance` reaps first (`reapStartup`, which deletes every record, `src/session/reap.ts`), then runs `sweepOrphanTempFiles` with an `audit` callback that calls `appendAudit(stateDir, { sessionId: deps.sessionId, … })` at HEAD. After plan 06, the `sessionId` input is replaced by `attributeOrphan`, which this plan implements.
- Records are deleted before the sweep, so at sweep time no record names a session. The attribution therefore needs a capture taken before the reap (contract C9).
- `src/daemon/main.ts` `emitStartup` logs the `StartupReport` fields explicitly. The new fields are added to that explicit list.
- Registry entries (`<stateDir>/workspaces/`, plan 02) are not removed by the reap today; this plan removes them at startup.
- `test/daemon/daemon.test.ts` and `test/daemon/main.test.ts` already test the maintenance report and the startup line; the executor extends them.

## Scope and ownership

Owns the four files listed. Phase 17's startup log line is the base for the new fields; this plan changes no other part of the log. Contract item C9 of `docs/integration/runtime-decision.md` binds this plan. Phase 19 replaces the reap itself; nothing here changes the reap's behaviour.

Owner rules: no live step, no build or test run inside the replan, no git command, no commit. The orphan-line audit is not written under a fabricated session.

## Tasks

### T1. Attribute orphan lines from the pre-reap records
- Files: `src/daemon/daemon.ts`, `test/daemon/daemon.test.ts`
- Action: in `runStartupMaintenance`, before `reapStartup` is called, build `owners: ReadonlyArray<{ readonly sessionId: string; readonly workspaceRoot: string }>` from `deps.store.list()` and `deps.store.load(id)` (widen the `store` member of `StartupMaintenanceDeps` from `Pick<SessionStore, "list" | "delete">` to add `"load"`, a type-only change in this file); a record that cannot be loaded contributes no owner and is counted in a local `unreadableRecords` count. Replace the `attributeOrphan` input that plan 06 passes as `() => undefined` with the function `ownerOfPath(owners, path)` that returns the `sessionId` of the owner whose `workspaceRoot` equals `path` or is a proper ancestor of it (path-segment comparison with `path.relative`, not string prefix), choosing the longest such root; it returns `undefined` when none matches. In the orphan sweep's `audit` callback, call `appendAudit(stateDir, { sessionId, tool, outcome, path, bytes })` when `ownerOfPath` returns an id, and otherwise increment `unattributedTempFiles`. Add `unattributedTempFiles: number` and `registryEntriesRemoved: number` to `StartupReport`; include `unattributedRecords` (the `unreadableRecords` count) too. The `sessionId` field of `StartupMaintenanceDeps` was removed by plan 06, which is the only plan that removes it; this plan does not touch that field.
  Every `StartupReport` literal gains the three fields `unattributedTempFiles`, `unattributedRecords` and `registryEntriesRemoved`. The `onStartup` literals in `test/daemon/main.test.ts` (their objects open at lines 194, 235, 267, 300 and 336; the `recordsDeleted` lines 197, 238, 270, 303 and 339 lie inside them) each gain `unattributedTempFiles: 0, unattributedRecords: 0, registryEntriesRemoved: 0`. The startup-line `deepEqual` at `test/daemon/main.test.ts` lines 213 to 228 (line 218 is `recordsDeleted`) gains the same three fields with value 0. The two report `deepEqual` expectations in `test/daemon/daemon.test.ts`, at lines 511 to 523 (line 514 is `recordsDeleted`) and at lines 623 to 636 (line 626 is `recordsDeleted`), gain the three fields: the first, from the scenario at lines 471 to 500, takes `unattributedTempFiles: 2`, `unattributedRecords: 1` and `registryEntriesRemoved: 0`, because both orphans lie outside every recorded workspace and the only record, `{"sessionId":"stale-session"}`, fails `SessionStore.load` with `SCHEMA_INVALID`; the second, from the reap failure at lines 604 to 611, takes `0`, `0` and `0`, because it holds no record and no registry entry, and no sweep ran.
  Write no line under the id `daemon` anywhere; a test asserts that `audit/daemon.jsonl` is absent after a startup with sessions.
- Done when: `test/daemon/daemon.test.ts` gains cases: (a) two records for projects A and B recorded, a temp file placed under A and another under B, and a temp file outside both: after startup, `audit/<idA>.jsonl` holds one orphan line whose path is the A file, `audit/<idB>.jsonl` holds the B line, and the outside file's removal appears in the report as `unattributedTempFiles: 1` with no audit line written under any session id; (b) `audit/daemon.jsonl` does not exist after the startup; (c) a record file that is unreadable (written as invalid JSON) is counted in `unattributedRecords` and the start still completes; (d) the reap order is observed: the orphan temp removal happens after the reap deletes the records (asserted by the report's counts and the record store's listing at the time of the sweep callback).
- Verify: `npm run build && node --test dist/test/daemon/daemon.test.js`

### T2. Registry entries are removed by the startup reap, and reported
- Files: `src/daemon/daemon.ts`, `src/daemon/main.ts`, `test/daemon/main.test.ts`
- Action: in `runStartupMaintenance`, after the reap has deleted the records and before the temp-file sweep, call `listWorkspaceEntryIds(stateDir)` and `removeWorkspaceEntry(stateDir, id)` for each id, counting the removals in `registryEntriesRemoved`. A removal failure is a reap failure and uses the existing `reapFailure` path with the catalogue code of the error. In `src/daemon/main.ts` `emitStartup`, add `unattributedTempFiles`, `unattributedRecords` and `registryEntriesRemoved` to the explicit field list of the startup line; keep every existing field and its name. Add a test in `test/daemon/main.test.ts`: a startup with one leftover registry entry and one leftover record logs `registryEntriesRemoved: 1` and `recordsDeleted: 1` on the startup line, and the entry's file is gone.
- Done when: `test/daemon/main.test.ts` asserts the new startup-line fields with their values and that the existing fields are unchanged in name; `test/daemon/daemon.test.ts` asserts that a leftover registry entry is removed by a startup and that a second startup removes nothing (`registryEntriesRemoved: 0`).
- Verify: `npm run build && node --test dist/test/daemon/main.test.js dist/test/daemon/daemon.test.js`
