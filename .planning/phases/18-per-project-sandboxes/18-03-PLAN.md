## Tasks

### T1. The admission ledger
- Files: `src/daemon/admission.ts`, `test/daemon/admission.test.ts`
- Action: create `src/daemon/admission.ts` exporting `class AdmissionLedger`. Constructor: `new AdmissionLedger({ maxSessions: number; recordedIds: () => readonly string[] })`. `maxSessions` must be a positive integer, otherwise `SCHEMA_INVALID`. Internal state: `reserved: Set<string>` (in-flight and live reservations) and `unproven: Set<string>` (ids whose removal failed). Committed set = union of `recordedIds()` (evaluated at each call), `reserved` and `unproven`, by id. Methods: `reserve(sessionId: string): void` is synchronous; if `sessionId` is already in the committed set it returns without change; otherwise if the committed set has `maxSessions` or more members it throws `POLICY_DENIED`; otherwise it adds `sessionId` to `reserved`. `markUnproven(sessionId: string): void` moves an id from `reserved` to `unproven` (a failed destroy or a failed start keeps its slot). `release(sessionId: string): void` removes the id from `reserved` and `unproven`; the caller calls it only after the container removal is proven. `committedCount(): number` returns the size of the committed set. `isCommitted(sessionId: string): boolean`. No method performs I/O and none awaits.
- Done when: `test/daemon/admission.test.ts` passes these cases: with `maxSessions = 2`, a third distinct `reserve` in the same synchronous turn throws `POLICY_DENIED` and `committedCount()` stays 2; `reserve` of an id already reserved returns and does not increase the count; a `recordedIds` list containing an id counts it once with a reservation of the same id; `markUnproven` then a new distinct `reserve` at the limit still throws `POLICY_DENIED`; `release` after `markUnproven` frees the slot and a new `reserve` succeeds; a `maxSessions` of 0 or 1.5 throws `SCHEMA_INVALID`; the ledger has no `await`: `reserve` returns `void`, not a promise, which the test asserts by checking `reserve(...)` returns `undefined` synchronously).
- Verify: `npm run build && node --test dist/test/daemon/admission.test.js`

### T2. The aggregate constants and the derived bound
- Files: `src/runtime/hardening.ts`, `test/runtime/hardening.test.ts`
- Action: in `src/runtime/hardening.ts`, add to the `HARDENING_PROFILE` object two fields, `aggregateMemoryBytes: 4 * 1024 * 1024 * 1024` and `aggregateNanoCpus: 4_000_000_000`, placed after `nanoCpus`, each with a one-line comment that states the aggregate budget and that the per-container caps stay as they are. Add the exported function `maxConcurrentSessions(profile: { memoryBytes: number; nanoCpus: number; aggregateMemoryBytes: number; aggregateNanoCpus: number }): number` that returns `Math.min(Math.floor(aggregateMemoryBytes / memoryBytes), Math.floor(aggregateNanoCpus / nanoCpus))`, and throws `SCHEMA_INVALID` if any input is not a positive integer or if the result is less than 1. Export `MAX_CONCURRENT_SESSIONS = maxConcurrentSessions(HARDENING_PROFILE)`. Do not change any other field; do not add a config or policy read. The two fields are inside `hardeningEvidenceDigest`, which hashes the whole profile, so every sandbox created after this change carries a different provisioning-evidence digest. C7 of plan 01 records that as intended; no stored digest is compared, so no existing sandbox is affected.
- Done when: `test/runtime/hardening.test.ts` gains the case "the derived concurrent-session bound is 2 with the profile's per-container caps", asserting `MAX_CONCURRENT_SESSIONS === 2`; a case asserting that halving `aggregateMemoryBytes` gives 2 through the function; a case asserting that a zero input throws `SCHEMA_INVALID`; a case asserting that `JSON.stringify(HARDENING_PROFILE)` contains the keys `aggregateMemoryBytes` and `aggregateNanoCpus`, and that `hardeningEvidenceDigest(image)` equals the sha256 of the canonical document built from that profile, so the two new fields are inside the evidence digest; the existing cases pass unchanged.
- Verify: `npm run build && node --test dist/test/runtime/hardening.test.js`
