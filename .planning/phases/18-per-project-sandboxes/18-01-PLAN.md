- Startup reap removes every realm container and every record (`src/session/reap.ts`, `src/runtime/sweep.ts` `removeAllRealmContainers`). No record survives a daemon start in the current code, so no legacy record can be adopted.
- Gateway identity evidence: the vendored `DriverSandbox` message (`src/runtime/driver/proto/compute_driver.proto`, lines 157 to 172) carries `name` (field 2, the compute-runtime sandbox name the driver already consumes) and `workspace` (field 6, whose comment states no normalization). The realm's pinned create argv (`buildCreateArgv`, `src/runtime/openshell.ts`) has no workspace selector; it passes `--name realm-<sessionId>`.

### T1. Record the per-project session contract
- Files: `docs/integration/runtime-decision.md`
- Action: insert a new level-two section `## Per-project session contract (Phase 18, MULTI-01 to MULTI-06, 2026-11-02)` directly after the existing `## Per-project sessions (Phase 18, MULTI-01)` section and before `## Startup reaper and scratch volume (Phase 19, RES-01)`. Begin the section with one paragraph stating that it refines the accepted 2026-10-30 decision and supersedes nothing in D5. Then write items C1 to C10 below as bold-labelled paragraphs. Each item carries its label (engineering decision, engineering ruling ratified or set by owner 2026-11-02 for C1, C2 and C7, or owner ruling for C6 alone), its decision, its reason, and its evidence in the form `(evidence: <repo path>)`. Do not change any existing text.

  **C1 identity. Engineering ruling, ratified by owner 2026-11-02, within the accepted D5(i).** The session id of a project is `p` followed by the first twelve lowercase hexadecimal characters of the SHA-256 of the canonical project path (the realpath, UTF-8 encoded, no trailing separator). The id is thirteen characters, matches `SESSION_ID_PATTERN` in `src/session/paths.ts`, and gives sandbox name `realm-p<12 hex>` of nineteen characters, the gateway maximum. The function is `sessionIdOfWorkspace` in `src/session/paths.ts` (plan 02). Collision rule: when a persisted record for the id names a different canonical path (`SessionRecord.workspaceRoot`), or a registry entry for the id names one, the request is refused with `SANDBOX_NAME_IN_USE` before any runtime I/O. Reason: D5(i) fixes the id as a function of the canonical path; the choice of hash, prefix and twelve hexadecimal characters is the engineering step that keeps the sandbox name within the gateway limit. A 48-bit id is not collision-free in principle, so the refusal, not the hash, is the guarantee; the birthday bound for a thousand projects is about 1.8e-9. (evidence: `src/session/paths.ts`, `SESSION_ID_PATTERN`; `src/runtime/openshell.ts`, `GATEWAY_SANDBOX_NAME_MAX_LENGTH`; `src/contract/validate.ts`, `SessionRecord`)

  **C2 containment. Engineering ruling, ratified by owner 2026-11-02: the explicit reading of MULTI-02.** Eligibility of a requested path is `bindWorkspaceUnderPolicy(policy.workspaceRoots, requested)` (existing) and, in addition, the canonical path equals or lies below the canonical `workspaceRoot` of `config.json`. Equality is allowed for both checks. The containment rule of MULTI-02 is read as "inside or equal to a configured root", which is what the existing helper does. Reason: `isInsideRoot` already admits equality, and `init` writes the project directory as the one policy root, so refusing equality would break the single-project layout that `init` writes. The owner-facing wording, "a descendant of a configured root" (`.planning/REQUIREMENTS.md`, MULTI-02; `.planning/MILESTONE-CONTEXT.md`, D5(i)), is unchanged; this record is where the reading is stated. A path failing either check is `POLICY_DENIED` before any container, record, registry or driver call. For every later use of a selected project, the daemon runs `verifyPinnedAt` on the pinned identity and requires the id to equal `sessionIdOfWorkspace` of the pinned realpath. A renamed or swapped directory is `POLICY_DENIED`. `verifyPinnedAt` is not weakened. (evidence: `src/fs/root.ts`, `bindWorkspaceUnderPolicy`, `verifyPinnedAt`, `isInsideRoot`; `src/cli/init.ts`, the written `workspaceRoots`)

  **C3 mount authority. Engineering decision.** Each admitted project gets a registry entry `<stateDir>/workspaces/<sessionId>.json` (directory mode 0700, file mode 0600, written atomically) holding `{ "schema": 1, "sessionId", "workspaceRoot", "dev", "ino" }`. The daemon writes it before the driver create. The driver resolves the sandbox name `realm-<id>` to the registry entry and checks, in order: the sandbox name carries the `realm-` prefix and its remainder passes `isSessionId`; the id recomputed from `workspaceRoot` equals `sessionId`; `workspaceRoot` equals or lies below the driver's own `config.workspaceRoot`; `verifyPinnedAt` of the stored device and inode at that path passes. Any failure is a driver refusal with check name `create.workspace`, with no container, no state directory and no secret entry. The driver mounts the resolved path at `/workspace`. The session verifier compares the inspected mount with the binding of the request, which the controller has verified against the session pin, so a driver that resolved a different directory fails the create closed. The session-side refusal of a request whose `workspaceRoot` differs from the pinned root (`requireSameDirectory` in `src/runtime/session-execution.ts`) is removed for that reason. The same resolution runs in `ValidateSandboxCreate`, because the two RPCs share `planCreate` (`src/runtime/driver/compute-driver.ts`, line 347). That is intended: validation refuses what create would refuse and writes nothing. Reason for the carrier: the gateway sandbox identity (`DriverSandbox.name`, which the driver already consumes) is the one identity the driver receives; the pinned create argv has no workspace selector, and the gateway normalizes an empty `ObjectMeta.workspace` to `default`. If a read-only capture of the pinned CLI create help, taken at execution time, shows a workspace selector, this choice is revisited before plan 04 starts, not after. The registry is a daemon-written, account-owned file, the same trust base as `config.json`; the driver's recomputation and containment checks make a wrong entry fail closed, and they do not trust the daemon's canonicalization blindly. (evidence: `src/runtime/driver/proto/compute_driver.proto`, `DriverSandbox.name`; `src/runtime/driver/proto/datamodel.proto`, `ObjectMeta.workspace`, lines 60 to 62; `src/runtime/session-execution.ts`, `requireSameDirectory`; `src/runtime/driver/compute-driver.ts`, `planCreate`)

  **C4 selection. Engineering decision.** Every stateless control request that addresses a project carries `selection`: `{ "workspaceRoot": <string>, "sessionId": <string> }`. `up` carries `workspaceRoot` only; the daemon derives the id and returns it on the reply. `status`, `tool`, `down` and `metrics` carry both fields. `doctor` carries an optional selection; without one it reports the agent-OS reading as unbound. A missing, malformed or self-inconsistent selection (the `sessionId` differs from the id derived from `workspaceRoot`) is `SCHEMA_INVALID`. A selection whose `workspaceRoot` lies outside every policy root, or outside the configured workspace root, is `POLICY_DENIED` for each of the four methods `status`, `down`, `tool` and `metrics` before any runtime I/O. This check runs before the no-live-session answer, so an outside directory never receives the unbound snapshot; `realm status`, `realm metrics`, `realm down` and the `tool` call run outside every project therefore report `POLICY_DENIED` (plan 12 records it). For `status` and `down`, a valid selection inside the roots with no live session answers the unbound snapshot, which keeps the idempotent `down` of CORE-06; `tool` with no live session is `REALM_NOT_ACTIVE`. The daemon never infers a session from the socket's lifetime, from the last `up`, or from a global implicit session. The client holds its selection; `close()` detaches the client's transport and removes no session. Reason: MULTI-03 requires each control request to name its project, because the control socket carries no session state. (evidence: `src/daemon/channel.ts`, `CONTROL_METHODS`; `src/daemon/client.ts`, `connectDaemon`)

  **C5 lifecycle. Engineering decision.** A session `down` is `controller.destroy()` on that session's handle: it stops and removes its container, releases its locks, and deletes its record. Then the daemon deletes its registry entry and releases its admission slot. Each step runs only after the previous one succeeded. If the destroy fails, the session stays registered and its slot stays committed. A `down` that leaves no live or admitting session (no registry entry and no admission reservation) arms the daemon stop, including a `down` whose selection names a project with no live session, which replies with the unbound snapshot. A `down` of one project while another session is live or admitting never stops the daemon. This keeps HEAD's effect: HEAD's `down` always closed the server, so a daemon that holds no session would otherwise keep the control socket after its last session ended. The reply for an unbound project is unchanged, so the idempotent `down` of CORE-06 keeps its answer; only the daemon's exit follows it. A daemon signal (SIGTERM or SIGINT) runs the in-process stop of every handle with `controller.stop()`, which keeps records and registry entries for the next start's reap, as today. Signal shutdown sends no control message and is never the session `down`. A host shutdown never sends `down`. This record changes HEAD's reading of `down` (every `down` closed the daemon), and plan 12 lists that change. (evidence: `src/lifecycle/controller.ts`, `LifecycleController.destroy` and `stop`; `src/daemon/daemon.ts`, `stop` and `shutdown` at HEAD)

  **C6 per-session state. Owner ruling, 2026-11-02 (an owner ruling in this record; C1, C2 and C7 are owner-ratified or owner-set).** Each session owns its record, its pinned project directory, its sandbox, its bind mount, its audit file `<stateDir>/audit/<sessionId>.jsonl`, its lock table (created by `createRealmHandle`), its controller, its dispatcher and its status snapshot. Metrics stay daemon-wide, because the counters are not listed in MULTI-03. Log lines for session events carry `sessionId` and never a path. `audit.head` is emitted per session when its handle is created and when it is destroyed; it is not emitted at daemon start or on signal shutdown. This amends Phase 17 ruling O-d by owner choice on 2026-11-02 (`audit.head` covers the daemon's own session file), because the daemon no longer owns one; the amendment is a consequence of this contract and is listed in plan 12's verification. (evidence: `src/realm/compose.ts`, `createRealmHandle`; `src/audit/chain.ts`, `readAuditHead`)

  **C7 aggregate bound. Set by owner 2026-11-02 (4 GiB, 4e9 nanoCpus, 2 sessions).** `HARDENING_PROFILE` in `src/runtime/hardening.ts` gains two constants: `aggregateMemoryBytes = 4 * 1024 ** 3` and `aggregateNanoCpus = 4_000_000_000`. Their derivation from the existing per-container caps is `maxSessions = min(floor(aggregateMemoryBytes / memoryBytes), floor(aggregateNanoCpus / nanoCpus))` with `memoryBytes = 1 GiB` and `nanoCpus = 2e9`, which is 2. Reason for the choice: the only existing numeric resource limits live in `HARDENING_PROFILE`; the bound needs one number that no existing setting holds; a config key or a policy key would be a schema change and a new catalogue entry would be a second one, and neither is needed. These are the only new numbers. They are an engineering choice, not a user setting. The executor of plan 03 records the host's observed memory and CPU count (read-only) beside them. If the host cannot hold two sessions at these bounds, plan 03 reports BLOCKED; only the owner can change these values. Admission is a synchronous reservation in the daemon, performed before the probe's first `await` in `up`: the committed set is the union, by session id, of the persisted record ids, the in-flight reservations and the ids whose removal is not yet proven. A reservation that would make the set exceed `maxSessions` is refused with `POLICY_DENIED`. Reason for that code: it exists, and the bound is a realm policy; it is not retryable, a trade-off recorded here. A reservation is released only after proven removal, or when no container was created for the id. The driver does not count sessions; the daemon is the single owner of the count, so there are no competing counters. Effect on provisioning evidence: the two fields change `HARDENING_PROFILE`, and `hardeningEvidenceDigest` hashes the whole profile, so every sandbox created after the change carries a different evidence digest. That is intended: the digest names the profile the verifier checked, and the profile now carries the aggregate budget. No stored digest is compared (the digest is sent to the sandbox runtime as provisioning evidence, `src/runtime/driver/runtime-channel.ts`), so no existing sandbox is affected. (evidence: `src/runtime/hardening.ts`, `HARDENING_PROFILE` and `hardeningEvidenceDigest`; `src/runtime/session-execution.ts`, `SANDBOX_CPUS` and `SANDBOX_MEMORY`; `src/runtime/driver/runtime-channel.ts`, `evidenceDigest`)

  **C8 legacy. Engineering decision.** The fixed id `daemon` is retired with no alias. The startup reap removes `sessions/daemon.json` as it removes every record, so no record conversion is needed. `audit/daemon.jsonl` is kept as history: verification and reconciliation still read it, and no new line is written under the id `daemon`. The session-record schema, the audit line format and the error catalogue are unchanged. Reason: the reap already removes every record at start, so a conversion would have nothing to convert, and a retained alias would be a second identity. (evidence: `src/daemon/main.ts`, `SESSION_ID`; `src/session/reap.ts`)

  **C9 startup maintenance attribution. Engineering decision.** Before the reap deletes records, the daemon captures the recorded canonical workspace of each session. An orphan temp-file sweep line is written to the audit file of the session whose recorded workspace contains the removed path. A removed path that no captured workspace contains is counted in the startup report and logged as an entry-log count; it is written to no session audit, so no daemon session is fabricated. Reason: records are deleted before the sweep runs, so the owner of a removed path can be known only from a capture taken before the reap. Registry entries left by a previous generation are removed at startup and counted (plan 09). Sequence is unchanged: reap, then temp-file sweep, then audit reconciliation, then serve. Phase 19 changes the reap and adds adoption; that change builds on C9. (evidence: `src/daemon/daemon.ts`, `runStartupMaintenance`; `src/fs/temp-sweep.ts`, `sweepOrphanTempFiles`)

  **C10 driver reservations. Engineering decision.** The driver's process-global `rootReserved` exclusion and its single-pinned-root liveness check are replaced by two per-sandbox rules. First, an in-flight reservation, held from before the first await to the end of the create, is keyed by the sandbox name: a create whose name is already reserved is refused with `create.pinned_root_held`. Second, a liveness check refuses a create when a live container of this driver already binds the resolved workspace (same device and inode), where the resolved workspace is the one the registry entry of the name names, not `config.workspaceRoot`. One live container per workspace, not one per driver. Reason for the pair: a create in flight has no container yet, so the name key covers the window before the container exists. Under C1 a directory has one sandbox name, and under C3 the registry check refuses a second name whose entry names a directory it does not derive, so no second name can reach one workspace through a valid entry. A reservation keyed by the workspace as well as by the name was considered and rejected for that reason: no valid input could reach it, so it would be dead state. The rules do not replace the daemon's count (C7). (evidence: `src/runtime/driver/compute-driver.ts`, `rootReserved`, `pinnedRootHeld` and `holdsPinnedRoot`)

  Rejected alternatives, recorded so they are not reopened silently: a workspace selector in the gateway (no evidence in the pinned CLI, C3); a new `config.json` key listing projects (static, not per `up`); a per-session container shared between projects (V2-02, deferred); a new catalogue code for admission (C7 uses `POLICY_DENIED`); a new control method for daemon shutdown (C5 uses the in-process stop); a `down` that never stops the daemon when no session is live (rejected in C5 for the reason given there).
