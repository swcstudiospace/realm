# Phase 18 plan 04 (unit D1): driver mount from the trusted registry

## Reconciliation against the code (read-only, 2026-11-02)

- `src/runtime/driver/compute-driver.ts`: `ComputeDriverConfig.workspaceRoot` is documented as the pinned workspace root, the mount for every sandbox. `planCreate` builds `sandboxBindingOf({ workspaceRoot: config.workspaceRoot, … })` (line 905) and returns `spec.workspaceDir` from the binding (line 919). `createSandbox` refuses while the process-global `rootReserved` is set (line 370) and sets it before the first await (line 373); `pinnedRootHeld` (line 734) refuses while any live container holds `config.workspaceRoot` (`holdsPinnedRoot`, line 1034). `buildSandbox` asserts the pinned root with `assertPinnedWorkspaceRoot(this.config.workspaceRoot)` at its `create.workspace` stage (line 404). `ensureWorkspace` (line 611) also asserts `config.workspaceRoot` with `assertPinnedWorkspaceRoot`; that is the ceiling check, which stays true after this change, so the line is kept. `deleteWorkspace` is always refused and is unchanged.
- The in-flight reservation is keyed by sandbox name only, and the liveness check (`pinnedRootHeld`) reads containers only. Under C1 of plan 01 a directory has one sandbox name, and under C3 the registry check refuses a second name whose entry points at a directory it does not name. So two names on one workspace cannot both pass: the name key refuses a second create under the same name while the first is in flight, and the per-workspace container check refuses a second name once a container is live. This plan implements the per-resolved-workspace liveness check and keeps the name key; it adds no second reservation key, because a key that no valid entry can reach would be dead state.
- `src/runtime/driver/main.ts` derives `roots` with `runtimeRootsOf` through `rootsFromConfig` (which returns the value unchanged) and passes `workspaceRoot: roots.workspaceRoot` to the driver config (line 95). `RuntimeRoots.stateDir` is added by plan 02 (its T3), which this plan depends on. The daemon and the driver read the same `config.json`, so both derive the same `stateDir` (`src/runtime/host-paths.ts`, `readHostRuntime`, and `loadRuntimeConfig`).
- The driver's refusal check names (`src/runtime/driver/refusal.ts`) already include `create.workspace`; no new check name is needed.
- The existing tests exercise one pinned root (`test/runtime/driver/compute-driver.test.ts`, fakes in `test/runtime/driver/fakes.ts`). `test/runtime/driver/socket-server.test.ts` builds its driver through `driverConfig()` (fakes.ts) and creates no sandbox, so it needs no change.

## Tasks

### T1. Resolve the sandbox's workspace from the registry, per sandbox
- Files: `src/runtime/driver/compute-driver.ts`, `src/runtime/driver/main.ts`, `test/runtime/driver/fakes.ts`, `test/runtime/driver/compute-driver.test.ts`, and the create-path test files listed in the frontmatter and in the migration list of the action
- Action: in `compute-driver.ts`, add to `ComputeDriverConfig` the field `readonly stateDir: string` (absolute; the realm state directory whose `workspaces/` subdirectory holds the daemon-written entries of plan 02), and rewrite the doc comment of `workspaceRoot` (line 122) to say it is the ceiling every mounted project must equal or lie below, and that it is never mounted itself. Add a function `resolveSandboxWorkspace(config, sandboxName)` used by `planCreate`. It first requires the name to carry the prefix `realm-`, and computes `sessionId = sandboxName.slice("realm-".length)`; a name without the prefix, or a `sessionId` that fails `isSessionId`, is refused with `refusal(scope, "create.workspace")`. It calls `readWorkspaceEntry(config.stateDir, sessionId)` (plan 02, which already refuses an entry whose recomputed id differs) and refuses with `create.workspace` when the entry is null or the read throws. It checks with `isInsideRoot(bindRoot(config.workspaceRoot), entry.workspaceRoot)` that the entry's `workspaceRoot` equals or lies below the ceiling (equality is accepted), and calls `verifyWorkspaceEntry(entry)`, refusing with the same check name on any throw. It returns the verified `PinnedRoot.realPath`. `planCreate` then uses that path, not `config.workspaceRoot`, for `sandboxBindingOf({ workspaceRoot: resolved, … })` and sets `spec.workspaceDir` from the binding. `planCreate` stays free of writes; the resolution only reads. `planCreate` is shared by `ValidateSandboxCreate` (line 347) and `CreateSandbox` (line 362). That sharing is intended: validation refuses exactly what create would refuse, and it writes nothing. Reservations and liveness (C10): delete the field `rootReserved` (line 294) and the method `pinnedRootHeld` (line 734). Add `private readonly reservedNames = new Set<string>()`. `createSandbox` calls `planCreate` (synchronous, as now), then refuses with `refusal(scope, "create.pinned_root_held", "REALM_INVALID_TRANSITION")` when `reservedNames` already holds the sandbox name; it adds the name before its first await and removes it in `finally`. Then a new private method `workspaceHeld(scope, resolved: string)` does what `pinnedRootHeld` did, with `holdsWorkspace(inspect, resolved)` in place of `holdsPinnedRoot(inspect, this.config.workspaceRoot)`, so the liveness check is per resolved workspace, and its refusal check name stays `create.pinned_root_held`. Rename `holdsPinnedRoot` (line 1034) to `holdsWorkspace` and keep its body. In `buildSandbox`, replace the `create.workspace` stage's `assertPinnedWorkspaceRoot(this.config.workspaceRoot)` (line 404) with `assertPinnedWorkspaceRoot(plan.spec.workspaceDir)`. `ensureWorkspace` (line 611) keeps its check of the ceiling. Comments: every comment that names `rootReserved`, `pinnedRootHeld`, `holdsPinnedRoot`, or the one-pinned-root rule is rewritten to describe the name reservation and the per-workspace liveness check; at HEAD these are lines 13, 17, 122, 292 to 294, 367, 447, 563, 568, 572, 608, 615, 730 to 732 and 1028 to 1032. `RuntimeRoots.stateDir` comes from plan 02 (its T3). In `src/runtime/driver/main.ts`, `loadDriverProcessConfig` puts `stateDir: roots.stateDir` in the driver config beside `workspaceRoot: roots.workspaceRoot` (line 95); `rootsFromConfig` returns `RuntimeRoots` only, not a `RuntimeConfig`. The registry path is derived inside `src/session/workspace-registry.ts` and nowhere else. Do not change the RPC table, `ensureWorkspace`'s checks, `deleteWorkspace`, the admission acknowledgement, or the launch-material checks. Do not add a refusal check name. Test fixtures: `driverConfig()` in `test/runtime/driver/fakes.ts` sets `stateDir` to a fresh directory under its temporary base, and the same file exports `writeSandboxWorkspaceEntry(config, workspaceDir)`, which creates the directory under the ceiling and writes the registry entry for `sessionIdOfWorkspace(realpath(workspaceDir))`. Every test that creates a sandbox names it `realm-<sessionIdOfWorkspace(...)>` for a project directory under the ceiling and writes that entry first; the names `realm-session-1` and `realm-agent-1` are replaced by derived names in those tests. Migration list, closed: the grep `git grep -l -e '\.createSandbox(' -e 'planCreate(' -- test` returns `test/runtime/driver/channel-artifacts.test.ts`, `test/runtime/driver/compute-driver.test.ts`, `test/runtime/driver/create-refusal.test.ts`, `test/runtime/driver/driver-main.test.ts`, `test/runtime/driver/gateway-wire.test.ts`, `test/runtime/driver/launch-material.test.ts`, `test/runtime/driver/runtime-channel.test.ts`, `test/runtime/driver/runtime-listener.test.ts`, `test/runtime/driver/supervisor-exit.test.ts` and `test/runtime/sandbox-binding.test.ts`. `test/runtime/driver/driver-service.test.ts` is added as well: its RPC calls `call(h, "CreateSandbox", …)` at lines 141 and 153 reach `planCreate`, and the grep does not match them. - Done when: `test/runtime/driver/compute-driver.test.ts` gains cases, each asserting the observable result on the fake libpod and the fake filesystem: (a) a create for sandbox `realm-p<id>` with a valid entry for `<id>` created under the test's ceiling produces a created spec whose `workspaceDir` equals the entry's realpath and whose mount list names it; (b) no entry, an entry naming another id, an entry for a path outside the ceiling, and an entry whose device and inode no longer match each refuse with `create.workspace`, and the fake libpod records zero create calls and no state directory exists; (c) two entries for two directories under the ceiling let two creates succeed on one driver instance, and a third create for the first directory is refused with `create.pinned_root_held` while the first container is live (the per-workspace liveness check); (d) two concurrent creates for the same sandbox name: the second is refused while the first is in flight; (e) a second name whose entry file is a copy of the first directory's entry (named for the second name's id, carrying the first directory's `workspaceRoot`) is refused with `create.workspace` by the recomputed-id check, with zero libpod calls and no state directory, which is why two names cannot resolve to one directory; (f) `ValidateSandboxCreate` for a name with no entry is refused with `create.workspace`, and for a name with a valid entry it is accepted, and in both cases it writes nothing (no state directory, no secret entry, no libpod call); (g) a sandbox name without the `realm-` prefix, and one whose remainder fails `isSessionId`, are each refused with `create.workspace` before any libpod call.
