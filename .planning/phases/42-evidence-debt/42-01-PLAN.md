## Behaviour (the contract the tasks implement)

Exports of the module, used by the test file (a script test imports them; there is no export gate for scripts): `HEADER_PATTERN`, `parseHeader(subject)`, `hasBreakingFooter(text)`, `isDeclared(body)`, `classifyCommit(commit)`, `evaluate(input)`, `formatReport(result)`, `collectCommits(options)`, `readPullRequest(text)`, `runGuard(options)`. `runGuard({ argv, env, cwd, out })` returns the exit code and writes lines through `out(line)`; the entry guard calls it with `process.argv.slice(2)`, `process.env`, `process.cwd()` and `console.log`, and sets `process.exitCode`.

Parsing:

- `HEADER_PATTERN` is `/^([a-z]+)(?:\(([^)]*)\))?(!)?:/`, the exact text of the changelog generator. `parseHeader(subject)` returns `null` when it does not match, else `{ type, scope, breaking }` with `breaking` true when the `!` group matched.
- `hasBreakingFooter(text)` is true when a line of `text` matches `/^BREAKING[ -]CHANGE: \S/m` (line start, uppercase token, one colon and a space, then text). A sentence that contains the words mid-line, a lowercase form, a token with no colon and a token with no value are not footers.
- `isDeclared(body)` is true when a line matches `/^[ \t]*[-*][ \t]+\[[xX]\][ \t]+Breaking change\b/m`. The unticked template line `- [ ] Breaking change: ...` is not a declaration.
- `classifyCommit({ hash, subject, body })` returns the same fields plus `marked` (header `!`), `footer` (footer in the body) and `breaking` (marked or footer).

Evaluation (`evaluate({ commits, title, body, landing, rangeError })`, pure):

- `signals`: the list of `commit-marker`, `commit-footer`, `body-footer`, `declared` that hold, each with a count for the commit signals.
- With `rangeError` set: one unproven finding `range-unavailable` and nothing else is evaluated (the signals of the body can still be listed).
- With no signal: result `ok`, no finding.
- Landing `merge` or `unknown`: `commit-unmarked` when no commit subject carries the marker, one finding per commit that has a footer and no marker (the finding names the short hash and the quoted subject).
- Landing `squash` or `unknown`: when the title is `undefined` or null, `title-not-supplied` (unproven); otherwise `title-unmarked` unless `parseHeader(title)` is non-null with `breaking` true.
- Result word: `violations` when any violation, else `unproven` when any unproven finding, else `ok`. Findings are ordered: range, commit, title.

Inputs (`runGuard`):

- Flags (node:util `parseArgs`, strict): `--base REF`, `--head REF`, `--title TEXT`, `--merge-method merge|squash|unknown`, `--enforce`. `--help` prints the usage and exits 0.
- Environment: `REALM_PR_JSON` (inline JSON), else when `GITHUB_EVENT_NAME` is `pull_request` the JSON file named by `GITHUB_EVENT_PATH`; `REALM_BREAKING_GUARD=enforce` enables enforcement. A flag overrides the JSON field of the same meaning.
- `readPullRequest(text)` accepts the GitHub event shape (`pull_request.title`, `.body`, `.base.sha`, `.head.sha`) and the flat shape (`title`, `body`, `base`, `head`, `merge_method`); a missing or null title or body is `undefined`/empty; a field of the wrong type is an input error (exit 2). The text is refused above 1048576 bytes.
- Default range when neither source gives a base and a head: base `origin/main`, head `HEAD`.
- A ref must be a non-empty string that does not start with `-`; otherwise exit 2.
- The merge method defaults to `unknown`; any other value than the three is exit 2.

Range collection (`collectCommits({ cwd, base, head })`): resolve each ref with `git rev-parse --verify --quiet REF^{commit}` (argument array, 30 s timeout); on failure return `{ commits: [], rangeError: MESSAGE }` where the message names the ref and says a shallow checkout may lack it. Then `git log --no-merges --max-count=2000 --format=%x1e%H%x1f%s%x1f%b BASE..HEAD` (the record format of the changelog generator: record separator 0x1e, field separator 0x1f), `maxBuffer` 16 MiB. A range of exactly 2000 commits is a range error ("range too large to read"). The result is commits newest first.

Output (`formatReport`): the header line `breaking-change guard: RESULT (mode MODE, landing LANDING, range BASE..HEAD, N commits, B breaking)`, a line `signals: ...` (the signal names, or `none`), then one line per finding with two leading spaces: `violation CODE: MESSAGE` or `unproven CODE: MESSAGE`; in report-only mode with findings, a last line `report-only: exit 0; run with --enforce to fail on findings`. The range text and every quoted subject, title or ref is a JSON string literal cut to 200 characters. BASE and HEAD in the header are quoted the same way.

Edge cases the tests must cover: a merge commit in the range is ignored (a merge of main into the branch); a subject that is not a Conventional Commit but carries a footer; a body with the footer in the middle of a paragraph; CRLF in a body; a title with leading whitespace (not conventional); an empty range with a declared body (signal present, rules apply); a null body; a repository with no `origin/main` (range error); a ref that starts with a dash; an invalid merge method; malformed JSON; a JSON file above the size cap; a GITHUB_EVENT_NAME that is not `pull_request` (the file is not read).
